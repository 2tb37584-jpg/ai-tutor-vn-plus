# Product Rules

1. Socratic tutoring before direct answers.
2. A student mistake is a learning signal.
3. Do not trust model-generated math without verification where deterministic verification is feasible.
4. Do not update mastery from a single low-confidence model judgment.
5. Tutor progression should be explicit and testable.
6. Avoid collecting unnecessary student data.
7. Optimize MVP for measurable learning behavior, not feature count.
8. Do not add voice, mobile, whiteboard or broad subject coverage until the core tutor loop passes evals.

9. Every task must map to a roadmap item, core-loop need, blocker, or explicit exit criterion. Otherwise, defer it.
10. Once contracts are stable, prefer end-to-end integration over creating new abstractions or verifier families.
11. Do not implement speculative features or domains without product evidence such as eval cases, user need, a core-loop blocker, or an explicit roadmap requirement.
12. Documentation and design work must be proportional to risk. Use long audits only for architecture, schema, security, mastery semantics, tutor behavior, or similarly high-impact decisions.
13. Do not create a new abstraction unless it removes duplicated logic, enforces a product invariant, or creates a necessary typed boundary.
14. Before expanding into the next module or feature family, close material integration debt in the current core learning loop.
