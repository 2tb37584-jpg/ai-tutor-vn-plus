# M06-12 — Record Deterministic Tutor Reply Mastery Evidence

Status: DONE
Codex: YES
Module: M06 Math Verifier / M08 Mastery
Phase: Phase 2 — Correctness

## Direction gate

Roadmap link: Phase 2 deterministic verification -> Phase 3 adaptive learning boundary
Core-loop impact: Student attempt -> deterministic verification -> mastery evidence
Why now: M06-11 makes deterministic correctness authoritative in live tutor progression, but verified attempts still do not update mastery.
Why not defer: Leaving mastery disconnected means the core learning loop cannot convert trusted attempt evidence into adaptive state.
Exit criterion affected: deterministic evidence must be authoritative and measurable before adaptive-learning expansion.

## Goal

Record mastery evidence for deterministic CORRECT/INCORRECT student attempts in `/tutor/reply`.

This task only connects already-authoritative deterministic attempt evidence to the existing mastery service.

Do not change the mastery algorithm.

## Evidence boundary

Create mastery evidence only when all are true:

- reply intent is a normal ATTEMPT;
- session has a supported deterministic verifier family;
- deterministic policy finishes with CORRECT or INCORRECT;
- current tutor state before this reply is one of:
  - ASK_ATTEMPT
  - HINT_1
  - HINT_2

Do NOT record mastery evidence for:

- HINT_REQUEST;
- UNSUPPORTED;
- exhausted INDETERMINATE;
- no-family / unsupported-family sessions;
- model-only likely_correct;
- current state VERIFY;
- EXPLAIN_STEP / TRANSFER / COMPLETE;
- client `/attempt` claims.

The VERIFY exclusion prevents double-counting the same problem after an attempt already produced deterministic verified evidence.

## Mastery event mapping

Use the existing mastery types.

For deterministic CORRECT:

```text
outcome = MasteryOutcome.CORRECT
```

For deterministic INCORRECT:

```text
outcome = MasteryOutcome.INCORRECT
```

For both:

```text
evidence_type = MasteryEvidenceType.DETERMINISTIC_VERIFICATION
verification_status = mastery.VerificationStatus.VERIFIED
verification_method = session.verification_family
confidence = 1.0
is_transfer = False
```

Identity:

```text
student_id = session.student_id
session_id = session.id
skill_code = session.primary_skill
```

Hint count derives from the state BEFORE transition:

```text
ASK_ATTEMPT -> 0
HINT_1      -> 1
HINT_2      -> 2
```

Do not derive hint count from model output.

## Important enum boundary

There are two different enums named `VerificationStatus`:

- verifier status: CORRECT / INCORRECT / UNSUPPORTED / INDETERMINATE
- mastery status: VERIFIED / UNVERIFIED / UNSUPPORTED / DISPUTED

Alias imports explicitly. Do not treat them as interchangeable.

## Transaction behavior

`record_mastery_evidence(...)` does not commit.

Call it inside the existing `/tutor/reply` transaction before the existing `db.commit()` so the tutor message/session update/mastery update remain in one transaction.

Do not add a second commit.

## Public API behavior

Do not change `TutorReplyResponse`.

Do not expose mastery probability or internal evidence metadata in the reply response in this task.

The existing `/attempt` endpoint must remain client-claim-only and mastery-ineligible.
