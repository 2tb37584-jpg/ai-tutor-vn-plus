# M06-15 — Add Deterministic Factorization Verifier

Status: DONE
Codex: YES
Module: Verifier

## Goal

Add a deterministic `factorization` verifier family that accepts only supported answers which are:

1. algebraically equivalent to the authored polynomial reference; and
2. explicitly written in an accepted nontrivial factored form.

This task must not treat algebraic equivalence alone as evidence of factorization mastery.

## Context

M06-14 established the transfer verification eligibility contract.

Relevant decisions:

- `algebra.factorization` is mastery-bearing.
- Its canonical `verifier_family` is `factorization`.
- The existing `expression_equivalence` verifier can prove polynomial equivalence but cannot by itself prove that the learner actually factored the expression.
- A deterministic factorization verifier can reuse the existing safe polynomial parser/equivalence machinery.
- No new external dependency is required.
- `factorization` becomes deterministic-transfer eligible only after this verifier family is implemented and tested.

The current verifier already exposes these status values:

```text
CORRECT
INCORRECT
UNSUPPORTED
INDETERMINATE
```

These semantics must be preserved.

## Required verifier contract

Add:

```text
ProblemFamily.FACTORIZATION = "factorization"
```

Add a frozen request dataclass conceptually equivalent to:

```python
@dataclass(frozen=True)
class FactorizationVerificationRequest:
    family: ProblemFamily
    reference: str
    candidate: str
```

Include it in the `VerificationRequest` union.

Route it through `verify()` only when:

```text
request.family is ProblemFamily.FACTORIZATION
AND
request is FactorizationVerificationRequest
```

Mismatched request/family must return:

```text
VerificationStatus.UNSUPPORTED
```

## Correctness contract

A candidate is `CORRECT` only when all conditions are true:

```text
1. reference is a supported finite polynomial expression;
2. candidate is a supported finite polynomial expression;
3. candidate is algebraically equivalent to reference;
4. candidate has an accepted explicit factored structure.
```

Algebraic equivalence alone is insufficient.

For example, for:

```text
reference = x^2 - 1
```

this must be `CORRECT`:

```text
(x-1)*(x+1)
```

and this must not be `CORRECT`:

```text
x^2-1
```

even though it is algebraically equivalent.

## Factored-form v1 predicate

Keep the predicate narrow and structural.

Use the parsed candidate expression with evaluation disabled, consistent with the existing safe expression parser.

A candidate counts as explicit factored form when the top-level expression is either:

### A. Nontrivial multiplication

A top-level `Mul` containing at least two factors where at least one factor contains a supported variable.

Examples intended as factored form:

```text
(x-1)*(x+1)
2*(x+3)
x*(x+2)
```

### B. Nontrivial power

A top-level `Pow` where:

```text
exponent is an integer > 1
AND
base contains a supported variable
```

Example:

```text
(x+1)^2
```

Do not recursively accept an expanded top-level `Add` merely because multiplication exists somewhere in a subexpression.

Do not create a general expression-shape language in this task.

## Important edge semantics

The following must be handled explicitly.

### Equivalent but not factored

Supported, equivalent candidate with no accepted top-level factored structure:

```text
INCORRECT
```

Examples:

```text
x^2-1
x^2+2*x+1
```

### Wrong factors

Supported candidate with accepted factor structure but not algebraically equivalent:

```text
INCORRECT
```

Example:

```text
(x-1)*(x-1)
```

for reference:

```text
x^2-1
```

### Unsupported syntax/domain

If the reference or candidate is outside the existing supported finite-polynomial expression domain:

```text
UNSUPPORTED
```

Examples should remain aligned with existing expression-verifier rules, including:

- unsafe characters;
- unsupported symbols;
- variable denominators;
- unsupported powers;
- non-finite expressions.

### Unexpected internal failure

Unexpected parser/simplification/runtime exceptions:

```text
INDETERMINATE
```

Do not collapse internal failure into `INCORRECT`.

## Reuse requirements

Prefer reusing existing private helpers such as:

```text

_is_non_finite
```

and existing symbolic equivalence logic rather than duplicating parsing policy.

If a tiny private helper makes the logic clearer, it may be added inside `verifier.py`.

Do not broaden the existing expression-equivalence parser domain in this task.

```text

```


The single failure is:

```text
tests/test_tutor_verification_context.py::
test_start_persists_only_registry_backed_implemented_verifier_families
```

Observed mismatch:

```text
skill.factorization
registry verifier_family = factorization

expected persisted TutorSession.verification_family = None
actual persisted TutorSession.verification_family = "factorization"
```

Repository inspection shows this is not merely a stale test.

`app/api/tutor.py::_verification_family_for_primary_skill()` currently treats successful construction of:

```python
ProblemFamily(skill.verifier_family)
```

as proof that the family is implemented for TutorSession runtime verification.

After M06-15 adds:

```text
ProblemFamily.FACTORIZATION
```

that helper starts persisting `"factorization"` automatically.

However `app/api/tutor.py::_verification_request_for_session()` currently constructs requests only for:

```text
numeric
expression_equivalence
linear_equation
```

and returns `None` for any other family.

Therefore adding the enum member causes TutorSession to persist a verification family that the current tutor runtime cannot actually reconstruct into a `VerificationRequest`.

This creates an inconsistent session contract.

### Blocker decision

Do not change the existing integration test expectation to `"factorization"`.

Do not modify `app/api/tutor.py` or `tests/test_tutor_verification_context.py` inside M06-15 because they are outside the allowed scope.

M06-15 is BLOCKED until a separate scoped integration task restores the invariant:

```text
a TutorSession.verification_family may be persisted only when
the tutor runtime can deterministically construct the corresponding
VerificationRequest from trusted persisted session context
```

The follow-up task should preserve:

```text

BUT
factorization is not automatically session-verifiable merely because
it is a ProblemFamily enum member
```

unless a separately reviewed trusted factorization reference contract is added.

### Why not wire FactorizationVerificationRequest immediately

The factorization verifier contract requires:

```text
reference = trusted original polynomial expression
candidate = learner factored response
```

The current session verification adapter is tied to existing persisted fields and does not yet establish that it has a trusted original-polynomial reference suitable for this new request.

Do not assume `normalized_problem` or `internal_expected_answer` can safely substitute without a separate contract review.
