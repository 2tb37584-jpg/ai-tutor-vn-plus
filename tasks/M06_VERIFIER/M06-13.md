# M06-13 — Add Safe Verification Decision Telemetry

Status: DONE
Codex: YES
Module: M06 Math Verifier
Phase: Phase 2 — Correctness

## Direction gate

Roadmap link: Phase 2 — analyzer/verifier disagreement escalation
Core-loop impact: Deterministic verification -> observable disagreement/retry/escalation
Why now: M06-11 and M06-12 now make verification authoritative, but there is no operational visibility into disagreement or indeterminate retry behavior.
Why not defer: Without telemetry, verifier/model disagreement and escalation failures cannot be measured safely in production.
Exit criterion affected: supported-domain correctness must be measurable, not only implemented.

## Goal

Add one privacy-safe structured application log event for each supported deterministic verification attempt in `/tutor/reply`.

Do not add a telemetry database, model, migration, service, dependency, or public API field.

## Minimal design

Use Python standard logging in `backend/app/api/tutor.py`.

Emit one final event after deterministic verification policy resolution:

```text
event=tutor_verification_decision
```

Log only safe metadata:

```text
session_id
skill_code
problem_family
verifier_status
model_likely_correct
disagreement
retry_count
escalation_outcome
mastery_eligible
verification_method
```

Definitions:

- `verifier_status`: final verifier status after any allowed retry.
- `retry_count`: 0 or 1.
- `escalation_outcome`: final `EscalationAction.value`.
- `mastery_eligible`: whether this live reply is eligible to emit mastery evidence under current orchestration rules.
- `verification_method`: persisted verifier family.

## Privacy boundary

Never log:

```text
student_message
normalized_problem
internal_expected_answer
message history
TutorTurn.message
image_data_url
raw prompt
API key
student name/email
```

Do not log full `MasteryEvidenceEvent`.

## Event boundary

Emit telemetry only when:

- reply intent is ATTEMPT;
- `_verification_request_for_session(...)` returned a supported typed request;
- deterministic verification/policy resolution ran.

Do not emit this event for:

- HINT_REQUEST;
- `verification_family=None`;
- unsupported/unrecognized persisted family;
- paths where deterministic verification never ran.

Emit exactly one event per reply, after retry resolution is complete.

## Retry behavior

If first verifier result is INDETERMINATE and policy requests retry:

- retry exactly as existing M06-11 behavior;
- final telemetry uses the second verifier status;
- `retry_count=1`.

Otherwise:

```text
retry_count=0
```

Do not add another retry.

## Mastery eligibility field

For telemetry, `mastery_eligible=True` only when all are true:

- final decision is deterministic CORRECT or INCORRECT;
- current pre-transition state is ASK_ATTEMPT, HINT_1, or HINT_2.

Therefore deterministic CORRECT/INCORRECT in VERIFY logs:

```text
mastery_eligible=False
```

This must match M06-12 live evidence-emission rules.

## Logging style

Prefer one compact key=value message via a module logger, for example:

```text
event=tutor_verification_decision session_id=... skill_code=... ...
```

Do not serialize raw request/session objects.

No new logging abstraction is required.
