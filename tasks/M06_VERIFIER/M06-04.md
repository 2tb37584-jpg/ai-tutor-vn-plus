# M06-04 — Introduce Deterministic Verifier Adapter Seam

Status: ACTIVE
Codex: YES
Module: M06 Math Verifier
Phase: Phase 2 — Correctness

## Goal

Introduce a minimal typed deterministic verifier adapter seam for the two verifier families that already exist:

- expression equivalence;
- one-variable linear equation candidate verification.

The new seam must distinguish:

- `CORRECT`;
- `INCORRECT`;
- `UNSUPPORTED`;
- `INDETERMINATE`;

without changing the behavior of any existing public verifier API.

## Context

M06-03 audited the current verifier surface and defined the adapter contract.

Current public APIs in `backend/app/services/verifier.py` are:

```python
equivalent(left: str, right: str) -> bool

classify_linear_equation(
    equation: str,
    variable: str = "x",
) -> LinearEquationResult

verify_linear_equation_solution(
    equation: str,
    candidate: str,
    variable: str = "x",
) -> bool

solve_simple_equation(
    equation: str,
    variable: str = "x",
) -> list[str]
```

Current compatibility semantics must remain unchanged:

```text
equivalent(...)
    -> False for either non-equivalent or unsupported/error input

classify_linear_equation(...)
    -> INVALID for unsupported/error input

verify_linear_equation_solution(...)
    -> False for wrong candidate or unsupported/error input

solve_simple_equation(...)
    -> [] unless exactly one supported solution exists
```

The new adapter seam exists so new orchestration code can distinguish deterministic incorrectness from unsupported/indeterminate verification without breaking old callers.

## Required contract

### Problem family

Define a minimal explicit family enum:

```python
class ProblemFamily(str, Enum):
    EXPRESSION_EQUIVALENCE = "expression_equivalence"
    LINEAR_EQUATION = "linear_equation"
```

Equivalent naming is acceptable only if semantics remain exactly these two families.

### Verification status

Define:

```python
class VerificationStatus(str, Enum):
    CORRECT = "correct"
    INCORRECT = "incorrect"
    UNSUPPORTED = "unsupported"
    INDETERMINATE = "indeterminate"
```

### Result

Define a minimal immutable result:

```python
@dataclass(frozen=True)
class VerificationResult:
    status: VerificationStatus
```

Do not add explanation/confidence fields unless current implementation strictly requires them.

### Requests

Use typed family-specific requests rather than one generic dictionary.

Expected shape:

```python
@dataclass(frozen=True)
class ExpressionEquivalenceRequest:
    family: ProblemFamily
    left: str
    right: str


@dataclass(frozen=True)
class LinearEquationRequest:
    family: ProblemFamily
    equation: str
    candidate: str
    variable: str = "x"
```

A union/type alias may be used:

```python
VerificationRequest = (
    ExpressionEquivalenceRequest
    | LinearEquationRequest
)
```

Do not introduce a generic `dict[str, Any]` request.

## Routing

Provide one deterministic router entry point for the new seam.

Preferred conceptual shape:

```python
def verify(request: VerificationRequest) -> VerificationResult:
    ...
```

Requirements:

- exactly one adapter path per known family;
- no fuzzy classification;
- no LLM selection;
- no fallback from one family to another;
- family classification is assumed to happen upstream;
- unsupported/unregistered family path must not become `CORRECT`.

If the typed request shape makes an unknown enum family impossible to construct naturally, test the router's unsupported/default path without weakening production typing.

## Expression-equivalence adapter semantics

Required mapping:

```text
supported + equivalent
    -> CORRECT

supported + non-equivalent
    -> INCORRECT

known unsupported/unsafe input
    -> UNSUPPORTED

unexpected verifier/runtime failure
    -> INDETERMINATE
```

Known unsupported cases include the current rejected domain such as:

- variable denominators;
- zero denominators;
- unsupported powers;
- unsafe parser input;
- equation input in expression-equivalence mode;
- non-finite expressions.

### Compatibility

Existing:

```python
equivalent(left, right) -> bool
```

must retain all current outputs.

It may delegate to the new detailed verification path, but:

```text
CORRECT -> True
anything else -> False
```

must preserve current tests.

## Linear-equation adapter semantics

The adapter verifies a scalar candidate against a supported one-variable linear equation.

Required mapping:

```text
supported unique equation + correct finite scalar candidate
    -> CORRECT

supported unique equation + wrong finite scalar candidate
    -> INCORRECT

invalid/unsupported equation
    -> UNSUPPORTED

NO_SOLUTION or INFINITELY_MANY_SOLUTIONS
for scalar-candidate verification
    -> UNSUPPORTED

unsupported/non-scalar/non-finite candidate
    -> UNSUPPORTED

unexpected verifier/runtime failure
    -> INDETERMINATE
```

### Compatibility

These existing APIs must remain available and keep current behavior:

```python
classify_linear_equation(...)
verify_linear_equation_solution(...)
solve_simple_equation(...)
```

Do not change their return types.

## Error classification

Known validation/domain failures should map to:

```text
UNSUPPORTED
```

Examples:

- parser rejects unsafe characters;
- unsupported equation shape;
- unsupported variable;
- unsupported denominator/power;
- candidate contains symbols;
- candidate is non-finite.

Unexpected failures that are not part of the declared unsupported domain should map to:

```text
INDETERMINATE
```

Do not silently convert unexpected verifier failure into `INCORRECT`.

Do not expose raw parser/SymPy exceptions through the adapter result.

## Backward compatibility

All pre-existing tests in `backend/tests/test_verifier.py` must continue to pass unchanged in expectation.

Do not remove existing public functions.

Do not change:

```text
LinearEquationStatus
LinearEquationResult
```

semantics.

The adapter seam is additive and internal-compatible.
