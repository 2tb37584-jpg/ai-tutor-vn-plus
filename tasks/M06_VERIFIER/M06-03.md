## Audit result

### Current verifier surface

Current deterministic verifier implementation lives in:

`backend/app/services/verifier.py`

The public verifier entry points are:

```python
equivalent(left: str, right: str) -> bool

classify_linear_equation(
    equation: str,
    variable: str = "x",
) -> LinearEquationResult

verify_linear_equation_solution(
    equation: str,
    candidate: str,
    variable: str = "x",
) -> bool

solve_simple_equation(
    equation: str,
    variable: str = "x",
) -> list[str]
```

There are currently two deterministic problem families.

#### Expression equivalence

`equivalent(left, right)` checks finite school-algebra polynomial expressions over the supported symbols `x`, `y`, and `z`.

The existing tests establish support for cases such as:

```text
(x+1)*(x+1)  ==  x^2+2*x+1
x*(y+z)      ==  x*y+x*z
(x+y)^2      ==  x^2+2*x*y+y^2
x/2          ==  0.5*x
1/2          ==  0.5
```

The current implementation rejects or does not support inputs including:

```text
variable denominators
zero denominators
unsupported powers such as x^(1/2)
negative powers
unsafe parser input
function syntax such as sin(x) or sqrt(x)
equation input passed to the expression verifier
non-finite expressions
```

Its public result is only:

```python
True | False
```

Therefore `False` currently means either:

1. the expressions are deterministically non-equivalent; or
2. the verifier could not support or safely parse the request.

Those states are intentionally indistinguishable at the compatibility API today.

#### One-variable linear equation

`classify_linear_equation()` deterministically classifies supported equations into:

```python
UNIQUE_SOLUTION
NO_SOLUTION
INFINITELY_MANY_SOLUTIONS
INVALID
```

Supported equations are one-variable linear equations using a supported variable and safe finite algebra.

The tests cover:

```text
2*x+3=7
3*(x-2)=9
2*y+3=7
x/2+1=3
x/(2+2)=2
```

The implementation also deterministically recognizes supported constant-result cases such as:

```text
x+1=x+2  -> NO_SOLUTION
x+1=x+1  -> INFINITELY_MANY_SOLUTIONS
```

Inputs classified as `INVALID` include:

```text
missing or multiple "=" signs
unsupported variables
multiple variables
nonlinear equations
variable denominators
zero denominators
unsafe parser input
unsupported function syntax
```

`verify_linear_equation_solution()` verifies only a finite scalar candidate against a supported equation with a unique solution.

Its compatibility result is boolean, so `False` currently includes:

```text
wrong candidate
invalid candidate
unsupported equation
equation without a unique scalar solution
```

`solve_simple_equation()` is a compatibility wrapper:

```python
unique supported solution -> [solution]
anything else             -> []
```

### Existing result and error behavior

The verifier deliberately does not allow parser or SymPy exceptions to escape through its current public compatibility functions.

Existing behavior is:

```text
expression verifier:
    equivalent -> False on unsupported/error

linear classifier:
    classify_linear_equation -> INVALID on unsupported/error

candidate verifier:
    verify_linear_equation_solution -> False on unsupported/error

compatibility solver:
    solve_simple_equation -> [] unless exactly one supported solution exists
```

These public semantics must remain unchanged while the adapter seam is introduced.

### Proposed adapter contract

The first adapter seam should remain inside the existing modular monolith and should not introduce a new dependency or service.

Use two explicit problem families:

```python
class ProblemFamily(str, Enum):
    EXPRESSION_EQUIVALENCE = "expression_equivalence"
    LINEAR_EQUATION = "linear_equation"
```

Use typed family-specific requests rather than one generic dictionary with many optional fields:

```python
@dataclass(frozen=True)
class ExpressionEquivalenceRequest:
    family: ProblemFamily
    left: str
    right: str


@dataclass(frozen=True)
class LinearEquationRequest:
    family: ProblemFamily
    equation: str
    candidate: str
    variable: str = "x"
```

The concrete implementation may enforce the family value by construction or validation.

The shared adapter result should distinguish four states:

```python
class VerificationStatus(str, Enum):
    CORRECT = "correct"
    INCORRECT = "incorrect"
    UNSUPPORTED = "unsupported"
    INDETERMINATE = "indeterminate"


@dataclass(frozen=True)
class VerificationResult:
    status: VerificationStatus
```

No confidence score or LLM-style explanation is required in the first implementation.

Status semantics:

```text
CORRECT
    The request is inside the adapter's deterministic domain and
    the candidate/equivalence claim is proven correct.

INCORRECT
    The request is inside the adapter's deterministic domain and
    is proven incorrect.

UNSUPPORTED
    The request is outside the adapter's declared deterministic
    verification domain or is not applicable to that adapter.

INDETERMINATE
    The request was routed to the correct deterministic adapter,
    but the verifier could not safely produce a deterministic
    conclusion because of an unexpected verifier/runtime condition.
```

Known unsupported syntax or known unsupported mathematical forms should return `UNSUPPORTED`, not `INDETERMINATE`.

`INDETERMINATE` is reserved for unexpected verifier failure and must never be interpreted as correct.

### Adapter input contract

The adapter layer should accept a typed verification request:

```python
VerificationRequest = (
    ExpressionEquivalenceRequest
    | LinearEquationRequest
)
```

The first implementation should not introduce a generic `dict[str, Any]` request.

This keeps invalid combinations such as an equation plus expression-equivalence fields out of the normal path and gives future numeric/unit or geometry families room to define their own typed request.

### Routing rule

Routing must be deterministic and explicit.

Conceptually:

```python
def verify(request: VerificationRequest) -> VerificationResult:
    adapter = ADAPTERS.get(request.family)

    if adapter is None:
        return VerificationResult(
            status=VerificationStatus.UNSUPPORTED,
        )

    return adapter(request)
```

The registry is an internal mapping from one `ProblemFamily` to exactly one adapter.

There must be no fuzzy classification, LLM selection, or fallback from one mathematical family to another inside the deterministic verifier.

Problem-family classification belongs upstream.

The verifier receives an explicit family and deterministically invokes one adapter.

### Expression-equivalence mapping

The expression adapter should expose the distinction hidden by the current boolean API:

```text
valid + equivalent
    -> CORRECT

valid + non-equivalent
    -> INCORRECT

known unsupported/unsafe input
    -> UNSUPPORTED

unexpected deterministic-verifier failure
    -> INDETERMINATE
```

The existing compatibility API remains:

```python
def equivalent(left: str, right: str) -> bool:
    result = detailed_expression_verification(...)
    return result.status is VerificationStatus.CORRECT
```

Therefore every existing `equivalent()` test continues to receive exactly the same boolean output.

### Linear-equation mapping

The linear-equation adapter verifies a scalar candidate for a supported one-variable equation.

Mapping:

```text
supported unique equation + correct finite scalar candidate
    -> CORRECT

supported unique equation + wrong finite scalar candidate
    -> INCORRECT

invalid/unsupported equation
    -> UNSUPPORTED

equation not applicable to unique scalar candidate verification
(NO_SOLUTION or INFINITELY_MANY_SOLUTIONS)
    -> UNSUPPORTED

unsupported/non-scalar candidate
    -> UNSUPPORTED

unexpected deterministic-verifier failure
    -> INDETERMINATE
```

Existing public functions remain compatible:

```python
classify_linear_equation(...)
verify_linear_equation_solution(...)
solve_simple_equation(...)
```

Their existing return semantics must not change.

### Compatibility plan

The adapter seam should be introduced behind the current public APIs rather than replacing them.

Phase 1 compatibility rule:

```text
existing caller -> existing verifier function -> same result as today
```

New orchestration code may later use:

```text
typed request -> deterministic adapter router -> VerificationResult
```

This allows new code to distinguish:

```text
INCORRECT
```

from:

```text
UNSUPPORTED / INDETERMINATE
```

without changing callers that currently depend on `bool`, `LinearEquationResult`, or `list[str]`.

The first implementation must demonstrate through regression tests that all existing verifier tests still pass unchanged.

### Architectural fit

The adapter seam remains inside the existing modular monolith.

It preserves the current boundary:

```text
Tutor / orchestration
        |
        v
deterministic verifier
        |
        +-- expression-equivalence adapter
        |
        +-- linear-equation adapter
```

No service extraction is justified.

This follows the project rule that deterministic checks should be used where math can be reliably verified and model-generated math must not be silently trusted.

It also creates an explicit future escalation boundary:

```text
CORRECT / INCORRECT
    -> deterministic conclusion

UNSUPPORTED / INDETERMINATE
    -> caller decides whether another verifier,
       stronger reasoning path, or escalation is required
```

The adapter itself must not silently call an LLM.
