# M06-03 — Define Solver Adapter Contract

Status: ACTIVE
Codex: NO
Module: M06 Math Verifier
Phase: Phase 2 — Correctness

## Goal

Define the smallest stable solver-adapter contract for routing deterministic verification by problem family before any new solver implementation is added.

This task is architecture/audit only. It must produce a concrete implementation contract for the next Codex task without changing production behavior.

## Why this task now

Phase 1 is complete and all existing tasks are DONE.

The Phase 2 roadmap starts with:

1. solver adapters by problem family;
2. stronger algebra verification;
3. numeric/unit verification;
4. geometry verification strategy;
5. escalation when analyzer and verifier disagree.

The current verifier already supports at least:
- one-variable linear equation verification;
- expression-equivalence verification.

Before adding more verifier families, we need a small explicit adapter seam so later families do not accumulate inside one monolithic verifier function.

## Micro-task

Audit only the current verifier boundary and define:

- adapter input contract;
- adapter result contract;
- problem-family identifier;
- adapter selection rule;
- unsupported-family behavior;
- how existing linear-equation and expression-equivalence logic map to the adapter seam;
- what the first implementation task should change.

Do not implement the adapters in this task.

## Design constraints

The contract must preserve these product/architecture rules:

- deterministic verification remains separate from LLM generation;
- unsupported/ambiguous cases must not silently pass;
- adapters live inside the existing modular monolith;
- no dependency is added without justification;
- current verifier behavior must remain reproducible;
- future numeric/unit and geometry verifiers should fit the same seam if practical;
- an adapter result must distinguish at least:
  - verified/correct;
  - verified/incorrect;
  - unsupported/not-applicable;
  - verifier error or indeterminate result.

Do not over-generalize for hypothetical future domains.

class ProblemFamily(str, Enum):

    EXPRESSION_EQUIVALENCE = "expression_equivalence"

@dataclass(frozen=True)
class SolverAdapterResult:
