# M06-05 — Define Numeric/Unit Verification Contract

Status: ACTIVE
Codex: NO
Module: M06 Math Verifier
Phase: Phase 2 — Correctness

## Goal

Define the smallest safe numeric/unit verification contract for the initial supported domain before implementing a numeric/unit adapter.

This task is architecture/audit only.

It must answer:

- which numeric answer forms are supported first;
- which unit forms/conversions are supported first;
- how exact values vs tolerances are handled;
- how equivalent units are normalized;
- how unsupported/ambiguous quantities are represented;
- how numeric/unit verification fits the `ProblemFamily` / `VerificationResult` seam introduced by M06-04;
- what the first implementation task should change.

Do not implement numeric/unit verification in this task.

## Why this task now

Phase 2 roadmap order is:

1. solver adapters by problem family;
2. stronger algebra verifier;
3. numeric/unit verifier;
4. geometry verifier strategy;
5. escalation when analyzer/verifier disagree.

M06-04 established the deterministic verifier seam with explicit outcomes:

```text
CORRECT
INCORRECT
UNSUPPORTED
INDETERMINATE
```

The next safe step is to define the numeric/unit domain before writing code so the verifier does not silently accept ambiguous conversions or over-generalize beyond tested school-level cases.

## Design principles

The numeric/unit contract must preserve:

- deterministic verification where feasible;
- explicit unsupported behavior where semantics are ambiguous;
- separation between model generation and verification;
- no silent unit assumptions;
- no mastery update from an unverifiable answer;
- modular-monolith architecture;
- small, testable initial domain.

Do not design a general scientific-units engine.

## Questions the audit must answer

### 1. Numeric answer forms

Determine whether the first implementation should support:

- integers;
- finite decimals;
- rational/fraction forms;
- mathematically equivalent arithmetic expressions;
- signed values.

Document exact support.

Do not automatically include percentages, scientific notation, radicals, intervals, inequalities, vectors, or complex numbers unless current product/evals require them.

### 2. Exact vs approximate comparison

Define when equality is:

- exact;
- rationally equivalent;
- tolerance-based.

If tolerance is allowed, define:

- absolute vs relative tolerance;
- default values;
- whether tolerance must be supplied explicitly by the request;
- whether rounding instructions are part of the contract.

The default should not silently introduce approximate equality unless the product requirement clearly needs it.

### 3. Unit representation

Define a minimal request shape for unit-bearing answers.

The audit must decide whether units are represented as:

- controlled unit codes;
- normalized symbols;
- another explicit typed representation.

Avoid free-form natural-language unit parsing in the first implementation unless existing product contracts already require it.

### 4. Initial supported unit families

Choose only the smallest useful school-level set justified by current product/eval needs.

Candidate families to evaluate, not automatically adopt:

```text
length
mass
time
area
volume
```

For each adopted family, define exact supported units and conversion factors.

Do not mix incompatible dimensions.

Do not add temperature conversion in the first implementation unless there is explicit evidence it is required, because affine conversions have different semantics from scale-only conversions.

### 5. Unit equivalence rules

Define:

- same-unit comparison;
- equivalent-unit conversion;
- dimension mismatch;
- unsupported unit;
- missing unit when one is required;
- extra unit when a dimensionless answer is expected.

Dimension mismatch must never become `INCORRECT` if the request itself is outside the supported contract; decide explicitly whether it is `INCORRECT` or `UNSUPPORTED` based on the request semantics and document the rule.

### 6. Verifier statuses

Map numeric/unit outcomes to the M06-04 result contract:

```text
CORRECT
INCORRECT
UNSUPPORTED
INDETERMINATE
```

At minimum distinguish:

- valid equivalent value/unit;
- valid but wrong value;
- valid value with wrong compatible-unit conversion result;
- incompatible dimension;
- unsupported unit;
- malformed numeric input;
- unexpected internal verifier failure.

### 7. Problem family

Decide whether the first implementation adds one family:

```text
NUMERIC_UNIT
```

or separates:

```text
NUMERIC
NUMERIC_UNIT
```

Prefer the smaller contract unless there is a strong reason to split.

Explain the decision.

### 8. Backward compatibility

M06-05 must define how adding numeric/unit support leaves existing families unchanged:

```text
EXPRESSION_EQUIVALENCE
LINEAR_EQUATION
```

No existing public verifier API may change in the first implementation.
