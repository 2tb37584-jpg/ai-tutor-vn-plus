# M06-05 — Define Numeric/Unit Verification Contract

Status: DONE
Codex: NO
Module: M06 Math Verifier
Phase: Phase 2 — Correctness

## Goal

Define the smallest safe numeric/unit verification contract for the initial supported domain before implementing another deterministic verifier adapter.

This task is architecture/audit only.

The evidence from the current product and eval corpus supports a numeric-only first implementation. Unit verification is explicitly deferred until there is typed unit metadata and real unit eval coverage.

Do not implement numeric or unit verification in this task.

## Why this task now

M06-04 established the deterministic verifier seam with explicit outcomes:

```text
CORRECT
INCORRECT
UNSUPPORTED
INDETERMINATE
```

The next Phase 2 verifier step is numeric/unit correctness.

The audit must avoid building a general unit system without product evidence.

## Evidence reviewed

### Current schema surface

`backend/app/schemas/tutor.py` currently exposes:

```python
class ProblemAnalysis(BaseModel):
    normalized_problem: str
    subject: str = "math"
    grade_band: str = "unknown"
    skills: list[str] = Field(default_factory=list)
    prerequisites: list[str] = Field(default_factory=list)
    expected_answer: str = ""
    verification_notes: str = ""

```

There is no typed verifier metadata for:

```text
problem_family
expected_value
expected_unit
candidate_unit
dimension
tolerance
rounding_rule
```

`StudentProblemAnalysis` intentionally does not expose the internal expected answer.

### Current analyzer surface

`TutorAI.analyze_problem()` asks the model to produce `ProblemAnalysis`.

The analyzer therefore currently provides only a free-form `expected_answer: str` plus `verification_notes: str`.

There is no controlled unit code or typed unit dimension.

A unit verifier must not infer production-grade unit semantics by parsing arbitrary free-form `expected_answer` text.

### Current eval corpus evidence

The current corpus contains:

```text
100 total cases
0 real unit candidates
```

A corrected unit scanner found no unit-bearing problem/expected-answer cases.

The corpus currently contains 8 non-empty verifier fixtures.

All 8 are:

```text
kind = linear_equation
```

There are currently no numeric verifier fixtures and no unit verifier fixtures.

Examples of existing scalar expected answers in the corpus include integers and fractions such as:

```text
4
-2
1/2
0
3/2
-14
```

Therefore the current corpus provides concrete evidence for scalar numeric answers, but no evidence that unit conversion support is required now.

## Audit result

### Current available inputs

For a future deterministic numeric verifier, the repository already has enough information to support an internal typed request containing:

```text
expected numeric answer
candidate numeric answer
explicit numeric problem family
```

The current generic `ProblemAnalysis.expected_answer: str` can represent a scalar expected answer, but it does not itself provide trusted family routing.

The verifier must continue to receive an explicitly classified `ProblemFamily` request. It must not guess the family from the answer string.

For unit verification, the current input surface is insufficient.

Missing typed data includes:

```text
expected unit
candidate unit
unit dimension
conversion family
rounding/tolerance semantics
```

No schema change is made in M06-05.

### Decision: numeric-only first

The first implementation after M06-05 should add one new deterministic family:

```python
ProblemFamily.NUMERIC
```

Do not add `NUMERIC_UNIT` yet.

Reasons:

1. The current corpus contains scalar numeric answers.
2. The current corpus contains zero unit-bearing cases.
3. The current schema has no typed unit metadata.
4. Free-form unit parsing would violate the project's deterministic-verification requirement.
5. Numeric-only verification fits the existing adapter seam without schema expansion.

Unit verification should become a separate future task only when product/eval evidence supplies a typed unit contract.

### Initial supported numeric domain

The first numeric adapter should support scalar numeric literals only.

Supported forms:

```text
integer
signed integer
finite decimal literal
signed finite decimal literal
rational fraction a/b
signed rational fraction
leading/trailing whitespace around the whole literal
```

Examples:

```text
4
-8
+3
0
0.5
-2.75
1/2
-7/3
```

All supported values must represent a finite real rational number.

The first implementation should normalize supported literals to an exact rational representation.

Preferred implementation:

```python
fractions.Fraction
```

with a conservative validator before construction.

This makes base-10 decimals exact for verifier purposes:

```text
0.1 == 1/10
0.5 == 1/2
1.25 == 5/4
```

### Explicitly unsupported numeric forms

The first implementation should return `UNSUPPORTED` for:

```text
scientific notation
percentages
radicals
irrational constants
complex numbers
intervals
inequalities
vectors
mixed-number notation
thousands separators
locale decimal commas
free-form arithmetic expressions
symbolic expressions
unit-bearing strings
NaN / infinity
fraction with denominator zero
```

Examples:

```text
1e-3
25%
sqrt(2)
pi
1+2
x
3 cm
1,5
1/0
```

This is intentionally narrower than the existing algebra parser.

The numeric adapter verifies final scalar answers, not arbitrary calculation expressions.

### Exact vs approximate comparison

The first implementation uses exact comparison only.

There is no default tolerance.

There is no implicit rounding.

There is no relative or absolute epsilon.

Examples:

```text
0.5 and 1/2
    -> exactly equal

0.1 and 1/10
    -> exactly equal

0.333 and 1/3
    -> not equal

3.14 and 3.140
    -> exactly equal
```

If future product requirements need answers such as "round to 2 decimal places" or measurement tolerance, that requires explicit typed tolerance/rounding metadata in a separate task.

The verifier must not silently infer approximation semantics from wording.

### Unit domain decision

Initial supported unit families:

```text
none
```

No length, mass, time, area, or volume conversion is implemented in the first numeric task.

This is a deliberate evidence-based decision, not a permanent rejection of unit verification.

Current evidence:

```text
UNIT_CANDIDATES = 0
```

and the current schema lacks typed unit metadata.

### Unit-bearing input behavior

For the first numeric adapter:

```text
numeric literal with unit text
    -> UNSUPPORTED
```

Examples:

```text
3 cm
2 kg
5 m²
10 phút
```

Dimension mismatch, missing unit, extra unit, and unit conversion are not evaluated as `INCORRECT` because unit semantics are outside the supported request contract.

They remain `UNSUPPORTED` until a dedicated typed unit verifier exists.

### Comparison semantics

For two supported scalar numeric literals:

```text
exact rational values equal
    -> CORRECT

exact rational values differ
    -> INCORRECT
```

For a request outside the declared numeric literal domain:

```text
-> UNSUPPORTED
```

For an unexpected internal/runtime verifier failure:

```text
-> INDETERMINATE
```

`UNSUPPORTED` and `INDETERMINATE` must never be interpreted as correct.

### Problem-family strategy

Add exactly one new family in the first implementation:

```python
class ProblemFamily(str, Enum):
    EXPRESSION_EQUIVALENCE = "expression_equivalence"
    LINEAR_EQUATION = "linear_equation"
    NUMERIC = "numeric"
```

Do not add `NUMERIC_UNIT`.

This keeps the contract aligned with real evidence and avoids implying unit support that does not exist.

### Request contract

Proposed typed request:

```python
@dataclass(frozen=True)
class NumericVerificationRequest:
    family: ProblemFamily
    expected: str
    candidate: str
```

No unit or tolerance fields are added in the first implementation.

The router receives the explicit family and must not classify numeric requests from free-form text.

### Result contract

Reuse the M06-04 result type unchanged:

```python
@dataclass(frozen=True)
class VerificationResult:
    status: VerificationStatus
```

Status mapping:

```text
supported expected + supported candidate + equal exact value
    -> CORRECT

supported expected + supported candidate + different exact value
    -> INCORRECT

malformed expected literal
    -> UNSUPPORTED

malformed candidate literal
    -> UNSUPPORTED

unsupported numeric notation
    -> UNSUPPORTED

unit-bearing input
    -> UNSUPPORTED

non-finite / zero-denominator input
    -> UNSUPPORTED

unexpected internal verifier failure
    -> INDETERMINATE
```

### Routing / integration

M06-04 already provides deterministic routing by `ProblemFamily`.

The next implementation should extend that same router:

```python
if request.family is ProblemFamily.NUMERIC:
    ...
```

There must be:

```text
no fuzzy routing
no LLM family selection
no fallback from NUMERIC to EXPRESSION_EQUIVALENCE
```

A numeric candidate that contains algebra or units must not be silently passed to another adapter.

### Tutor integration boundary

Adding a numeric adapter does not by itself mean TutorAI can automatically route every student answer to it.

The current Tutor schema lacks an explicit deterministic verifier family field.

Therefore:

```text
M06-06
    may add the numeric adapter itself

later integration task
    must decide when Tutor orchestration is allowed to construct
    NumericVerificationRequest
```

Do not expand M06-06 into TutorAI/schema integration.

This preserves a small implementation scope.

### Backward compatibility

The existing deterministic families remain unchanged:

```text
EXPRESSION_EQUIVALENCE
LINEAR_EQUATION
```

No existing public verifier API should change.

The numeric adapter is additive.

Existing tests for:

```python
equivalent(...)
classify_linear_equation(...)
verify_linear_equation_solution(...)
solve_simple_equation(...)
```

must continue to pass.

### Dependency decision

No new dependency is justified.

Python stdlib is sufficient:

```python
fractions.Fraction
re
```

A conservative regex/parser should constrain the accepted literal domain before conversion.

Do not add a units library.

Do not add a scientific-computing dependency.

### Eval/test implications

The first implementation needs focused unit tests even though the current eval corpus has no numeric verifier fixtures.

Minimum numeric test matrix:

```text
4 vs 4
    -> CORRECT

-8 vs -8
    -> CORRECT

1/2 vs 0.5
    -> CORRECT

0.1 vs 1/10
    -> CORRECT

3/2 vs 1.5
    -> CORRECT

3 vs 4
    -> INCORRECT

0.333 vs 1/3
    -> INCORRECT

whitespace-wrapped valid literal
    -> supported

1/0
    -> UNSUPPORTED

x
    -> UNSUPPORTED

1+2
    -> UNSUPPORTED

sqrt(2)
    -> UNSUPPORTED

1e-3
    -> UNSUPPORTED

25%
    -> UNSUPPORTED

3 cm
    -> UNSUPPORTED

NaN / infinity
    -> UNSUPPORTED
```

Router tests must prove:

```text
NUMERIC request -> numeric adapter
mismatched request/family -> UNSUPPORTED
existing expression/linear routing remains unchanged
```

An `INDETERMINATE` test should be added with monkeypatch only if it remains small and does not require production test hooks.

### Eval corpus recommendation

Do not add numeric/unit eval fixtures in the same implementation task merely to increase scope.

After the numeric adapter exists and is integrated into an actual orchestration path, add a separate eval task with explicit numeric verifier fixtures.

Unit fixtures should not be added until a typed unit contract exists.
