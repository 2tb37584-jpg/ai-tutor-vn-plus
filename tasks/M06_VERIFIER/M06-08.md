# M06-08 — Define Analyzer/Verifier Disagreement Escalation Policy

Status: ACTIVE
Codex: NO
Module: M06 Math Verifier
Phase: Phase 2 — Correctness

## Goal

Define the policy for handling disagreement between model/analyzer judgment and deterministic verifier results.

This is architecture/design only. Do not implement escalation in this task.

## Audit result

### Current decision inputs

The deterministic verifier exposes `CORRECT`, `INCORRECT`, `UNSUPPORTED`, and `INDETERMINATE` for explicit problem families. `UNSUPPORTED` means outside the deterministic contract; `INDETERMINATE` means a supported path failed unexpectedly.

`TutorTurn` exposes `likely_correct: bool | None`. Current `TutorAI._with_continued_turn_state()` uses this model field in attempt states: `True -> ATTEMPT_CORRECT`, `False -> ATTEMPT_INCORRECT`, `None -> no correctness transition`. There is no deterministic verifier call in `TutorAI`.

The tutor state machine already has the events needed for supported deterministic outcomes: attempt-state `ATTEMPT_CORRECT` / `ATTEMPT_INCORRECT`, and verify-state `VERIFIED` / `VERIFICATION_FAILED`.

`/tutor/reply` currently records the learner message, calls `TutorAI.continue_turn(...)`, applies the answer-leakage guard, stores the model-produced state, and commits. It does not call `verify(...)` or `record_mastery_evidence(...)`.

The live session stores `normalized_problem`, `primary_skill`, `internal_expected_answer`, and `current_state`, but does not persist a trusted typed deterministic verifier request for every verifier family. This blocks safe generic wiring because `NUMERIC`, `EXPRESSION_EQUIVALENCE`, and `LINEAR_EQUATION` need different trusted inputs.

Current mastery logic is already conservative. Mastery is eligible only when `verification_status == VERIFIED`, outcome is `CORRECT` or `INCORRECT`, and evidence type is `DETERMINISTIC_VERIFICATION` or `VERIFIED_TRANSFER`. `LLM_JUDGMENT`, `CLIENT_CLAIM`, `UNVERIFIED`, `UNSUPPORTED`, and `DISPUTED` do not update mastery. `/tutor/attempt` already returns `mastery_updated=False` for a client claim.

### Important integration risk

There are two unrelated enums named `VerificationStatus`:

- verifier service: `CORRECT`, `INCORRECT`, `UNSUPPORTED`, `INDETERMINATE`
- mastery service: `VERIFIED`, `UNVERIFIED`, `UNSUPPORTED`, `DISPUTED`

They must never be passed through interchangeably. Orchestration must map them explicitly and should use qualified imports or aliases.

### Authority hierarchy

Authority order:

1. supported deterministic verifier result;
2. model/analyzer `likely_correct` as advisory only;
3. student/client self-report as non-authoritative evidence.

For a supported deterministic request, `CORRECT` or `INCORRECT` is authoritative. Model confidence and client claims cannot override it.

For `UNSUPPORTED` or exhausted `INDETERMINATE`, effective correctness remains unknown.

### Authority matrix

| Verifier status | Model likely_correct | Effective correctness | Tutor action | Mastery eligible | Retry? |
| --- | --- | --- | --- | --- | --- |
| CORRECT | True | correct | deterministic correct transition | Yes | No |
| CORRECT | False | correct | deterministic correct transition; record disagreement | Yes | No |
| CORRECT | None | correct | deterministic correct transition | Yes | No |
| INCORRECT | False | incorrect | deterministic incorrect transition | Yes | No |
| INCORRECT | True | incorrect | deterministic incorrect transition; record disagreement | Yes | No |
| INCORRECT | None | incorrect | deterministic incorrect transition | Yes | No |
| UNSUPPORTED | True/False/None | unknown | keep correctness unresolved; Socratic fallback | No | No |
| INDETERMINATE | any, retry_count=0 | unknown | retry deterministic verifier once | No | Yes |
| INDETERMINATE | any, retry_count>=1 | unknown | stop retrying; Socratic fallback | No | No |

### CORRECT policy

`CORRECT` is authoritative regardless of model output. From attempt states use `ATTEMPT_CORRECT`. If deterministic verification is explicitly performed while already in `VERIFY`, `VERIFIED` may be used.

Mastery mapping:

- `MasteryOutcome.CORRECT`
- `MasteryEvidenceType.DETERMINISTIC_VERIFICATION`
- mastery `VerificationStatus.VERIFIED`

Model disagreement is logged but does not trigger retry.

### INCORRECT policy

`INCORRECT` is authoritative regardless of model output. From attempt states use `ATTEMPT_INCORRECT`. If the check is truly the final verification step while already in `VERIFY`, `VERIFICATION_FAILED` may be used.

Mastery mapping:

- `MasteryOutcome.INCORRECT`
- `MasteryEvidenceType.DETERMINISTIC_VERIFICATION`
- mastery `VerificationStatus.VERIFIED`

A model `likely_correct=True` must not approve the attempt.

### UNSUPPORTED policy

`UNSUPPORTED` means the deterministic verifier does not support the request/domain. It does not mean the learner is wrong.

Allowed model behavior: continue Socratic tutoring, ask for reasoning, ask a focused clarification question, suggest a self-check, or continue hints.

Not allowed: convert model confidence into deterministic correctness, mark the answer verified, create mastery-eligible deterministic evidence, or guess another verifier family.

Initial state policy: keep the current tutor state unless another explicit user-driven event applies.

Mastery is not eligible. Retry count is zero.

### INDETERMINATE policy

`INDETERMINATE` is an internal/reliability path.

Allow at most one deterministic retry with the same request, same `ProblemFamily`, and same deterministic verifier. Do not change family, rewrite the request, or use an LLM to construct a replacement deterministic claim.

If retry succeeds, use the resulting `CORRECT` or `INCORRECT`. If retry remains `INDETERMINATE`, stop retrying, keep effective correctness unknown, block mastery, and continue Socratic fallback. Telemetry/error logging is required.

### Retry policy

- `CORRECT`: 0 retries
- `INCORRECT`: 0 retries
- `UNSUPPORTED`: 0 retries
- `INDETERMINATE`: at most 1 deterministic retry

Retry may not change problem family.

### Model fallback policy

The model may continue Socratic dialogue, ask for clarification, ask for reasoning, suggest checking a step, or identify a possible misconception tentatively.

The model may not override `CORRECT` or `INCORRECT`, upgrade `UNSUPPORTED` or exhausted `INDETERMINATE` into a correctness verdict, or create mastery-eligible evidence by itself.

`TutorTurn.likely_correct` may remain available as advisory output, but orchestration must not use it as the effective correctness source when deterministic verification is supported or has failed indeterminately.

### Tutor-state mapping

From `ASK_ATTEMPT`, `HINT_1`, or `HINT_2`:

- verifier `CORRECT` -> `ATTEMPT_CORRECT`
- verifier `INCORRECT` -> `ATTEMPT_INCORRECT`

For `UNSUPPORTED` or exhausted `INDETERMINATE`, emit no correctness transition; keep state stable and use a neutral Socratic fallback.

If deterministic verification is explicitly performed in `VERIFY`:

- `CORRECT` -> `VERIFIED`
- `INCORRECT` -> `VERIFICATION_FAILED`

only when that orchestration context truly represents final verification.

### Mastery policy

- verifier `CORRECT`: eligible as deterministic verified correct evidence
- verifier `INCORRECT`: eligible as deterministic verified incorrect evidence
- verifier `UNSUPPORTED`: not eligible
- verifier `INDETERMINATE`: not eligible
- model-only `likely_correct`: not eligible
- client claim: not eligible

### Telemetry contract

Minimum fields:

- `session_id`
- `skill_code`
- `problem_family`
- `verifier_status`
- `model_likely_correct`
- `disagreement`
- `retry_count`
- `escalation_outcome`
- `mastery_eligible`
- `verification_method`

`disagreement=True` only for `CORRECT + model False` or `INCORRECT + model True`. For `UNSUPPORTED` and `INDETERMINATE`, model output is advisory rather than a true correctness disagreement.

Do not log API keys, `image_data_url`, full transcripts, full prompts, `internal_expected_answer`, or duplicated raw learner content by default.

### Leakage safeguards

Current API flow already uses `_guard_tutor_turn(...)` and `detects_final_answer_leak(...)`. Escalation must preserve this boundary.

A fallback model prompt must not receive `internal_expected_answer` merely because deterministic verification returned `UNSUPPORTED` or `INDETERMINATE`.

Fallback may receive the problem, primary skill, recent tutoring history, newest learner message, current tutor state, and a neutral verification-unavailable instruction. The answer-leakage guard must still run on fallback output.

### Current architectural gap

The live `/tutor/reply` path has no deterministic verification step and no trusted typed verifier request for every family. Therefore policy resolver, typed verifier context, reply wiring, mastery wiring, and telemetry must not be bundled into one implementation task.

### Implementation readiness decision

`NEEDS_SPLIT_TASKS`

Reasons:

1. policy semantics can be implemented independently;
2. live reply flow has no verifier orchestration seam;
3. current session/analysis data does not provide trusted typed verifier inputs for every family;
4. mastery service exists but is not invoked by `/tutor/reply`;
5. one combined implementation would violate the project's small-task rule.

Codex: YES

#### Goal

#### Allowed files

Exactly:

- `backend/app/services/verification_policy.py`
- `backend/tests/test_verification_policy.py`

If another file is required, stop and report.

#### Forbidden scope

Do not modify verifier, TutorAI, tutor state, mastery, schemas, API routes, models, migrations, eval corpus, frontend, dependencies, or task files.

Do not call the verifier, call a model, change tutor state, write mastery, log student content, or guess a `ProblemFamily`.

#### Required behavior

- `CORRECT`: effective correct, mastery eligible, no retry, model cannot override
- `INCORRECT`: effective incorrect, mastery eligible, no retry, model cannot override
- `UNSUPPORTED`: effective unknown, mastery ineligible, no retry, model-assisted-only action
- first `INDETERMINATE`: effective unknown, mastery ineligible, exactly one deterministic retry allowed
- `INDETERMINATE` after one retry: effective unknown, mastery ineligible, no retry, model-assisted-only action
- disagreement is true only for `CORRECT + model False` and `INCORRECT + model True`

#### Acceptance criteria

- [ ] Pure policy module has no DB/API/model dependencies.
- [ ] CORRECT is authoritative over model False.
- [ ] INCORRECT is authoritative over model True.
- [ ] Model None does not change deterministic correctness.
- [ ] UNSUPPORTED produces unknown correctness.
- [ ] UNSUPPORTED is not retryable.
- [ ] UNSUPPORTED is not mastery-eligible.
- [ ] First INDETERMINATE result allows exactly one deterministic retry.
- [ ] INDETERMINATE after one retry is not retryable.
- [ ] INDETERMINATE is never mastery-eligible.
- [ ] Disagreement is recorded only for authoritative deterministic/model conflicts.
- [ ] No student content is accepted or emitted by the resolver.
- [ ] Existing verifier behavior is unchanged.
- [ ] No dependency is added.
- [ ] Unit tests cover the full decision matrix.

#### Tests

At minimum cover:

- CORRECT + True / False / None
- INCORRECT + True / False / None
- UNSUPPORTED + True / False / None
- INDETERMINATE + retry_count 0 / 1 / >1

No live/provider test.
