# M06-08 — Define Analyzer/Verifier Disagreement Escalation Policy

Status: ACTIVE
Codex: NO
Module: M06 Math Verifier
Phase: Phase 2 — Correctness

## Goal

Define the policy for handling disagreement between model/analyzer judgment and deterministic verifier results.

This is architecture/design only.

The task must define:

- which source is authoritative for supported deterministic verification;
- how `CORRECT`, `INCORRECT`, `UNSUPPORTED`, and `INDETERMINATE` affect Tutor Engine behavior;
- when retry/escalation is allowed;
- when model judgment may be used only as advisory evidence;
- when mastery updates are allowed or blocked;
- what telemetry is required;
- what the first implementation task should change.

Do not implement escalation in this task.

## Context

M06-03 through M06-07 established:

- explicit deterministic verifier routing by problem family;
- verifier statuses:
  - `CORRECT`
  - `INCORRECT`
  - `UNSUPPORTED`
  - `INDETERMINATE`
- deterministic families currently include:
  - `EXPRESSION_EQUIVALENCE`
  - `LINEAR_EQUATION`
  - `NUMERIC`
- geometry is deferred because there is no current taxonomy/eval/schema demand;
- unsupported domains must not be mislabeled as deterministic failure;
- model confidence must not silently override deterministic verification.

The next Phase 2 requirement is to define disagreement/escalation behavior before wiring the verifier deeper into tutoring/mastery orchestration.

## Product principles

The policy must preserve:

- Socratic tutoring over direct-answer solving;
- deterministic verification as the source of truth when the request is supported;
- model judgment as probabilistic/advisory unless independently verified;
- no mastery update from unverifiable evidence;
- clear separation between unsupported domain and verifier runtime failure;
- no silent answer leakage during escalation;
- modular-monolith architecture;
- measurable behavior through tests/evals.

## Required policy questions

### 1. Authority hierarchy

Define precedence for:

```text
deterministic verifier result
model/analyzer likely_correct judgment
student self-report
```

For a supported deterministic request, the verifier must not be overridden by model confidence.

### 2. CORRECT behavior

Define what happens when:

```text
verifier = CORRECT
model = likely_correct True
```

and when:

```text
verifier = CORRECT
model = likely_correct False or None
```

Specify:

- Tutor state transition;
- whether the model disagreement is logged;
- whether mastery evidence is eligible;
- whether any retry is needed.

### 3. INCORRECT behavior

Define what happens when:

```text
verifier = INCORRECT
model = likely_correct False
```

and when:

```text
verifier = INCORRECT
model = likely_correct True or None
```

The policy must prevent model approval from overriding deterministic rejection.

### 4. UNSUPPORTED behavior

Define what happens when the verifier cannot support the request/domain.

`UNSUPPORTED` means:

```text
the deterministic verifier does not claim correctness or incorrectness
```

It does not mean the student's answer is wrong.

Specify:

- whether model-assisted tutoring may continue;
- whether model judgment may guide dialogue;
- whether mastery evidence is blocked;
- whether unsupported cases are eligible for later eval/task expansion;
- whether retrying the same deterministic verifier is useful.

### 5. INDETERMINATE behavior

Define what happens when the request belongs to a supported deterministic path but verification fails unexpectedly.

Specify:

- whether one deterministic retry is allowed;
- whether retry must be local/in-process rather than model-based;
- whether model judgment may be shown to the learner;
- whether mastery evidence is blocked;
- whether telemetry/error logging is required;
- when escalation stops.

### 6. Model-assisted fallback

Define the boundary for model-assisted fallback.

The model may potentially:

```text
continue Socratic tutoring
ask for clarification
critique reasoning
suggest a check
```

but must not convert unsupported/indeterminate evidence into deterministic correctness.

### 7. Tutor state interaction

Map disagreement outcomes to existing Tutor Engine events/states where possible.

Current relevant concepts include:

```text
ATTEMPT_CORRECT
ATTEMPT_INCORRECT
VERIFIED
VERIFICATION_FAILED
VERIFY
```

Do not add new states in M06-08.

If the existing state model is insufficient, record that as a follow-up need.

### 8. Mastery evidence policy

Define exactly when an attempt is eligible for mastery update.

At minimum answer:

```text
verifier CORRECT -> eligible?
verifier INCORRECT -> eligible?
verifier UNSUPPORTED -> eligible?
verifier INDETERMINATE -> eligible?
model-only likely_correct -> eligible?
```

The default safety rule should be:

```text
no mastery update from unsupported or indeterminate verification
```

Any exception must be explicitly justified by existing product rules.

### 9. Retry policy

Define:

- which statuses are retryable;
- maximum retry count;
- whether retry is deterministic only;
- whether retry can change problem family;
- what happens after retry exhaustion.

Default expectation:

```text
CORRECT      -> no retry
INCORRECT    -> no retry
UNSUPPORTED  -> no retry
INDETERMINATE -> at most one deterministic retry
```

Do not authorize family guessing on retry.

### 10. Telemetry

Define minimal telemetry fields for disagreement and escalation.

Candidate fields:

```text
session_id
problem_family
verifier_status
model_likely_correct
disagreement
retry_count
escalation_outcome
mastery_eligible
```

Do not include sensitive student content unless required.

Do not log raw API keys, image data, or full private transcripts by default.

### 11. Error vs domain distinction

The policy must preserve:

```text
UNSUPPORTED = outside deterministic contract
INDETERMINATE = supported path failed unexpectedly
```

These must have different telemetry and follow-up behavior.

### 12. Answer-leakage guard

Escalation must not cause the Tutor Engine to reveal the expected answer merely because deterministic verification failed.

Define:

- what information may be passed to a model fallback;
- whether internal `expected_answer` may be included;
- how to keep fallback Socratic.

Default expectation:

```text
do not pass the internal expected answer to a fallback generation prompt
unless a later reviewed task explicitly requires it
```

### 13. Follow-up implementation boundary

Define the smallest implementation task needed after this policy.

Prefer one orchestration seam rather than changing verifier internals.

The task should be 2–6 files.

If API/schema changes are necessary, split them into a separate task.
