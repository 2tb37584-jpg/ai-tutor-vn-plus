# M06-11 — Wire Deterministic Verification Into Tutor Reply

Status: ACTIVE
Codex: YES
Module: M06 Math Verifier
Phase: Phase 2 — Correctness

## Direction gate

Roadmap link: Phase 2 — deterministic verifier integration and analyzer/verifier disagreement handling
Core-loop impact: Student attempt -> deterministic verification -> authoritative tutor progression
Why now: M06-09 provides the decision policy and M06-10 persists trusted verifier routing context.
Why not defer: The live `/tutor/reply` flow still lets model `likely_correct` determine progression even when deterministic verification is available.
Exit criterion affected: >=98% correctness on the supported initial domain.

## Goal

Wire the existing deterministic verifier and M06-09 decision policy into `/tutor/reply` for sessions with a supported persisted `verification_family`.

This task changes tutor progression only.

Do not write mastery and do not add telemetry.

## Current problem

Today:

```text
student reply
-> ai.continue_turn(...)
-> model likely_correct
-> TutorAI changes turn.state
-> API persists that model-derived state
```

For supported deterministic families, the target flow is:

```text
student reply
-> ai.continue_turn(...) for teaching-message generation
-> build typed VerificationRequest from persisted session context
-> verify(...)
-> resolve_verification_decision(...)
-> authoritative state transition
-> leakage guard
-> persist authoritative state
```

Generation remains model-assisted; correctness progression becomes deterministic where supported.

## Supported request construction

Use `payload.student_message` as the candidate.

### NUMERIC

```text
family    = ProblemFamily.NUMERIC
expected  = session.internal_expected_answer
candidate = payload.student_message
```

### EXPRESSION_EQUIVALENCE

```text
family = ProblemFamily.EXPRESSION_EQUIVALENCE
left   = session.internal_expected_answer
right  = payload.student_message
```

### LINEAR_EQUATION

```text
family    = ProblemFamily.LINEAR_EQUATION
equation  = session.normalized_problem
candidate = payload.student_message
```

Use the verifier request type's existing default variable.

Do not parse or rewrite any reference/candidate string.

## Intent boundary

For:

```text
payload.intent == HINT_REQUEST
```

preserve existing behavior.

Do not construct a verification request and do not call `verify(...)`.

This task applies deterministic verification only to normal attempt replies.

## Retry policy

For a supported typed request:

1. call `verify(request)` once;
2. resolve with `retry_count=0`;
3. if the policy action is `RETRY_DETERMINISTIC`, call `verify(request)` exactly one more time using the same request object/data;
4. resolve the second result with `retry_count=1`;
5. never retry again.

Do not change family or rewrite input between retries.

## Authoritative state mapping

When the final decision has:

```text
EffectiveCorrectness.CORRECT
```

map by current state:

```text
ASK_ATTEMPT -> ATTEMPT_CORRECT
HINT_1      -> ATTEMPT_CORRECT
HINT_2      -> ATTEMPT_CORRECT
VERIFY      -> VERIFIED
```

When the final decision has:

```text
EffectiveCorrectness.INCORRECT
```

map by current state:

```text
ASK_ATTEMPT -> ATTEMPT_INCORRECT
HINT_1      -> ATTEMPT_INCORRECT
HINT_2      -> ATTEMPT_INCORRECT
VERIFY      -> VERIFICATION_FAILED
```

Use `transition_tutor_state(...)` for the transition.

Do not jump directly from an attempt state to `TRANSFER`.

For other current states, do not invent a deterministic transition.

## Unknown deterministic outcome

For a supported persisted family, when the final policy decision is `UNKNOWN` because verification is:

```text
UNSUPPORTED
or
INDETERMINATE after the one allowed retry
```

the model must not advance correctness state.

Keep the authoritative state at the original `current_state`.

The model-generated message may remain model-assisted, but state progression must not treat the model judgment as deterministic correctness.

## Sessions without supported persisted family

If `session.verification_family` is `None` or cannot map to the existing `ProblemFamily` enum:

- do not guess a family;
- do not call the verifier;
- preserve existing `/reply` behavior for this task.

Do not broaden M06-11 into unsupported-domain policy redesign.

## TutorTurn consistency

If deterministic policy overrides the state produced by `ai.continue_turn(...)`, return/persist a `TutorTurn` whose:

```text
state
hint_level
```

are consistent with the authoritative state.

Expected hint levels:

```text
HINT_1 -> 1
HINT_2 -> 2
all other states reached by this task -> 0
```

Do not change model message content merely because verifier/model disagree.

Keep `likely_correct` as the model's advisory field in this task.

The deterministic authority is expressed through the persisted/returned tutor state.

Existing final-answer leakage guard must still run after state correction.
