# M06-14 — Define Transfer Verification Eligibility Contract

Status: READY
Codex: NO
Module: Verifier

## Goal

Define which mastery-bearing skills are eligible for deterministic transfer completion under the current verifier architecture, and identify the smallest verifier follow-up work required for currently unsupported skill families.

This is a design/decomposition task only.

Do not modify product code in this task.

The output must resolve the blocker discovered in `M07-06 — Complete Deterministic Transfer-Item Coverage`.

## Context

`M07-06` is BLOCKED because the three mastery-bearing skills missing from the authored question bank use canonical verifier families that are not currently supported by the deterministic verifier contract.

Repository inspection established:

```text
algebra.factorization -> factorization
algebra.rational_expression.domain -> domain_condition
algebra.rational_expression.simplify -> manual_or_future
```

Current deterministic question-bank/verifier families are:

```text
numeric
expression_equivalence
linear_equation
```

Therefore the project must decide whether to:

1. add deterministic verification support for one or more missing families;
2. explicitly exclude some skills from deterministic transfer eligibility;
3. split unsupported/manual skills into a separate future verification path.

Do not coerce canonical verifier families into unrelated existing families merely to satisfy coverage.

## Design questions

Determine and document:

1. Whether `factorization` can be verified deterministically with the current symbolic/algebra primitives.
2. Whether `domain_condition` can be verified deterministically with the current symbolic/algebra primitives.
3. What `manual_or_future` means operationally for transfer eligibility.
4. Whether each of the three skills should be:
   - deterministic-transfer eligible now;
   - eligible after a small verifier implementation task;
   - explicitly ineligible until a later verifier capability exists.
5. Whether adding support requires:
   - a new `ProblemFamily`;
   - a new request dataclass;
   - a new verifier adapter/branch;
   - new parsing/canonicalization logic;
   - or only reuse/composition of existing deterministic logic.
6. Whether any proposed verifier behavior can distinguish:
   - CORRECT;
   - INCORRECT;
   - UNSUPPORTED;
   - INDETERMINATE
   without relying on model confidence.
7. Whether question-bank authored items for those skills can carry a stable verification reference before student evaluation.
8. Whether the skill taxonomy should remain unchanged.
9. The exact definition of `transfer-eligible skill`.
10. Which follow-on tasks are required before `M07-06` can resume.
11. Whether `M05-07` remains blocked after this decision.
12. What deterministic tests are required for each supported family.

## Product constraints

The decision must preserve:

- deterministic verification whenever feasible;
- generation and verification separation;
- explicit/testable tutor progression;
- no model-only correctness judgment for transfer completion;
- canonical skill taxonomy semantics;
- modular monolith architecture;
- no new dependency without demonstrated need.

Do not weaken a skill's canonical verifier meaning merely to make transfer completion easier.

## Preferred decision principle

Use the narrowest safe transfer-eligibility contract.

A mastery-bearing skill is deterministic-transfer eligible only when:

```text
an authored transfer item can provide a verification reference
AND
the application can evaluate the student's response independently of the model
AND
the verifier can return an explicit deterministic status
```

A skill may remain mastery-bearing while being temporarily ineligible for deterministic transfer.

Mastery-bearing status and transfer eligibility are not required to be identical concepts.

## Required analysis by family

### factorization

Determine whether deterministic equivalence between a student's factored expression and a canonical algebraic reference can be supported safely.

At minimum answer:

- can the current expression-equivalence machinery prove algebraic equivalence?
- how will the verifier distinguish a genuinely factored form from an equivalent expanded form, if product form matters pedagogically?
- is algebraic equivalence alone sufficient for this skill's observable mastery evidence?
- what parser/canonicalization constraints apply?
- what should return UNSUPPORTED vs INCORRECT?

Do not assume expression equivalence is sufficient without checking the skill semantics.

### domain_condition

Determine whether a student's stated domain restriction can be checked deterministically.

At minimum answer:

- what representation should the verification reference use?
- can the current parser represent excluded values/conditions?
- does correctness mean set equality of excluded values/domain constraints?
- what answer forms should be accepted?
- what should return UNSUPPORTED vs INCORRECT?
- does this require a genuinely new verifier family?

Do not reduce domain reasoning to numeric verification.

### manual_or_future

Determine the intended operational meaning of this taxonomy value.

At minimum decide whether:

```text
manual_or_future
```

means:

- explicitly not deterministically verifiable today;
- eligible only after future verifier work;
- or a taxonomy placeholder that should be redesigned in a separate task.

Do not silently remap it to an existing verifier family.

## Transfer eligibility contract

The final decision must define a pure eligibility rule conceptually equivalent to:

```text
is_deterministic_transfer_eligible(skill_code) -> bool
```

This task does not implement that function.

Document:

- which current mastery-bearing skills are eligible;
- which are not eligible;
- why;
- what capability would make each excluded skill eligible later.

The rule must not depend on LLM output or runtime randomness.

## Taxonomy decision

Prefer leaving the canonical taxonomy unchanged unless repository evidence shows the existing family labels are incorrect.

If taxonomy changes would be required, STOP and split that into a separate design task.

Do not edit taxonomy in M06-14.

## Question-bank impact

Explicitly state what `M07-06` should enforce after this task.

Two valid examples of possible outcomes are:

```text
A. every mastery-bearing skill must have a transfer item
```

only if deterministic verifier support exists for all of them;

or:

```text
B. every deterministic-transfer-eligible mastery-bearing skill must have a transfer item
```

if some mastery-bearing skills intentionally remain unsupported.

The final decision must choose one.

Do not implement the invariant here.

## Follow-on implementation decomposition

If deterministic verifier support is feasible, keep each implementation task small.

Preferred decomposition:

```text
one verifier family/capability per task
2–6 files per task
schema/request contract + verifier logic + focused tests
```

Do not combine factorization and domain-condition implementation unless they genuinely share one existing primitive and the total scope remains small.

If a family needs new parsing semantics, separate parser/contract design from implementation when necessary.

## Required tests for any future verifier implementation

Tests must distinguish at minimum:

```text
canonical correct form
equivalent alternate correct form
clearly incorrect form
unsupported syntax
indeterminate/parser failure
malformed request/family mismatch
```

For factorization, also test whether pedagogically invalid expanded-only answers are accepted or rejected according to the reviewed skill contract.

For domain conditions, test equivalent representations of the same excluded-value/domain set if the chosen contract supports them.

No live model calls.
