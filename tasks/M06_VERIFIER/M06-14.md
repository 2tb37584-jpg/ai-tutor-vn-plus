# M06-14 — Define Transfer Verification Eligibility Contract

Status: DONE
Codex: NO
Module: Verifier

## Goal

Define which mastery-bearing skills are eligible for deterministic transfer completion under the current verifier architecture, and identify the smallest verifier follow-up work required for currently unsupported skill families.

This is a design/decomposition task only.

Do not modify product code in this task.

The output must resolve the blocker discovered in `M07-06 — Complete Deterministic Transfer-Item Coverage`.

## Context

`M07-06` is BLOCKED because the three mastery-bearing skills missing from the authored question bank use canonical verifier families that are not currently supported by the deterministic verifier contract.

Repository inspection established:

```text
algebra.factorization -> factorization
algebra.rational_expression.domain -> domain_condition
algebra.rational_expression.simplify -> manual_or_future
```

Current deterministic question-bank/verifier families are:

```text
numeric
expression_equivalence
linear_equation
```

Therefore the project must decide whether to:

1. add deterministic verification support for one or more missing families;
2. explicitly exclude some skills from deterministic transfer eligibility;
3. split unsupported/manual skills into a separate future verification path.

Do not coerce canonical verifier families into unrelated existing families merely to satisfy coverage.

## Design questions

Determine and document:

1. Whether `factorization` can be verified deterministically with the current symbolic/algebra primitives.
2. Whether `domain_condition` can be verified deterministically with the current symbolic/algebra primitives.
3. What `manual_or_future` means operationally for transfer eligibility.
4. Whether each of the three skills should be:
   - deterministic-transfer eligible now;
   - eligible after a small verifier implementation task;
   - explicitly ineligible until a later verifier capability exists.
5. Whether adding support requires:
   - a new `ProblemFamily`;
   - a new request dataclass;
   - a new verifier adapter/branch;
   - new parsing/canonicalization logic;
   - or only reuse/composition of existing deterministic logic.
6. Whether any proposed verifier behavior can distinguish:
   - CORRECT;
   - INCORRECT;
   - UNSUPPORTED;
   - INDETERMINATE
   without relying on model confidence.
7. Whether question-bank authored items for those skills can carry a stable verification reference before student evaluation.
8. Whether the skill taxonomy should remain unchanged.
9. The exact definition of `transfer-eligible skill`.
10. Which follow-on tasks are required before `M07-06` can resume.
11. Whether `M05-07` remains blocked after this decision.
12. What deterministic tests are required for each supported family.

## Product constraints

The decision must preserve:

- deterministic verification whenever feasible;
- generation and verification separation;
- explicit/testable tutor progression;
- no model-only correctness judgment for transfer completion;
- canonical skill taxonomy semantics;
- modular monolith architecture;
- no new dependency without demonstrated need.

Do not weaken a skill's canonical verifier meaning merely to make transfer completion easier.

## Preferred decision principle

Use the narrowest safe transfer-eligibility contract.

A mastery-bearing skill is deterministic-transfer eligible only when:

```text
an authored transfer item can provide a verification reference
AND
the application can evaluate the student's response independently of the model
AND
the verifier can return an explicit deterministic status
```

A skill may remain mastery-bearing while being temporarily ineligible for deterministic transfer.

Mastery-bearing status and transfer eligibility are not required to be identical concepts.

## Transfer verification eligibility decision

### Current verifier capability

The current deterministic verifier supports exactly:

```text
numeric
expression_equivalence
linear_equation
```

Current mastery-bearing taxonomy mapping:

```text
arithmetic.signed_number_operations        -> numeric
algebra.expression.distributive_property   -> expression_equivalence
algebra.expression.combine_like_terms      -> expression_equivalence
algebra.expression.simplify                -> expression_equivalence
algebra.equation.equivalent_transform      -> linear_equation
algebra.linear_equation                    -> linear_equation
algebra.identity.basic                     -> expression_equivalence
algebra.factorization                      -> factorization
algebra.rational_expression.domain         -> domain_condition
algebra.rational_expression.simplify       -> manual_or_future
```

The verifier already distinguishes `CORRECT`, `INCORRECT`, `UNSUPPORTED`, and `INDETERMINATE`.

Model confidence and `TutorTurn.likely_correct` are not verification evidence and must never upgrade `UNSUPPORTED` or `INDETERMINATE` to `CORRECT`.

The existing expression machinery can parse finite school-algebra polynomial expressions over `x`, `y`, and `z` and prove algebraic equivalence. It intentionally rejects variable denominators.

### factorization

Decision:

```text
eligible after a small dedicated deterministic verifier implementation
```

Expression equivalence is useful but insufficient by itself because factorization mastery requires both algebraic equivalence and an actual factored form.

Target request contract:

```text
FactorizationVerificationRequest
family: factorization
reference: original polynomial expression
candidate: learner's proposed factored expression
```

A correct candidate must:

1. parse under the existing safe finite-polynomial rules;
2. be algebraically equivalent to the reference;
3. have a supported nontrivial factored structure rather than merely an expanded additive polynomial.

Examples of intended supported shapes:

```text
(x-1)*(x+1)
2*(x+3)
(x+1)^2
```

Status semantics:

```text
CORRECT
    supported + equivalent + accepted factored structure

INCORRECT
    supported but non-equivalent
    OR equivalent but not in accepted factored form

UNSUPPORTED
    syntax/symbols/denominator/power/domain outside factorization v1

INDETERMINATE
    unexpected internal parser/symbolic failure
```

Expected follow-up additions:

```text
ProblemFamily.FACTORIZATION
FactorizationVerificationRequest
factorization verifier branch
focused tests
```

No new external dependency is required.

### domain_condition

Decision:

```text
eligible after a separate small deterministic verifier implementation
```

This skill requires checking excluded domain values and must not be reduced to numeric verification or ordinary expression equivalence.

Target request shape:

```text
DomainConditionVerificationRequest
family: domain_condition
reference: canonical authored excluded-value set
candidate: learner's stated excluded-value/domain condition
variable: x
```

Recommended authored reference convention:

```text
-3,2
```

meaning the excluded set `{x = -3, x = 2}`.

The learner-answer parser should accept only a small documented grammar and normalize equivalent answer forms to an exact excluded-value set.

Conceptual accepted forms may include:

```text
x != -3, x != 2
x ≠ -3; x ≠ 2
```

Correctness is set equality of excluded exact values, not string equality and not model judgment.

Status semantics:

```text
CORRECT
    parsed candidate set equals reference set

INCORRECT
    parsed candidate set differs

UNSUPPORTED
    syntax/variable/set form/domain reasoning outside the narrow v1 contract

INDETERMINATE
    unexpected internal parser/normalization failure
```

Keep v1 limited to exact excluded scalar values arising from supported Grade 8 denominator conditions. Do not build a general symbolic inequality/set solver.

Expected follow-up additions:

```text
ProblemFamily.DOMAIN_CONDITION
DomainConditionVerificationRequest
small parser/normalizer
domain-condition verifier branch
focused tests
```

No new external dependency is required for this narrow v1.

### manual_or_future

Decision:

```text
not deterministic-transfer eligible now
```

`algebra.rational_expression.simplify` requires both valid rational-expression simplification and preservation of the original domain restrictions after cancellation.

The current verifier rejects variable denominators and has no request contract carrying both simplified-form equivalence and preserved domain restrictions.

Therefore `manual_or_future` means operationally:

```text
mastery-bearing
but not deterministically verifiable under the current verifier architecture
and therefore not eligible for deterministic transfer completion
```

Do not remap it to `expression_equivalence`.

A future rational-expression verifier requires a separate design task.

### Transfer eligibility rule

Conceptual rule:

```text
is_deterministic_transfer_eligible(skill_code) -> bool
```

A skill is eligible only when all conditions hold:

```text
1. the skill is mastery-bearing;
2. its canonical verifier family is implemented deterministically;
3. an authored transfer item can provide a stable verification reference before the learner answers;
4. the learner response can be classified without model judgment;
5. runtime can reconstruct the exact transfer verification contract across requests.
```

Mastery-bearing status and transfer eligibility are distinct concepts.

Eligible now:

```text
arithmetic.signed_number_operations
algebra.expression.distributive_property
algebra.expression.combine_like_terms
algebra.expression.simplify
algebra.equation.equivalent_transform
algebra.linear_equation
algebra.identity.basic
```

Eligible after dedicated verifier work:

```text
algebra.factorization
algebra.rational_expression.domain
```

Not eligible now:

```text
algebra.rational_expression.simplify
```

The rule must not depend on LLM output or randomness.

### Taxonomy impact

Decision:

```text
no taxonomy change
```

The current labels are semantically meaningful:

- `factorization` means output form matters in addition to equivalence;
- `domain_condition` means excluded-domain reasoning;
- `manual_or_future` explicitly marks missing deterministic support.

Do not coerce these labels into existing families.

### Question-bank invariant

M07-06 must no longer enforce:

```text
every mastery-bearing skill has a transfer item
```

The correct invariant is:

```text
every deterministic-transfer-eligible mastery-bearing skill
has at least one authored transfer item
whose verification family matches the canonical skill definition
and whose authored verification reference self-validates
```

Operationally:

- the 7 currently supported-family mastery skills are eligible now;
- `algebra.factorization` joins after factorization verifier support;
- `algebra.rational_expression.domain` joins after domain-condition verifier support;
- `algebra.rational_expression.simplify` remains outside while its family is `manual_or_future`;
- `general.problem_solving` remains outside because it is not mastery-bearing.

M07-06 should remain BLOCKED until the intended new deterministic families exist and the invariant is updated to target transfer-eligible mastery skills.

### Risks

- Algebraic equivalence alone would accept expanded answers that do not demonstrate factorization.
- Overly permissive structural checks could reward superficial multiplication syntax.
- An overly broad domain parser would turn a small Grade 8 verifier into a general symbolic-set parser.
- String equality for domain answers would reject mathematically equivalent forms.
- Coercing `manual_or_future` into expression equivalence would lose the preserved-domain requirement.
- Treating all mastery-bearing skills as transfer-eligible would recreate the M07-06 blocker.
- Duplicating transfer eligibility across modules would create policy drift.
- Expanding rational-expression verification in this chain would exceed the intended scope.
