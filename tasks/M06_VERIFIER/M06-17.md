The v1 contract must compare exact excluded scalar values deterministically and must not become a general symbolic set or inequality solver.

## Required verifier contract

Add:

```text
ProblemFamily.DOMAIN_CONDITION = "domain_condition"
```

Add a frozen request dataclass conceptually equivalent to:

```python
@dataclass(frozen=True)
class DomainConditionVerificationRequest:
    family: ProblemFamily
    reference: str
    candidate: str
    variable: str = "x"
```

Include it in `VerificationRequest`.

Route it through `verify()` only when:

```text
request.family is ProblemFamily.DOMAIN_CONDITION
AND
request is DomainConditionVerificationRequest
```

Mismatched request/family must return:

```text
VerificationStatus.UNSUPPORTED
```

## Reference contract

The authored/reference side must use a stable narrow machine-readable representation of exact excluded scalar values.

Use comma-separated exact values, for example:

```text
-3,2
```

meaning:

```text
{x = -3, x = 2}
```

The reference parser must:

- trim whitespace;
- accept exact integers;
- accept exact rational literals such as `1/2`;
- normalize duplicates away;
- compare as a mathematical set, not by order;
- reject malformed or unsupported reference syntax as `UNSUPPORTED`.

Do not accept free-form prose on the reference side.

## Candidate v1 grammar

Support a deliberately small learner-answer grammar for one variable.

At minimum accept exact exclusion clauses using:

```text
x != 2
x ≠ 2
x != -3, x != 2
x ≠ -3; x ≠ 2
```

Whitespace variations should be tolerated.

Order must not matter.

Duplicate clauses should normalize away.

The candidate values may be:

```text
integer
exact rational literal
```

Examples:

```text
x != 2
x != -3, x != 2
x != 1/2
```

Do not support in v1:

```text
interval notation
set-builder notation
inequalities such as x > 2
compound boolean expressions
multiple variables
decimal approximations
symbolic roots
free-form Vietnamese prose
```

Those should be `UNSUPPORTED`, not guessed.

## Variable contract

The request variable defaults to:

```text
x
```

For v1, support only variables already in the verifier's supported symbol set:

```text
x
y
z
```

Candidate clauses must use exactly the request variable.

A candidate using a different variable is:

```text
UNSUPPORTED
```

## Correctness semantics

Normalize both sides to exact excluded-value sets.

Return:

```text
CORRECT
```

when candidate and reference sets are exactly equal.

Return:

```text
INCORRECT
```

when candidate syntax is supported and parses successfully, but the normalized excluded-value set differs.

Examples:

```text
reference: -3,2
candidate: x != 2, x != -3
=> CORRECT
```

```text
reference: -3,2
candidate: x != -3
=> INCORRECT
```

```text
reference: -3,2
candidate: x != -3, x != 2, x != 5
=> INCORRECT
```

```text
reference: -3,2
candidate: x != 3, x != 2
=> INCORRECT
```

## Unsupported semantics

Return:

```text
UNSUPPORTED
```

for expected validation/domain rejection such as:

- malformed reference;
- unsupported candidate grammar;
- unsupported variable;
- candidate variable mismatch;
- decimal approximations;
- interval notation;
- set-builder notation;
- symbolic values;
- unsafe characters;
- empty candidate;
- empty or malformed exclusion clause.

Do not interpret unsupported text with heuristics or an LLM.

## Indeterminate semantics

Unexpected internal parsing/normalization/runtime failure must return:

```text
INDETERMINATE
```

Do not collapse unexpected failures into `INCORRECT` or `UNSUPPORTED`.

## Exact numeric normalization

Prefer reusing the existing exact numeric literal parser already used by the numeric verifier if it can be reused without changing its public semantics.

Exact equality should be based on normalized exact values, e.g. `Fraction`, not floats.

Therefore:

```text
1/2
2/4
```

should normalize to the same excluded value if both are accepted by the existing exact numeric parser.

Do not add decimal tolerance logic.
