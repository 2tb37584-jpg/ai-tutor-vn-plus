# M06-07 — Define Geometry Verifier Strategy

Status: READY
Codex: NO
Module: M06 Math Verifier
Phase: Phase 2 — Correctness

## Goal

Define the verification strategy for geometry problems before any geometry verifier implementation is attempted.

This is an architecture/audit task only.

The task must determine:

- which geometry problem families are deterministic enough to verify safely;
- which inputs must be typed rather than inferred from free-form text;
- where existing numeric/algebra verifier components can be reused;
- which geometry tasks must remain `UNSUPPORTED`;
- which geometry tasks may require model-assisted reasoning but must not be treated as deterministically verified;
- what prerequisites must exist before a geometry implementation task is allowed.

Do not implement geometry verification in this task.

## Why this task now

Phase 2 roadmap order is:

1. solver adapters by problem family;
2. stronger algebra verifier;
3. numeric/unit verifier;
4. geometry verifier strategy;
5. escalation when analyzer/verifier disagree.

M06-03 through M06-06 established:

- deterministic verifier routing by explicit problem family;
- explicit statuses:
  - `CORRECT`
  - `INCORRECT`
  - `UNSUPPORTED`
  - `INDETERMINATE`
- exact scalar numeric verification;
- no fuzzy/LLM routing inside the deterministic verifier;
- no unit support without typed unit metadata.

The next safe step is to define the geometry boundary before adding any geometry code.

## Product constraint

The current product/eval focus is Grade 8 algebra.

Do not add geometry implementation merely because the model can answer geometry questions.

The project rule remains:

> Add a new subject/domain only when taxonomy, evals, and a verification strategy exist for it.

M06-07 supplies only the verification-strategy part.

It does not authorize geometry rollout.

## Strategy questions

### 1. Current geometry evidence

Determine:

- number of geometry skills in the controlled skill registry;
- number of geometry eval cases;
- whether any existing verifier fixture already represents geometry;
- whether current schemas contain typed geometry fields.

Do not infer geometry support from generic `expected_answer: str`.

### 2. Geometry subfamily classification

Evaluate at least these candidate subfamilies:

```text
A. direct numeric geometry
B. algebraic geometry
C. coordinate geometry
D. diagram-dependent geometry
E. proof / reasoning geometry
```

For each, decide one of:

```text
DETERMINISTIC_CANDIDATE
MODEL_ASSISTED_ONLY
UNSUPPORTED_FOR_NOW
```

Do not implement any of them in M06-07.

### 3. Direct numeric geometry

Examples:

```text
perimeter from explicit side lengths
area from explicit dimensions
angle arithmetic from explicit numeric relations
```

Determine whether these could reuse the exact numeric verifier once the expected numeric target is typed.

Do not assume units are supported.

### 4. Algebraic geometry

Examples:

```text
solve x from perimeter expression
solve x from angle-sum equation
```

Determine whether these should reuse:

```text
LINEAR_EQUATION
EXPRESSION_EQUIVALENCE
NUMERIC
```

rather than adding geometry-specific math logic.

Prefer composition of existing verifier families where the geometry semantics have already been reduced to typed algebra.

### 5. Coordinate geometry

Evaluate separately:

```text
distance
midpoint
slope
simple coordinate substitution
```

Determine whether these are safe deterministic candidates if typed coordinates are available.

Do not authorize free-form coordinate extraction in the verifier.

### 6. Diagram-dependent geometry

Examples:

```text
read a length from an image
infer parallel/perpendicular marks
infer equal-angle marks
infer hidden labels or incidence from a diagram
```

These must not be treated as deterministic unless the diagram has already been converted into a trusted typed representation.

Define the boundary clearly.

### 7. Proof / reasoning geometry

Examples:

```text
prove two triangles congruent
prove two lines parallel
justify an angle equality
multi-step Euclidean proof
```

Determine whether current deterministic infrastructure can verify these.

Default expectation:

```text
not deterministically verified in the initial domain
```

If model-assisted critique is proposed, it must remain separate from deterministic `CORRECT`.

### 8. Typed request contracts

For every geometry subfamily considered a deterministic candidate, define the minimum typed request shape.

Possible examples:

```python
@dataclass(frozen=True)
class CoordinateDistanceRequest:
    family: ProblemFamily
    x1: str
    y1: str
    x2: str
    y2: str
    candidate: str
```

or:

```python
@dataclass(frozen=True)
class GeometryNumericRequest:
    family: ProblemFamily
    expected: str
    candidate: str
```

Do not copy examples blindly.

Prefer reusing existing `NumericVerificationRequest` after upstream geometry semantics have been reduced to a numeric target.

### 9. Problem-family strategy

Decide whether geometry needs:

```text
one broad GEOMETRY family
```

or several explicit families such as:

```text
COORDINATE_DISTANCE
COORDINATE_MIDPOINT
GEOMETRY_ANGLE_SUM
```

Avoid a broad family if it would require fuzzy routing inside the verifier.

### 10. Status semantics

Map geometry outcomes to:

```text
CORRECT
INCORRECT
UNSUPPORTED
INDETERMINATE
```

At minimum distinguish:

- supported deterministic candidate with correct result;
- supported deterministic candidate with wrong result;
- unsupported geometry subfamily;
- missing required typed geometry input;
- diagram-dependent ambiguity;
- proof/reasoning-only task;
- unexpected internal verifier failure.

### 11. Integration boundary

Define what belongs to:

```text
analyzer/orchestrator
```

versus:

```text
deterministic verifier
```

The verifier must not:

- interpret a diagram;
- guess geometry relationships;
- classify free-form geometry text;
- infer hidden givens.

The analyzer/orchestrator may eventually produce typed geometry facts, but those facts require their own confidence and validation policy.

### 12. Escalation interaction

M06-07 should note how future geometry verification interacts with the next roadmap item:

```text
escalate model when analyzer/verifier disagree
```

Do not implement escalation here.

Record which geometry situations should produce:

```text
UNSUPPORTED
```

versus:

```text
INDETERMINATE
```

so future escalation can distinguish unsupported domain from internal failure.
