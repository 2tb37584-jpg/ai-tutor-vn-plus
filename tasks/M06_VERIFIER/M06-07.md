# M06-07 — Define Geometry Verifier Strategy

Status: ACTIVE
Codex: NO
Module: M06 Math Verifier
Phase: Phase 2 — Correctness

## Goal

Define the verification strategy for geometry problems before any geometry verifier implementation is attempted.

This is an architecture/audit task only.

## Context

M06-03 through M06-06 established:

- deterministic verifier routing by explicit problem family;
- explicit statuses:
  - `CORRECT`
  - `INCORRECT`
  - `UNSUPPORTED`
  - `INDETERMINATE`
- exact scalar numeric verification;
- no fuzzy/LLM routing inside the deterministic verifier;
- no unit support without typed unit metadata.

Phase 2 roadmap next asks for a geometry verifier strategy.

The current product focus remains Grade 8 algebra.

### Deterministic candidates

The following geometry cases are theoretically safe only after upstream logic has already converted geometry semantics into typed deterministic inputs.

#### Direct numeric geometry

Examples:

```text
perimeter from explicitly provided side lengths
area from explicitly provided dimensions
angle arithmetic from explicit numeric relations
```

Strategy:

```text
geometry analyzer/orchestrator
    -> trusted typed target
    -> NumericVerificationRequest
    -> NUMERIC verifier
```

Do not add a geometry-specific numeric comparison engine.

The current numeric verifier is sufficient once the expected scalar target is trusted.

Units are still unsupported unless a separate typed unit contract is introduced later.

#### Algebraic geometry

Examples:

```text
solve x from an explicit perimeter equation
solve x from an explicit angle-sum equation
check an algebraic transformation derived from geometry
```

Strategy:

```text
geometry analyzer/orchestrator
    -> trusted algebraic representation
    -> existing deterministic verifier family
```

Reuse:

```text
LINEAR_EQUATION
EXPRESSION_EQUIVALENCE
NUMERIC
```

Do not duplicate algebra-solving logic inside a geometry verifier.

#### Coordinate geometry

Potential later deterministic subfamilies include:

```text
distance
midpoint
slope
simple coordinate substitution
```

These are deterministic only if coordinates and requested operation are already typed.

Example future typed request:

```python
@dataclass(frozen=True)
class CoordinateDistanceRequest:
    family: ProblemFamily
    x1: str
    y1: str
    x2: str
    y2: str
    candidate: str
```

However, M06-07 does not recommend implementing this now because there is no current taxonomy/eval/schema evidence.

### Unsupported initial cases

The deterministic verifier must not claim correctness for:

```text
reading lengths directly from an image
inferring parallel marks from a diagram
inferring perpendicular marks
inferring equal-angle marks
guessing unlabeled geometry relationships
determining incidence from ambiguous diagrams
multi-step Euclidean proofs
triangle-congruence proof checking
parallel-line proof checking
free-form geometric justification
```

These remain outside deterministic verification until there is a trusted structured representation and dedicated eval coverage.

### Diagram-dependent boundary

The deterministic verifier must never:

```text
interpret pixels
run OCR
guess diagram labels
infer hidden givens
infer visual relationships
decide whether lines "look" parallel
decide whether an angle "looks" equal
```

If a future analyzer converts a diagram into typed facts, those facts must have their own validation/confidence policy before deterministic verification is invoked.

A model-generated geometry fact is not automatically trusted merely because it is structured.

### Proof / reasoning boundary

Proof-style geometry is not deterministically verified in the current system.

A future model may:

```text
critique proof steps
suggest missing justification
identify likely invalid reasoning
```

but model-assisted critique must not be mapped directly to:

```text
VerificationStatus.CORRECT
```

without a dedicated proof verifier and eval-backed rules.

### Typed contract needs

No new geometry request type is justified now.

If geometry is later introduced, deterministic subfamilies must use explicit typed requests.

Preferred strategy:

```text
reuse existing requests after upstream reduction
```

where possible.

Examples:

```python
NumericVerificationRequest(
    family=ProblemFamily.NUMERIC,
    expected="12",
    candidate="12",
)
```

or:

```python
LinearEquationRequest(
    family=ProblemFamily.LINEAR_EQUATION,
    equation="2*x+30=180",
    candidate="75",
)
```

A broad request such as:

```python
GeometryRequest(problem_text: str, candidate: str)
```

is explicitly rejected because it would force fuzzy classification and semantic interpretation inside the verifier.

### Problem-family strategy

Do not add a broad:

```text
GEOMETRY
```

family.

A broad geometry family would mix:

```text
numeric
algebraic
coordinate
diagram-dependent
proof
```

semantics and would require fuzzy routing inside the verifier.

If future geometry-specific deterministic operations are introduced, use narrow explicit families only when existing verifier families cannot represent them safely.

Examples that might eventually justify narrow families:

```text
COORDINATE_DISTANCE
COORDINATE_MIDPOINT
COORDINATE_SLOPE
```

but only after taxonomy/eval/product demand exists.

### Reuse strategy

Geometry should compose existing deterministic primitives rather than duplicate them.

Use:

```text
NUMERIC
```

for trusted scalar expected values.

Use:

```text
LINEAR_EQUATION
```

for trusted one-variable linear equations arising from geometry.

Use:

```text
EXPRESSION_EQUIVALENCE
```

for trusted algebraic equivalence arising from geometry.

Do not create geometry-specific copies of these algorithms.

### Status mapping

Future geometry orchestration should use the existing status semantics consistently.

#### CORRECT

Return only when:

```text
the geometry semantics have already been reduced to a supported typed deterministic request
and the deterministic verifier confirms the candidate
```

#### INCORRECT

Return only when:

```text
the typed deterministic request is valid and supported
but the candidate is mathematically wrong
```

#### UNSUPPORTED

Use when:

```text
geometry subfamily is not supported
required typed geometry facts are missing
diagram interpretation would be required
proof/reasoning verification would be required
unit semantics are required but not typed/supported
current request cannot be reduced to an existing deterministic family
```

#### INDETERMINATE

Use only when:

```text
the request belongs to a supported deterministic path
but an unexpected internal/runtime verifier failure prevents a reliable result
```

Do not use `INDETERMINATE` merely because geometry is outside the supported domain.

Unsupported domain and internal failure must remain distinguishable.

### Analyzer/orchestrator vs verifier boundary

#### Analyzer/orchestrator responsibility

Potential future responsibilities:

```text
classify geometry subfamily
extract typed givens
interpret explicit natural-language relationships
convert geometry semantics into algebra/numeric form
track confidence and ambiguity
decide whether deterministic verification is allowed
```

#### Deterministic verifier responsibility

Only:

```text
validate a supported typed mathematical request
```

The verifier must not:

```text
read the original geometry problem
interpret a diagram
infer shape relationships
guess missing givens
classify free-form geometry text
```

### Dependency decision

No new dependency is justified.

For the currently identified deterministic candidates:

```text
NUMERIC
LINEAR_EQUATION
EXPRESSION_EQUIVALENCE
```

already provide the necessary mathematical verification once the problem has been reduced to trusted typed inputs.

Coordinate geometry formulas could later be implemented with stdlib/SymPy if needed.

Do not add a geometry library.

Do not add computer-vision dependencies.

### Escalation interaction

The next Phase 2 roadmap item is disagreement/escalation between analyzer and deterministic verifier.

Geometry makes the distinction especially important.

Examples:

```text
analyzer says a diagram implies two lines are parallel
but no trusted typed fact exists
    -> UNSUPPORTED, not deterministic CORRECT

analyzer produces a typed linear equation
and deterministic verifier rejects the student's candidate
    -> deterministic verifier result remains authoritative for that typed equation

supported verifier path throws unexpected internal error
    -> INDETERMINATE and eligible for escalation/retry policy

geometry task requires proof or diagram interpretation
    -> UNSUPPORTED and may be routed to model-assisted tutoring,
       but not labeled deterministically verified
```

M06-07 does not implement escalation.

### First follow-up task

Do not create a geometry implementation task.

The next Phase 2 task should be:

```text
M06-08 — Define Analyzer/Verifier Disagreement Escalation Policy
```

This should be architecture/design first, `Codex: NO`.

It should define:

- when deterministic verifier results override model judgment;
- when `UNSUPPORTED` permits model-assisted handling;
- when `INDETERMINATE` triggers retry/escalation;
- how disagreement affects mastery evidence;
- how to prevent model confidence from overriding deterministic failure;
- what logs/telemetry are needed;
- what the first implementation task should be.

Geometry implementation should remain deferred until all of these exist:

```text
controlled geometry taxonomy
geometry eval corpus
typed geometry analysis contract
explicit supported deterministic subfamily
tests for that subfamily
```
