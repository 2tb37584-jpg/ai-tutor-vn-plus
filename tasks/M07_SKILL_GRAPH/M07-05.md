# M07-05 — Add Authored Difficulty Levels to Question Bank v1

Status: ACTIVE
Codex: YES
Module: M07 Skill Graph / Curriculum
Phase: Phase 3 — Adaptive Learning

## Direction gate

Roadmap link: Phase 3 — Difficulty estimates
Core-loop impact: Question bank -> difficulty-aware candidate selection -> future next-best-question recommendation
Why now: Question bank v1 exists and is deterministically verified, but items have no stable difficulty signal for future adaptive selection.
Why not defer: Spaced repetition and next-best-question tasks need a question-level difficulty signal before selection policy can be specified cleanly.
Exit criterion affected: enables controlled adaptive sequencing experiments without pretending current learner telemetry is already a calibrated difficulty model.

## Evidence / design decision

Current repository signals include:

- mastery probability;
- mastery exposures;
- correct streak;
- hint count;
- response latency.

These are learner/session signals, not yet validated question-level difficulty estimates.

There is currently no sufficient per-question attempt history or calibration dataset to estimate empirical item difficulty.

Therefore v1 uses an authored ordinal difficulty level stored with each question.

Do not infer or update difficulty from mastery, hints, latency, or correctness in this task.

Do not implement BKT/IRT or any learned estimator.

## Goal

Add a minimal authored difficulty contract to the existing immutable question bank.

Use integer levels:

```text
1 = foundational
2 = standard
3 = stretch
```

This is a v1 authored estimate, not a calibrated psychometric parameter.

## Micro-task

difficulty

No new service, table, migration, API route, scheduler, or recommendation logic.

## Updated question contract

Each record must contain exactly:

```text
id
skill_code

```

### difficulty

Type:

```text
integer
```

Allowed values:

```text
1
2
3
```

Meaning:

```text
1 = foundational
2 = standard
3 = stretch
```

Rules:

- authored metadata only;
- must not be derived from current student mastery;
- must not be derived from response latency;
- must not be derived from hint count;
- must not mutate at runtime;
- no decimal/continuous score in v1.

## Seed-bank assignment principles

Assign difficulty based on mathematical complexity within the supported v1 domain.

Use simple, explainable heuristics:

### numeric

- level 1: single-step integer signed arithmetic;
- level 2: fraction/decimal or sign-sensitive arithmetic;
- level 3: reserve only for clearly more complex supported numeric items.

### expression_equivalence

- level 1: direct single-operation simplification/distribution;
- level 2: multiple algebraic operations or identity recognition;
- level 3: reserve only for clearly more complex supported transformations.

### linear_equation

- level 1: one-step/simple isolation;
- level 2: multi-step isolation, coefficients, negatives, or parentheses;
- level 3: reserve only for clearly more complex supported equations.

Do not force every family to contain every level.

Do not change question text, answers, verifier references, IDs, skills, or family unless required to fix a pre-existing correctness issue discovered by tests.

## Validation

Extend existing loader validation so:

- records still have exact-field validation;
- all existing string fields remain non-empty strings;
- `difficulty` must be an `int`;
- reject booleans as difficulty values;
- difficulty must be one of `{1, 2, 3}`;
- all existing skill/family/verifier self-validation remains unchanged.

Important Python detail:

```text
bool is a subclass of int
```

so explicitly reject `True` and `False`.
