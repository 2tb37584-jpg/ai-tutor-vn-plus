# M09-02 — Answer-Leakage Regression Suite

Status: ACTIVE
Codex: YES

## Goal

Add a durable answer-leakage regression suite for early tutor turns without redesigning the leakage detector.

The suite must verify both:

1. detector behavior in isolation;
2. composite eval-runner behavior using the detector plus fixture `first_turn_must_not_contain` phrases.

This task is about coverage and release-gate evidence, not new tutor behavior.

## Context

Current runtime already has:

- `backend/app/services/answer_leakage.py`
- deterministic `detects_final_answer_leak(...)`
- runtime guard tests in `test_tutor_api_leakage_guard.py`
- baseline eval runner in `backend/app/services/eval_runner.py`
- canonical eval fixtures in `evals/cases.jsonl`

M09-01 established the composite leakage metric:

- existing deterministic detector;
- plus normalized fixture forbidden phrases.

The detector is intentionally conservative and does not need to understand all mathematically equivalent answer forms by itself.

For example, a fixture may include both:

```text
x != 2
x ≠ 2
```

even when the detector only matches one exact normalized representation.

M09-02 must lock down that combined behavior with tests rather than silently broadening detector semantics.

## Product rule

Early tutor turns must not disclose the final answer.

A regression that exposes the final answer must become a durable eval/test case.

False positives also matter: ordinary instructional use of numbers must not be treated as final-answer leakage solely because the same number appears in the answer.

## Detector regression categories

Expand `backend/tests/test_answer_leakage.py` with focused cases covering at least the following categories.

### 1. Model self-report

Must detect leakage when:

```python
model_reports_reveal is True
```

regardless of otherwise safe-looking tutor text.

### 2. Numeric answer cue

For numeric expected answers, detect direct answer statements such as equivalents of:

```text
đáp án là 4
kết quả là 4
answer is 4
result = 4
```

Use existing detector behavior; do not redesign cue vocabulary in this task.

### 3. Variable assignment

Detect direct assignments such as:

```text
x = 4
x=4
y = -2
```

when the expected answer is the corresponding scalar.

### 4. Unicode/case/whitespace normalization

Lock existing deterministic normalization behavior around:

- case differences;
- Unicode NFKC;
- extra whitespace;
- spaces around `=`.

### 5. Boundary safety

Prevent substring false positives.

Examples:

```text
expected answer: 4
safe text: 40 học sinh
safe text: 4x
```

must not be flagged merely because `"4"` is a substring.

### 6. Instructional-number safety

A tutor may legitimately mention the same number as the final scalar answer inside a hint without directly disclosing it.

Example:

```text
expected answer: 2
safe hint: Hãy thử cộng 2 vào hai vế.
```

This must remain safe under existing detector behavior.

### 7. Signed/decimal scalar cases

Add regression coverage for supported scalar textual forms such as:

```text
-2
2.5
2,5
```

Use expectations consistent with the current implementation.

Do not invent mathematical equivalence between decimal comma and decimal point.

### 8. Non-scalar exact-answer leakage

Lock direct textual leakage for controlled examples such as:

```text
(x-2)(x-3)
x != 2
```

The detector may use exact normalized containment for these non-scalar answers.

Do not expand it to symbolic-equivalence solving.

## Composite eval leakage categories

Expand `backend/tests/test_eval_runner.py` around `score_leakage(...)`.

Cover at least:

1. detector catches direct numeric cue;
2. detector catches variable assignment;
3. detector catches direct non-scalar answer text;
4. fixture forbidden phrase catches a representation the detector alone does not need to understand;
5. Unicode/case/whitespace normalization works for forbidden phrases;
6. safe hint passes when neither mechanism detects leakage;
7. detector self-report causes failure even if text is safe;
8. one matched forbidden phrase is enough to fail;
9. details identify detector vs matched fixture phrase;
10. forbidden phrase matching does not rely on another LLM.

### Required notation-variant regression

Include a composite scorer case where:

```text
expected_answer = "x != 2"
```

but first turn contains:

```text
x ≠ 2
```

and the fixture includes:

```text
"x ≠ 2"
```

The composite eval result must be `fail`.

This locks the intended architecture:

- detector handles deterministic direct patterns;
- fixture phrases cover curated notation/representation variants;
- no new symbolic or LLM judge is introduced.

## Canonical fixture expansion

Update `evals/cases.jsonl` with a small answer-leakage-risk set.

Do not expand to 200 cases.

Add approximately 4–8 new Grade 8 algebra cases, enough to cover important answer shapes not already represented.

Each new case must:

- have a unique stable id;
- use a controlled `expected_skills` code;
- include `expected_answer`;
- include meaningful `first_turn_must_not_contain`;
- set `grade` to `8`;
- set `expected_first_state` to `"ask_attempt"`;
- contain no real student PII;
- avoid unsupported verifier blocks unless the case is a supported linear equation;
- preserve valid JSONL, one object per line.

Prefer coverage diversity over many near-duplicates.

Useful answer-shape coverage includes:

- negative linear solution;
- fractional or decimal linear solution;
- distributive/simplified expression;
- factorization expression;
- rational-domain restriction with a notation variant.

Do not add a verifier block merely to increase coverage.

## Suggested stable case ids

Equivalent ids are acceptable, but keep a clear pattern, for example:

```text
g8-linear-negative-leakage-001
g8-linear-fraction-leakage-001
g8-distributive-leakage-001
g8-factor-sign-leakage-001
g8-rational-domain-notation-leakage-001
```

Do not rename existing ids.

## Fixture correctness

New fixtures themselves must be mathematically coherent enough that:

- problem and expected answer agree;
- expected skill is appropriate;
- forbidden phrases actually represent final-answer disclosures.

Do not depend on live LLM output to validate fixture math.

If uncertain about a case, prefer a simpler supported Grade 8 algebra example.

## Acceptance criteria

M09-02 is complete when:

- detector regression coverage includes cue, assignment, normalization, boundary, safe-number, signed/decimal, and non-scalar cases;
- composite eval leakage coverage distinguishes detector hits from fixture phrase hits;
- `x != 2` vs `x ≠ 2` notation-variant leakage is caught by the composite scorer;
- safe hints remain passing;
- false-positive boundary checks are locked;
- model self-report remains authoritative for leakage detection;
- canonical eval fixture gains a small diverse leakage-risk set;
- no production detector/runner code changes;
- no new dependency;
- no DB/network/external AI in tests;
- existing runtime leakage tests still pass;
- targeted tests pass;
- full backend regression passes.

## Required tests

At minimum, the modified test suite should provide durable assertions for:

1. self-report true => leak;
2. Vietnamese numeric answer cue => leak;
3. English numeric answer cue => leak;
4. scalar assignment => leak;
5. signed scalar assignment => leak;
6. decimal scalar direct answer => leak;
7. decimal-comma scalar direct answer => leak;
8. scalar substring in larger number => safe;
9. scalar adjacent to variable token => safe;
10. instructional use of answer number => safe;
11. NFKC/case/whitespace normalized direct answer => leak;
12. factorization exact answer => leak;
13. rational restriction exact answer => leak;
14. composite score fails on detector hit;
15. composite score fails on forbidden phrase only;
16. composite score catches `x ≠ 2` for expected `x != 2` via fixture phrase;
17. safe composite first turn passes;
18. self-report makes composite score fail;
19. metric details expose which mechanism fired.

Existing tests may satisfy some of these; do not duplicate identical coverage unnecessarily.

## Stop conditions

Stop and report rather than expanding scope if:

- a required regression fails because production detector logic must change;
- eval-runner production code appears to need modification;
- a new symbolic equivalence engine would be needed;
- an LLM judge would be needed;
- TutorAI/runtime guard behavior would need modification;
- Docker/dependencies would need modification;
- fixture expansion starts becoming a broad curriculum dataset task.
