# M09-20 — Build Supported-Domain Verifier Benchmark and Measure Phase 2 Exit Gate

Status: DONE
Codex: YES
Module: M09 Evals
Phase: Phase 2 — Correctness

## Direction gate

Roadmap link: Phase 2 correctness exit gate
Core-loop impact: Deterministic verification -> measured supported-domain correctness
Why now: M09-19 aligned the eval harness with the production typed verifier contract, but the existing 100-case corpus contains only 8 linear verifier fixtures and cannot measure the three-family supported domain.
Why not defer: Adding more verifier logic before measuring current correctness would violate evidence-before-expansion.
Exit criterion affected: >=98% correctness on supported initial domain.

## Goal

Create a dedicated offline verifier benchmark covering the three current production verifier families:

```text
linear_equation
expression_equivalence
numeric
```

Measure the production verifier through the M09-19 eval harness and enforce the Phase 2 exit gate:

```text
overall verifier correctness >= 0.98
```

Do not change verifier implementation in this task.

## Benchmark design

Create a dedicated benchmark separate from the existing 100-case live/tutor corpus:

```text
backend/tests/data/verifier_supported_domain.jsonl
```

Use the canonical verifier fixture schema introduced in M09-19.

Benchmark size:

```text
60 cases total
20 linear_equation
20 expression_equivalence
20 numeric
```

Within each family:

```text
10 expected correct
10 expected incorrect
```

This benchmark measures correctness only on intentionally supported deterministic inputs.

Do not include malformed/out-of-domain examples in the >=98% denominator. Unsupported/indeterminate boundary behavior remains covered by verifier unit tests and M09-19 contract tests.

## Case requirements

Every benchmark line must be a valid EvalCase JSON object accepted by `load_cases(...)`.

Each case must include:

```text
id
problem
expected_skills
expected_answer
first_turn_must_not_contain
grade
expected_first_state
verifier
```

Because the benchmark runs offline and scores only `verifier_correctness`, non-verifier fields may be minimal but must remain semantically valid and deterministic.

Use:

```text
grade = 8
expected_first_state = ask_attempt
```

Do not include real student data.

## Family coverage

### linear_equation — 20 cases

Use one-variable school-algebra equations within the currently supported contract.

Cover a representative mix such as:

```text
integer solutions
negative solutions
zero solution
fractional solutions
variables on both sides
parentheses/distribution
signed coefficients
simple rational coefficients
```

Include 10 correct candidates and 10 incorrect candidates.

Do not use:

```text
nonlinear equations
symbolic denominator equations
multiple variables
no-solution / infinitely-many-solution cases
unsupported syntax
```

Those are outside the supported-domain correctness denominator.

### expression_equivalence — 20 cases

Use finite polynomial school-algebra expressions supported by the current verifier.

Cover a representative mix such as:

```text
collection of like terms
distribution
negative signs
powers
multi-term polynomials
x/y/z supported symbols
constant expressions
```

Include 10 equivalent and 10 non-equivalent candidates.

Do not use equations, unsupported symbols, symbolic denominators, or non-finite expressions.

### numeric — 20 cases

Use exact scalar rational literals supported by the current numeric verifier.

Cover a representative mix such as:

```text
integers
negative integers
zero
terminating decimals
fractions
equivalent fraction/decimal forms
signed fractions
```

Include 10 correct and 10 incorrect candidates.

Do not use units, scientific notation, irrational constants, commas, percentages, or unsupported syntax.

## Expected statuses

All benchmark fixtures must use only:

```text
correct
incorrect
```

Distribution must be exactly:

```text
30 correct
30 incorrect
```

No benchmark case may expect:

```text
unsupported
indeterminate
```

```text

```

```python
run_cases(cases, mode="offline")
```

Use the resulting `verifier_correctness` metric.

Assert:

```text

```

Also compute and expose per-family measurement for diagnostics.

Per-family rates are diagnostic only in this task; do not invent a new roadmap pass threshold for each family.

The test output should print one concise deterministic line when run with `pytest -s`, for example:

```text

```

Do not print problem text, reference values, candidate values, or any secret/student data in the summary.
