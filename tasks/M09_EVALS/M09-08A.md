# M09-08A — OpenAI-Compatible Provider Base URL

Status: ACTIVE
Codex: YES

## Goal

Add optional OpenAI-compatible provider base URL support so AI Tutor VN can use either:

- the default OpenAI endpoint; or
- a configured OpenAI-compatible endpoint such as VietAPI.

This task is a narrow configuration/transport change only.

It must not change tutor behavior, prompts, model-selection logic, eval scoring, or API contracts.

## Why this task exists

M09-08 live-model validation is currently blocked.

The backend currently constructs the client as:

```python
OpenAI(api_key=settings.openai_api_key)
```

and has no configurable `base_url`.

VietAPI requires an OpenAI-compatible base URL such as:

```text
https://api.vietapi.tech/v1
```

The current M09-08 live smoke cannot proceed safely until the backend can receive an optional custom provider base URL.

## Configuration contract

Add a new setting:

```python
openai_base_url: str = ""
```

Environment variable:

```text
OPENAI_BASE_URL
```

Meaning:

### Empty / whitespace-only

Use the OpenAI SDK default endpoint.

Equivalent client construction:

```python
OpenAI(api_key=settings.openai_api_key)
```

Do not pass an empty `base_url`.

### Non-empty

Strip surrounding whitespace and pass the configured value:

```python
OpenAI(
    api_key=settings.openai_api_key,
    base_url=settings.openai_base_url.strip(),
)
```

Do not add provider-specific branching.

Do not rewrite the URL.

Do not append `/v1` automatically.

The configured value is authoritative.

## `.env.example`

Document:

```text
OPENAI_BASE_URL=
```

Keep the existing variables:

```text
OPENAI_API_KEY=
OPENAI_MODEL=...
OPENAI_REASONING_EFFORT=...
```

Do not place a real key in `.env.example`.

A short comment may indicate that `OPENAI_BASE_URL` is optional and intended for OpenAI-compatible providers.

Do not make VietAPI the default.

## Docker Compose

Pass the variable to the backend:

```yaml
OPENAI_BASE_URL: ${OPENAI_BASE_URL:-}
```

Do not modify any other service behavior.

Do not add secrets directly to `docker-compose.yml`.

## TutorAI construction

Keep demo behavior unchanged:

- if `OPENAI_API_KEY` is empty, `self.client` remains `None`;
- `OPENAI_BASE_URL` by itself must not create a client.

When the API key exists:

- empty base URL => instantiate SDK without `base_url`;
- configured base URL => instantiate SDK with the stripped `base_url`.

Prefer a small explicit construction path.

Do not change the rest of TutorAI.

## Test design

Create:

`backend/tests/test_tutor_ai_provider.py`

Tests must not call the network.

Monkeypatch the imported `OpenAI` constructor and `get_settings()` or use an equivalent deterministic approach.

Cover at least:

1. no API key => client remains `None`;
2. API key + empty base URL => OpenAI constructor receives API key and no `base_url`;
3. API key + whitespace-only base URL => no `base_url`;
4. API key + custom base URL => constructor receives the custom `base_url`;
5. surrounding whitespace in custom base URL is stripped;
6. custom base URL does not alter `openai_model`;
7. no network request is made.

The tests must not print or persist a real API key.

Use obvious fake values such as:

```text
test-key
https://provider.example/v1
```

## Compatibility note

This task proves only that the SDK client can target a configured OpenAI-compatible endpoint.

It does NOT claim that every provider fully supports:

```python
client.responses.parse(...)
```

or the project's structured-output schema.

That compatibility is intentionally verified by the parent M09-08 one-case live smoke.

If live structured parsing fails later, create a separate provider-compatibility task rather than broadening M09-08A.
