# M09-21 — Define Phase 3 Pilot Post-Test Measurement Contract

Status: DONE
Codex: Mostly ChatGPT
Module: Evals / Phase 3

## Direction gate

Phase 3 must produce evidence for its roadmap exit criterion before Phase 4 or a new feature family begins. This task defines the measurement contract only; it does not implement measurement infrastructure or collect pilot data.

## Goal

Define exactly how AI Tutor VN will measure the Phase 3 roadmap exit criterion:

```text
measurable post-test improvement on pilot users
```

## Context

Phase 3 implementation pieces are already present:

- curriculum prerequisite graph;
- authored question bank;
- authored difficulty;
- spaced-review scheduling;
- next-best-question recommendation;
- delivery of next learning action after completion;
- UI start of recommended authored question.

The Phase 3 roadmap exit criterion is still not measured.

## Why now

The product has the core Phase 3 learning-loop pieces, but no defined evidence contract for determining whether pilot learners improve on a trusted post-test. This task establishes that contract before additional feature expansion.

## Why not defer

Per `09_DEV_WORKFLOW.md`, the module-exit gate must be checked before entering a new feature family and evidence must precede expansion. Phase 4 should not start merely because Phase 3 components exist.

## Exit criterion affected

This task defines the measurement for the Phase 3 roadmap exit criterion: measurable post-test improvement on pilot users.

## Measurement contract

### Population

Measurement applies only to:

- pilot learners;
- Grade 8 algebra;
- the currently supported deterministic verification domain.

Results must not be generalized to other grades, subjects, or populations.

### Measurement unit

Use a matched learner design:

```text
same pilot learner
→ pre-test
→ defined AI Tutor learning exposure
→ post-test
```

Only learners with both valid pre-test and post-test results belong in the paired improvement calculation. Unmatched pre-test and post-test cohorts must not be mixed into the primary metric.

### Assessment trust boundary

Assessment scoring must rely on trusted authored assessment items and deterministic verification already supported by the product. An LLM judgment must not be the correctness authority for the Phase 3 exit metric.

Assessment items must remain inside supported verifier families. Unsupported or indeterminate verifier outcomes must not be silently counted as correct or incorrect.

### Assessment separation and leakage prevention

The measurement contract must prevent assessment leakage. Pre/post assessment items, expected answers, and verifier references must not be exposed through learner-facing tutor responses, recommendation payloads, ordinary tutoring prompts, or public API fields.

The post-test must measure learning rather than memorization of answers previously revealed by the tutor. Identical pre/post questions are not required; equivalent assessment forms following the same locked skill blueprint are preferred.

### Primary outcome

For each matched learner:

```text
pre_score = verified correct items / valid scored pre-test items
post_score = verified correct items / valid scored post-test items
paired_delta = post_score - pre_score
```

Primary cohort summary:

```text
mean paired_delta
```

The report must also include:

- matched learner count;
- mean pre_score;
- mean post_score;
- median paired_delta;
- number improved;
- number unchanged;
- number declined.

Do not invent a minimum improvement threshold or statistical-significance requirement that the roadmap does not currently specify. The contract should make the measured value visible and truthful rather than force a PASS.

### Skill-level diagnostics

Where the fixed assessment blueprint supports it, compute per-skill pre/post verified correctness for diagnostics. Skill-level metrics are diagnostic only unless a later task explicitly defines a gate.

Evaluation scoring must not update mastery state merely to make the metric favorable.

### Timing

A valid measurement requires:

```text
pre-test completed before the measured learning exposure
post-test completed after the measured learning exposure
```

The later implementation task must define one explicit intervention window or completion condition. M09-21 does not invent a pilot duration.

### Failure and exclusion reporting

A future measurement report must separately count and expose:

```text
missing pre-test
missing post-test
invalid/incomplete assessment
unsupported verification
indeterminate verification
```

These cases must not be silently discarded, and excluded cases must not enter the matched primary denominator.

### Reproducibility

A future implementation must make the metric reproducible from trusted structured records. Calculation must not depend on model prose, manual reviewer interpretation, hidden chain-of-thought, or random scoring. Given the same trusted assessment records, the same result must be produced.

## Privacy and data-minimization contract

The measurement contract requires:

- opaque internal learner IDs only;
- no learner names;
- no email addresses;
- no phone numbers;
- no raw chat transcripts;
- no uploaded student images;
- no unnecessary free-text student content;
- no secrets or API keys;
- no real pilot data committed to the public Git repository.

Repository tests and fixtures must use synthetic data only. Any future export intended for repository artifacts must contain aggregate or synthetic data, not identifiable learner records.
