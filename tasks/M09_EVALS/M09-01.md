# M09-01 — Baseline Evaluation Runner

Status: ACTIVE
Codex: YES

## Goal

Build a baseline evaluation runner that executes curated Grade 8 algebra cases and emits machine-readable JSON metrics.

The runner must separate:

1. deterministic/offline evaluation that can run without network or an API key;
2. live TutorAI evaluation that exercises problem analysis and first-turn tutoring behavior.

Evaluation generation and verification must remain separate where possible.

M09-01 establishes measurement infrastructure. It does not define final release thresholds.

## Context

The repository already contains:

- `evals/cases.jsonl`
- `docs/EVALS.md`
- `evals/AGENTS.md`
- controlled skill registry
- deterministic answer-leakage detector
- one-variable linear-equation verifier
- deterministic TutorState
- TutorAI analysis and first-turn behavior

Current `evals/cases.jsonl` contains four curated Grade 8 algebra cases.

The long-term evaluation plan calls for at least 200 cases, but expanding the dataset to 200 is NOT part of M09-01.

M09-01 builds the runner first so every future regression can become a durable measurable case.

## Product rule

Evals are release gates for tutor behavior, not demo examples.

Do not store real student personal data in eval fixtures.

The core product goal remains learning gain, but M09-01 measures system behavior prerequisites before later pre-test/post-test learning-gain evaluation.

## Module / micro-task

Module:

`M09 Evals`

Micro-task:

1. define a strict JSONL case loader;
2. implement deterministic offline metrics;
3. implement live TutorAI metrics behind explicit live mode;
4. emit one stable machine-readable report schema;
5. add focused unit tests;
6. enrich the existing four fixtures only where needed for deterministic verifier/state checks.

## Execution model

The runner supports two modes:

### offline

Must require:

- no OpenAI API key;
- no network;
- no database.

Offline mode evaluates only deterministic metrics that have sufficient fixture data.

Metrics that require TutorAI must be reported as `not_scored`, not failed.

### live

Live mode exercises:

```python
TutorAI.analyze_problem(...)
TutorAI.first_turn(...)
```

and then scores analysis/first-turn behavior with deterministic scorers.

Live mode requires a configured OpenAI client/API key.

If a real live client is unavailable, the CLI must fail clearly instead of silently using demo-mode output as a live evaluation.

Unit tests must use a fake/injected TutorAI adapter and must not call the network.

## Fixture schema

Each JSONL line is one case.

Required fields:

```json
{
  "id": "g8-linear-001",
  "problem": "2x + 3 = 11. Tìm x.",
  "expected_skills": ["algebra.linear_equation"],
  "expected_answer": "4",
  "first_turn_must_not_contain": ["x = 4", "x=4"]
}
```

Optional fields supported by M09-01:

```json
{
  "grade": 8,
  "expected_first_state": "ask_attempt",
  "risk_tags": ["answer_leakage"],
  "verifier": {
    "kind": "linear_equation",
    "equation": "2*x+3=11",
    "candidate": "4",
    "expected_valid": true
  }
}
```

Future fixture fields may be added later, but M09-01 must not implement broad schema evolution machinery.

## Loader validation

The loader must reject malformed fixture files deterministically.

Reject at least:

- invalid JSON;
- blank/invalid object line;
- missing `id`;
- duplicate case id;
- missing/blank `problem`;
- missing/empty `expected_skills`;
- missing `expected_answer`;
- non-list `first_turn_must_not_contain`;
- unsupported verifier kind;
- malformed verifier block.

A malformed fixture is a runner/configuration failure, not a failed student-case metric.

## Report schema

Emit JSON only to stdout when running the CLI.

Human-readable logs must go to stderr if any are needed.

The report must have a stable top-level shape equivalent to:

```json
{
  "schema_version": 1,
  "mode": "offline",
  "case_count": 4,
  "summary": {
    "extraction_correctness": {
      "passed": 0,
      "failed": 0,
      "not_scored": 4,
      "rate": null
    },
    "skill_classification": {},
    "answer_leakage": {},
    "verifier_correctness": {},
    "tutor_state_correctness": {}
  },
  "cases": []
}
```

For each metric:

- `passed`: scored cases that passed;
- `failed`: scored cases that failed;
- `not_scored`: cases where the metric was not applicable or requires live mode;
- `rate`: `passed / (passed + failed)`, or `null` when nothing was scored.

Do not treat `not_scored` as failure.

## Per-case report

Each case result must include at least:

```json
{
  "id": "g8-linear-001",
  "metrics": {
    "extraction_correctness": {
      "status": "pass|fail|not_scored",
      "details": {}
    },
    "skill_classification": {},
    "answer_leakage": {},
    "verifier_correctness": {},
    "tutor_state_correctness": {}
  }
}
```

Details should contain enough information to debug the failure without exposing secrets.

Do not include API keys, credentials, or raw internal chain-of-thought.

## Metric 1 — extraction correctness

This metric is live-mode only in M09-01.

Use:

```python
analysis.normalized_problem
```

from TutorAI.

For v1, extraction correctness is deterministic important-number preservation.

Extract numeric literals from:

- fixture `problem`;
- `analysis.normalized_problem`.

Pass when the ordered/multiset numeric literals are preserved according to one explicitly implemented deterministic rule.

The rule must be documented in code/tests.

Do not use an LLM to judge extraction correctness.

If the case contains no numeric literal, report `not_scored` for this v1 metric rather than inventing a semantic extraction judge.

M09-01 does not yet evaluate image/diagram extraction.

## Metric 2 — skill classification

This metric is live-mode only.

Canonicalize:

- fixture `expected_skills`;
- `analysis.skills`;

through the controlled skill registry.

Unknown actual skills must not silently become valid.

Pass when the canonical actual skill set exactly matches the canonical expected skill set.

Use set semantics for the main pass/fail metric.

Optionally report ordered/primary-skill information in details, but do not create another top-level metric in this task.

## Metric 3 — answer leakage

This metric is live-mode only because it scores the tutor's generated first turn.

Use both:

1. the existing deterministic answer-leakage detector;
2. the fixture's `first_turn_must_not_contain` phrases.

Fail when either mechanism detects leakage.

The explicit forbidden-phrase check must use deterministic normalization such as:

- Unicode NFKC;
- casefold;
- whitespace collapse.

Do not use another LLM to judge leakage.

The first turn's own `reveal_final_answer` signal may be passed to the existing detector, but model self-report alone is not authoritative.

## Metric 4 — verifier correctness

This metric is offline/deterministic.

Only score cases containing a supported `verifier` block.

For M09-01 the only supported verifier kind is:

`linear_equation`

Use the existing:

```python
verify_linear_equation_solution(...)
```

Compare the actual boolean result with fixture `expected_valid`.

Cases without a verifier block must be `not_scored`.

Unsupported verifier kinds are fixture errors, not `not_scored`.

Do not modify verifier behavior in this task.

## Metric 5 — tutor-state correctness

This metric is live-mode only.

Compare:

```python
first_turn.state.value
```

with fixture:

```text
expected_first_state
```

Default `expected_first_state` to:

`ask_attempt`

only if the field is omitted.

Current curated first-turn cases should expect `ask_attempt`.

## Live evaluation flow

For each case in live mode:

1. call `TutorAI.analyze_problem(case.problem, None)`;
2. call `TutorAI.first_turn(analysis, case.grade)`;
3. score extraction deterministically;
4. score skill classification deterministically;
5. score answer leakage deterministically;
6. score tutor-state deterministically;
7. also score any deterministic verifier fixture.

Do not call TutorAI more than necessary.

Do not persist a TutorSession or use the database.

## Offline evaluation flow

For each case in offline mode:

1. load/validate fixture;
2. score deterministic verifier fixture if present;
3. mark extraction as `not_scored`;
4. mark skill classification as `not_scored`;
5. mark answer leakage as `not_scored`;
6. mark tutor-state correctness as `not_scored`;
7. emit a complete report using the same schema as live mode.

Offline mode must not instantiate/use an external OpenAI client.

## Dependency injection / testability

Structure the runner so tests can provide a fake analyzer/tutor implementation.

Do not monkeypatch network libraries as the primary design.

The scoring functions should be pure where practical.

Examples of useful separations:

```text
load_cases(...)
score_extraction(...)
score_skills(...)
score_leakage(...)
score_verifier(...)
score_tutor_state(...)
run_cases(...)
```

Exact names may differ.

## CLI

Provide a module CLI callable as:

```powershell
python -m app.services.eval_runner --mode offline --cases /tmp/cases.jsonl
```

and:

```powershell
python -m app.services.eval_runner --mode live --cases /tmp/cases.jsonl
```

CLI stdout must contain only the JSON report.

CLI should return non-zero for:

- malformed fixture file;
- unsupported configuration;
- live mode without a real configured AI client;
- unexpected runner/internal error.

Metric failures themselves should still produce a report rather than crash the runner.

M09-01 does not implement threshold-based release-gate exit codes.

## Saving machine-readable output

The runner writes JSON to stdout so the caller can save it without changing repository/runtime mounts.

Example PowerShell workflow:

```powershell
docker compose cp .\evals\cases.jsonl backend:/tmp/cases.jsonl

docker compose exec -T backend `
  python -m app.services.eval_runner `
  --mode offline `
  --cases /tmp/cases.jsonl |
  Set-Content -Encoding utf8 $env:TEMP\ai-tutor-baseline-offline.json
```

A live report can be saved the same way when an API key is configured.

Do not commit generated result files in M09-01.
