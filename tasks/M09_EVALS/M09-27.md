# M09-27 — Add pilot reserved-exclusion orchestration seam

Status: DONE
Codex: YES — SMALL
Module: Evals
Phase: Phase 3 pilot readiness

## Direction gate

This task advances Phase 3 pilot readiness by composing the completed deterministic assignment and next-learning-action seams. It reserves only assessment pre/post IDs and does not wire pilot context into tutor runtime or claim the Phase 3 exit criterion.

## Goal

The implemented thin pilot-specific orchestration service composes:

```text
opaque assignment_seed
-> M09-24 assign_pilot_items(...)
-> derive reserved PRE + POST question IDs
-> M09-26 recommend_next_learning_question(excluded_question_ids=reserved_ids)
```

The service is limited to assessment-item leakage composition.

## Context

M09-24 is DONE and exposes `assign_pilot_items(*, assignment_seed: str)`. M09-25 is DONE and makes the deterministic recommender honor caller-supplied exclusions. M09-26 is DONE and forwards those exclusions through the next-learning-action adapter. M09-27 provides the pilot-specific composition layer receiving an opaque caller-supplied assignment seed.

## Why now

M09-27 composes the existing generic services into the pilot-specific boundary that derives reserved assessment IDs and forwards them to next-learning-action.

## Exit relationship

Completion means only that an explicit pilot assignment seed can be composed into reserved pre/post exclusions and passed to the existing next-learning-action seam. It does not create runtime assignment context, enforce learning-item selection, deliver assessments, complete pilot readiness, satisfy Phase 3, or authorize Phase 4.

## Micro-task

The implemented service exposes:

```python
def recommend_next_pilot_learning_question(
    db: Session,
    *,
    student_id: int,
    tutor_state: TutorState,
    now: datetime,
    assignment_seed: str,
) -> QuestionBankItem | None:
    ...
```

The public name is `recommend_next_pilot_learning_question` and behavior remains limited to this composition seam.

## Public contract

The service receives an opaque caller-supplied `assignment_seed`. On COMPLETE it calls `assign_pilot_items(assignment_seed=assignment_seed)` once, derives exclusions, calls `recommend_next_learning_question(...)` once, and returns its result unchanged.

## Reserved-ID derivation contract

Only `pre_question_id` and `post_question_id` are excluded. `learning_question_id` must remain available and must not be included:

```python
reserved_question_ids = tuple(
    question_id
    for assignment in assignments
    for question_id in (
        assignment.pre_question_id,
        assignment.post_question_id,
    )
)
```

Assignment tuple order is preserved, with `(pre, post)` order preserved within each assignment.

## Seed ownership

`assignment_seed` is an opaque token supplied by a future caller. The service must not generate it, hash learner identity into it, use `student_id`, email, name, phone, other PII, session IDs, timestamps, randomness, or UUIDs, persist it, or read it from the database. Seed validation remains owned by `assign_pilot_items`; invalid seed errors propagate.

## Error ownership

Do not add exception translation. Assignment-service `ValueError`s propagate. Downstream errors preserve existing behavior. Downstream `None` and selected `QuestionBankItem` results are returned unchanged.

## Architecture boundary

This is one thin composition service only. It must not modify `pilot_assessment_assignment.py`, `next_learning_action.py`, `question_recommender.py`, `tutor.py`, tutor schemas, session models, mastery, DB/schema/migrations, frontend, question bank, API contracts, or dependencies. No runtime tutor wiring occurs in M09-27.
