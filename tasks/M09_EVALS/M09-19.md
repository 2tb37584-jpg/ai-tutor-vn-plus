# M09-19 — Upgrade Verifier Eval Harness to Typed Verifier Contract

Status: READY
Codex: YES
Module: M09 Evals
Phase: Phase 2 — Correctness

## Direction gate

Roadmap link: Phase 2 correctness exit gate (>=98% correctness on supported initial domain)
Core-loop impact: Verification -> measurable deterministic correctness
Why now: The current eval metric only exercises the legacy linear-equation helper and cannot measure the current typed verifier families.
Why not defer: Without a harness aligned to the production verifier contract, Phase 2 correctness cannot be measured credibly.
Exit criterion affected: >=98% correctness on supported initial domain.

## Goal

Upgrade the verifier portion of the eval harness to use the production typed verifier contract:

```text
ProblemFamily
VerificationStatus
ExpressionEquivalenceRequest
LinearEquationRequest
NumericVerificationRequest
verify(...)
```

Support the three current verifier families:

```text
linear_equation
expression_equivalence
numeric
```

Do not expand the benchmark corpus in this task.

## Context

Current eval behavior:

- `VerifierFixture` is hard-coded to:
  - `kind`
  - `equation`
  - `candidate`
  - `expected_valid: bool`
- `_parse_verifier(...)` accepts only `kind="linear_equation"`.
- `score_verifier(...)` directly calls the legacy helper:
  `verify_linear_equation_solution(...)`.
- Existing corpus contains 8 verifier fixtures, all linear-equation fixtures.
- Production verification now routes through typed requests and returns:
  - `correct`
  - `incorrect`
  - `unsupported`
  - `indeterminate`

The eval harness must measure that current contract rather than a legacy boolean helper.

## Micro-task

Refactor only the verifier-fixture parsing/scoring seam.

Do not change unrelated eval metrics.

## Canonical internal fixture

Normalize verifier fixtures internally to:

```python
@dataclass(frozen=True)
class VerifierFixture:
    family: str
    reference: str
    candidate: str
    expected_status: str
```

Interpret `reference` by family:

```text
linear_equation
reference = equation text

expression_equivalence
reference = expected/reference expression

numeric
reference = expected scalar literal
```

`expected_status` must correspond to a current `VerificationStatus.value`:

```text
correct
incorrect
unsupported
indeterminate
```

## Canonical fixture input shape

The parser should accept a new canonical JSON verifier block:

```json
{
  "family": "numeric",
  "reference": "1/2",
  "candidate": "0.5",
  "expected_status": "incorrect"
}
```

Equivalent expression example:

```json
{
  "family": "expression_equivalence",
  "reference": "2*(x+1)",
  "candidate": "2*x+2",
  "expected_status": "correct"
}
```

Linear example:

```json
{
  "family": "linear_equation",
  "reference": "2*x+3=11",
  "candidate": "4",
  "expected_status": "correct"
}
```

## Legacy backward compatibility

Do not modify the existing 8 linear verifier corpus fixtures in this task.

Continue accepting the legacy shape:

```json
{
  "kind": "linear_equation",
  "equation": "2*x+3=11",
  "candidate": "4",
  "expected_valid": true
}
```

Normalize it internally as:

```text
family = linear_equation
reference = equation
candidate = candidate
expected_status = correct if expected_valid is true
expected_status = incorrect if expected_valid is false
```

Only the exact current legacy linear shape should be accepted.

Do not introduce multiple overlapping legacy schemas.

## Validation rules

For canonical fixture blocks:

- keys must be exactly:
  - `family`
  - `reference`
  - `candidate`
  - `expected_status`
- `family` must be one of the current `ProblemFamily` values.
- `reference` must be a non-empty string.
- `candidate` must be a non-empty string.
- `expected_status` must be one of the current `VerificationStatus` values.

For legacy blocks:

- keys must be exactly:
  - `kind`
  - `equation`
  - `candidate`
  - `expected_valid`
- `kind` must equal `linear_equation`.
- `equation` and `candidate` must be non-empty strings.
- `expected_valid` must be bool.

Any hybrid, partial, extra-key, or unsupported-family block must raise `FixtureError`.

Do not silently coerce unknown values.

## Scoring contract

`score_verifier(...)` must:

1. return `not_scored` when fixture is `None`;
2. create the correct typed request from the normalized fixture;
3. call production `verify(request)`;
4. compare `result.status.value` with `fixture.expected_status`;
5. return:
   - `pass` when equal;
   - `fail` when different.

Details should expose safe deterministic comparison metadata only, for example:

```text
expected_status
actual_status
family
```

Do not include unrelated problem text or student content.

## Typed request mapping

### linear_equation

```python
LinearEquationRequest(
    family=ProblemFamily.LINEAR_EQUATION,
    equation=fixture.reference,
    candidate=fixture.candidate,
)
```

Use the existing default variable contract unless the current production API requires an explicit value.

### expression_equivalence

```python
ExpressionEquivalenceRequest(
    family=ProblemFamily.EXPRESSION_EQUIVALENCE,
    left=fixture.reference,
    right=fixture.candidate,
)
```

### numeric

```python
NumericVerificationRequest(
    family=ProblemFamily.NUMERIC,
    expected=fixture.reference,
    candidate=fixture.candidate,
)
```
