# M09-36 — Track pilot intervention completion and exact progression

Status: ACTIVE
Codex: Yes, small
Module: Evals
Phase: Phase 3 pilot readiness

## Goal

Complete trusted pilot intervention runtime behavior: deterministic completion of the exact persisted LEARNING assignment, progression to the next exact persisted assignment, and transition of the enrollment to POST only after all nine learning assignments are complete. For pilot-provenance TRANSFER selection, exclude only the assignment's PRE and POST questions while leaving its LEARNING question eligible.

## Context

M09-30 persists pilot enrollments and frozen assignments. M09-32 provides deterministic PRE/POST assessment behavior. M09-34B protects generic tutor paths from active-pilot reserved items. M09-35 starts the exact server-authorized persisted LEARNING assignment and saves session provenance. This task adds completion/progression without changing those contracts or claiming Phase 3 success.

## Trusted completion authority

An assignment may be completed only on the existing deterministic edge: the persisted session begins the request in `TRANSFER`, transfer verification returns `CORRECT`, and the existing `TRANSFER_COMPLETED` transition returns `COMPLETE`. Model `likely_correct`, generated COMPLETE, message count, elapsed time, mastery probability, and client claims are not completion authority. Tutor-state semantics remain unchanged.

## Provenance validation

For pilot-provenance sessions, validate the exact persisted assignment and enrollment before durable tutor side effects. Require matching assignment/enrollment/student provenance, active `intervention` phase, matching authored LEARNING question and skill, exactly nine assignments ordered by persisted ID, scored/submitted PRE records, untouched POST records, and a prefix of completed LEARNING timestamps. An incomplete session assignment must be the first incomplete assignment. Already-completed provenance is allowed for duplicate sessions and must be idempotent. Malformed state raises a narrow state error; invalid trusted authored configuration raises a narrow configuration error. Do not use fuzzy matching, seeds, or recomputation.

## Pilot TRANSFER exclusions

For a valid pilot session, exclude exactly that assignment's PRE and POST IDs from deterministic transfer selection. Do not exclude its LEARNING ID solely because it is frozen for the LEARNING role. Do not introduce cross-skill exclusions. For non-pilot sessions, preserve the generic active-pilot reservation resolver and its all-role exclusions unchanged.

## Completion persistence

When a trusted pilot session reaches COMPLETE, set only its exact assignment's `learning_completed_at` to the server-side `received_at` timestamp if it is currently null. Do not require correctness history on the original LEARNING problem. Do not mutate PRE/POST results, frozen IDs, skill, session provenance, or mastery.

## Duplicate-session idempotency

M09-35 permits multiple sessions for one incomplete assignment. If one session has already completed that assignment, a later duplicate's trusted COMPLETE must not overwrite the first timestamp, complete a different assignment, or corrupt progression; it may resolve the current next incomplete assignment.

## Exact next-assignment progression

After completion, select the first incomplete persisted assignment ordered by ID and resolve exactly its `learning_question_id` using the trusted question bank. Require exact item ID and matching skill. Return the learner-safe item through the existing `next_learning_action` projection. This projection is informational; only the M09-35 pilot-start route starts the next tutor session. Pilot provenance completion must not call the generic recommender. Non-pilot TRANSFER completion keeps its current recommendation behavior.

## Final intervention -> POST transition

When all nine assignments have a completion timestamp, change the enrollment phase to `post` and return no next learning action. Do not start or submit a POST assessment, and do not set phase to `complete`; M09-33 owns POST delivery and completion.

## Generic recommender boundary

Persisted pilot assignment order is authoritative for pilot progression. Bypass `recommend_next_learning_question(...)` for pilot-provenance completion only. Preserve generic recommendation behavior for non-pilot TRANSFER completion.

## M09-34B/M09-35 preservation

Do not weaken generic M09-34B all-role reserved-item guards. Keep M09-35 exact server-selected LEARNING item, student ownership, response projection, and `TutorSession` provenance unchanged. Completion belongs to the trusted tutor reply runtime, not pilot start.

## Transaction/error boundary

Add `backend/app/services/pilot_intervention.py` with narrow state/configuration errors and immutable context/progression results. The service may set only the selected assignment's `learning_completed_at` and enrollment phase; it must not commit. `tutor_reply` owns the transaction. Known intervention state/configuration failures map to generic 503 `Pilot learning is temporarily unavailable`; rollback pending tutor mutations first. Unexpected exceptions propagate. Already-COMPLETE session follow-up must not redo pilot progression, timestamp mutation, or recommendation.

## Privacy/trust boundary

No public API/schema changes, raw answer persistence, expected answer/verifier leakage, client progression authority, PII-derived identifiers, model correctness authority, seed persistence, or assessment auto-start. Expose only existing learner-safe next-action fields.
