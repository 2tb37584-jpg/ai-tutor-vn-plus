# M09-22 — Add Pure Paired Pilot Measurement Calculator

Status: DONE
Codex: YES — SMALL
Module: Evals / Phase 3

## Direction gate

M09-21 is DONE and defines the Phase 3 pilot post-test measurement contract. M09-22 implements only the smallest deterministic calculation seam needed to turn already-trusted structured pre/post summaries into reproducible paired metrics.

## Goal

Add a pure calculator that consumes trusted aggregate assessment records and deterministically produces matched learner results, pre/post scores, paired deltas, cohort summary metrics, and explicit exclusion counts.

M09-22 must not add persistence, APIs, dashboards, analytics infrastructure, verifier calls, model calls, or real pilot data.

## Context

The primary learner metrics are:

```text
pre_score = verified correct items / valid scored pre-test items
post_score = verified correct items / valid scored post-test items
paired_delta = post_score - pre_score
```

The primary cohort metric is:

```text
mean paired_delta
```

Required cohort diagnostics are matched learner count, mean pre-score, mean post-score, median paired delta, and improved/unchanged/declined counts. Required exclusion diagnostics are missing pre-test, missing post-test, invalid/incomplete assessment, unsupported verification, and indeterminate verification.

Only learners with valid pre and valid post assessments enter the primary denominator.

## Micro-task

Implement the pure production seam in `backend/app/services/pilot_measurement.py` and its focused unit tests in `backend/tests/test_pilot_measurement.py`. The calculator receives already-trusted aggregate assessment records and performs no I/O or external calls.

## Why now

The Phase 3 product loop exists and M09-21 has defined its exit metric, but there is not yet a deterministic implementation that can calculate the paired improvement report.

## Why not defer

Evidence must precede expansion. A small pure calculator provides the narrowest reproducible measurement seam without coupling evaluation to runtime tutoring, persistence, or recommendation behavior.

## Exit criterion affected

## Architecture boundary

The calculator must not load ORM models, query the database, call the verifier, call TutorAI, read raw chat or uploaded images, expose or consume expected answers, perform HTTP/API work, update mastery, or update recommendations.

## Input contract

Define a frozen structured input equivalent to:

```python
PilotAssessmentRecord(
    learner_id: str,
    phase: Literal["pre", "post"],
    outcome: Literal[
        "valid",
        "invalid_incomplete",
        "unsupported_verification",
        "indeterminate_verification",
    ],
    verified_correct_items: int,
    valid_scored_items: int,
)
```

Equivalent names are acceptable only when semantics remain identical.

`learner_id` is a non-empty opaque internal identifier used only for pairing. A valid assessment requires `valid_scored_items > 0` and `0 <= verified_correct_items <= valid_scored_items`. Excluded outcomes must not contribute score values; prefer requiring both score counts to be zero.

At most one record may exist for each `(learner_id, phase)`. Duplicate records must fail deterministically with `ValueError`; the calculator must not silently choose one.

## Validation rules

Reject malformed trusted-record input rather than guessing. At minimum reject empty learner IDs, unsupported phases or outcomes, booleans used as integer score counts, negative counts, correct counts greater than scored counts, zero scored items for valid assessments, non-zero counts for excluded assessments, and duplicate learner/phase records.

## Matching semantics

A learner enters the paired cohort only with a valid pre record and a valid post record. A learner with only a post record contributes to `missing_pre`; a learner with only a pre record contributes to `missing_post`. Invalid, unsupported, and indeterminate outcomes must be counted explicitly and must not enter the matched denominator. A learner may contribute to more than one diagnostic exclusion category when the records truthfully imply more than one condition.

## Output and report contract

For every matched learner, return `pre_score`, `post_score`, and `paired_delta`, with scores calculated as verified correct items divided by valid scored items. Output must not contain raw answers, expected answers, verifier references, chats, or images.

Return deterministic cohort fields equivalent to:

```text
matched_learner_count
mean_pre_score
mean_post_score
mean_paired_delta
median_paired_delta
improved_count
unchanged_count
declined_count
```

Classify deltas exactly as positive improved, zero unchanged, and negative declined. Do not use arbitrary tolerances. Exact rational arithmetic may be used internally without adding dependencies.

If no valid matched learners exist, `matched_learner_count` is zero and undefined aggregate score/delta values are `None`, not zero. Counts remain zero where appropriate and no PASS/FAIL outcome is invented.

## Exclusion semantics

Return explicit diagnostic counts equivalent to `missing_pre`, `missing_post`, `invalid_incomplete`, `unsupported_verification`, and `indeterminate_verification`. These counts are outside the matched primary denominator and must not be silently discarded.

## Determinism

For identical input records, output must be identical regardless of input ordering. Results must not depend on randomization, wall-clock time, model prose, manual reviewer judgment, or hidden chain-of-thought. Paired learner results must use deterministic ordering, such as sorted opaque learner IDs.

## Privacy boundary

No real pilot or student records may be added. Tests use synthetic opaque IDs such as `learner-a` and `learner-b` only. Tests and repository artifacts must contain no real names, emails, phone numbers, raw chat, student images, unnecessary free text, secrets, or API keys.

## Explicit non-goals

M09-22 does not run the pilot, define pilot duration, persist assessments, add database tables or migrations, add schemas or API endpoints, collect answers, call a deterministic verifier or LLM, add a CLI, dashboard, or UI, update mastery or recommendation policy, implement BKT/IRT, add dependencies, define statistical significance, or invent a minimum improvement threshold.

M09-22 does not implement per-skill diagnostics. M09-21 defines them as diagnostic where a future locked assessment blueprint supports them; adding per-skill inputs is outside this smallest seam.
