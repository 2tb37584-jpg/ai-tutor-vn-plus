# M09-08B — OpenAI-Compatible Structured API Mode

Status: ACTIVE
Codex: YES

## Goal

Add a generic provider API mode so `TutorAI` can use structured generation through either:

- OpenAI Responses API (`responses.parse`) — current/default behavior; or
- Chat Completions structured parsing (`chat.completions.parse`) — for OpenAI-compatible providers whose `/responses` wire format is not compatible with the OpenAI SDK parser.

This task exists because the M09-08 live smoke proved:

- authentication succeeds;
- `gpt-5.6-terra` responds;
- VietAPI `/v1/responses` returns HTTP 200 but a `chat.completion`-shaped payload with `choices`, not Responses-shaped `output`;
- OpenAI SDK 2.54.0 therefore fails inside `responses.parse()` with `TypeError: 'NoneType' object is not iterable`;
- `client.chat.completions.parse(...)` with a Pydantic response model succeeds and returns a parsed object.

The implementation must remain provider-neutral. Do not special-case VietAPI.

## Configuration contract

Add a new typed setting:

```python
from typing import Literal

openai_api_mode: Literal["responses", "chat_completions"] = "responses"
```

Environment variable:

```text
OPENAI_API_MODE
```

Default:

```text
responses
```

The default must preserve current behavior for existing OpenAI deployments.

Invalid values should fail through normal Pydantic settings validation rather than silently choosing another mode.

## `.env.example`

Document:

```text
OPENAI_API_MODE=responses
```

Keep existing OpenAI-compatible settings unchanged.

A short comment is acceptable, for example:

```text
# Structured API mode: responses or chat_completions
```

Do not make a third-party provider the default.

## Docker Compose

Pass the variable to backend:

```yaml
OPENAI_API_MODE: ${OPENAI_API_MODE:-responses}
```

Do not change any other service behavior.

## TutorAI behavior

### Client construction

Do not change the already-implemented `OPENAI_BASE_URL` contract.

No API key must still mean:

```python
self.client = None
```

### `responses` mode

All existing production behavior must remain equivalent to the current implementation:

```python
self.client.responses.parse(...)
```

Return:

```python
response.output_parsed
```

Do not change request shape for this mode.

### `chat_completions` mode

Use:

```python
self.client.chat.completions.parse(...)
```

with the same Pydantic response model currently supplied as `text_format` in Responses mode.

For Chat Completions use:

```python
response_format=<Pydantic model>
```

Return:

```python
response.choices[0].message.parsed
```

The public methods must still return the exact existing types:

- `ProblemAnalysis`
- `TutorTurn`

No dict should leak past the transport layer.

If parsed output is unexpectedly absent, fail explicitly; do not synthesize a fake successful result.

## Request-shape preservation

### `first_turn(...)`

Current system/user prompt semantics must stay exactly the same.

Only translate the API transport shape required by Chat Completions.

### `continue_turn(...)`

Current system/user prompt semantics, state policy instructions, transcript, and newest student message must stay exactly the same.

Only translate the API transport shape required by Chat Completions.

### `analyze_problem(...)`

Text-only analysis must preserve the same system prompt and user text.

Image analysis must remain supported.

Responses mode must keep its current content form.

For Chat Completions, translate multimodal content into the OpenAI-compatible Chat Completions form expected by the installed SDK, preserving:

- the same text;
- the same image data URL;
- image detail equivalent to current `detail="auto"` behavior.

Do not preprocess, resize, upload, persist, or log image data.

## Implementation shape

Prefer a small private transport helper rather than duplicating three full methods.

A reasonable design is one helper that accepts:

- expected Pydantic response type;
- Responses API input;
- Chat Completions messages;

and dispatches according to `self.settings.openai_api_mode`.

Do not introduce a new module unless absolutely necessary. This task is intentionally limited to `tutor_ai.py`.

Keep the helper private.

## Tests

Create:

`backend/tests/test_tutor_ai_api_mode.py`

Tests must be deterministic and make zero network calls.

Use fake clients / monkeypatching.

Cover at least:

### Configuration / routing

1. default mode is `responses`;
2. `responses` mode calls `client.responses.parse`;
3. `chat_completions` mode calls `client.chat.completions.parse`;
4. no silent fallback occurs between modes;
5. custom `OPENAI_BASE_URL` behavior from M09-08A remains unaffected.

### Structured return handling

6. Responses mode returns `response.output_parsed`;
7. Chat Completions mode returns `response.choices[0].message.parsed`;
8. parsed `ProblemAnalysis` remains a `ProblemAnalysis`;
9. parsed `TutorTurn` remains a `TutorTurn`;
10. absent Chat Completions parsed output fails explicitly rather than returning an invalid object.

### Prompt / behavior preservation

11. `first_turn(...)` sends the same system prompt and equivalent user context in both modes;
12. `continue_turn(...)` sends the same system prompt and equivalent generated user prompt in both modes;
13. state-normalization logic still applies after the model response exactly as before.

### Image transport

14. `analyze_problem(...)` text-only Chat Completions request contains the original text;
15. image-mode Chat Completions request includes the original data URL;
16. image detail remains equivalent to `auto`;
17. image data is not logged or persisted by the new code.

### Network safety

18. tests do not issue HTTP requests.
