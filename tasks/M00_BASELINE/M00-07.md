# M00-07 — Task Lifecycle Automation

Status: ACTIVE
Codex: YES
Module: Baseline / Developer Workflow

## Goal

Automate task lifecycle status changes so developers no longer need to manually edit both `TASK_INDEX.md` and individual task files.

Required interface:

```powershell
.\dev.ps1 task status
.\dev.ps1 task start Mxx-yy
.\dev.ps1 task done Mxx-yy
```

This task must make task-control transitions safer and more consistent without modifying product/business code.

## Context

M00-06 introduced the root developer command layer:

```powershell
.\dev.ps1 status
.\dev.ps1 review
.\dev.ps1 test eval
.\dev.ps1 test full
.\dev.ps1 snapshot
```

Task lifecycle is still manual. This has already caused status mismatches and unwanted text/encoding churn in task files.

`TASK_INDEX.md` and the corresponding `tasks/.../Mxx-yy.md` file must agree.

The repository remains the source of truth.

## Micro-task

Implement a small lifecycle command group inside `dev.ps1` that can:

1. report lifecycle consistency;
2. start one READY task safely;
3. complete the current ACTIVE task safely;
4. refuse unsafe or ambiguous transitions;
5. preserve file encoding/content outside the exact status fields being changed.

Do not build a generic workflow framework.

## Allowed files

1. `dev.ps1`
2. `09_DEV_WORKFLOW.md`
3. `tasks/M00_BASELINE/M00-07.md`

Prefer modifying only `dev.ps1` and `09_DEV_WORKFLOW.md` during implementation.

Do not modify `TASK_INDEX.md` as part of Codex implementation except when exercising the lifecycle command in an explicitly isolated validation step approved by the user/reviewer.

If another implementation file is required, stop and report before expanding scope.

## Forbidden scope

Do NOT modify:

- backend production/business logic;
- TutorAI prompts;
- eval scorer semantics;
- eval fixtures;
- taxonomy or skill registry;
- API schemas;
- migrations;
- frontend behavior;

- dependencies;
- unrelated task files.

Do NOT:

- add dependencies;

- print secrets or `.env`;
- automatically select the next task;
- automatically commit;
- rewrite whole markdown files in a way that causes unrelated encoding/EOL churn;
- silently repair inconsistent task-control state.

## Source-of-truth rules

For a task ID such as `M00-07`:

- `TASK_INDEX.md` contains the indexed status;
- exactly one matching task file must exist under `tasks/**/M00-07.md`;
- the task file contains a top-level line in the form:

```text
Status: READY
```

Supported lifecycle statuses remain:

```text
BACKLOG / READY / ACTIVE / BLOCKED / REVIEW / DONE
```

Lifecycle commands must validate both sources before writing.

## Command: `task status`

Usage:

```powershell
.\dev.ps1 task status
```

Read-only.

Must report at minimum:

- current ACTIVE task from `TASK_INDEX.md`;
- matching task-file status;
- whether index and task file agree;
- whether more than one ACTIVE task exists;
- concise error when the ACTIVE task file is missing or ambiguous.

Expected healthy output shape:

```text
===== TASK STATUS =====
ACTIVE: M00-07
INDEX_STATUS: ACTIVE
FILE_STATUS: ACTIVE
CONSISTENT: yes
```

If there is no ACTIVE task:

```text
ACTIVE: none
CONSISTENT: yes
```

If state is inconsistent, command must exit nonzero.

Do not modify files.

## Command: `task start`

Usage:

```powershell
.\dev.ps1 task start Mxx-yy
```

Preconditions:

- task ID exists exactly once in `TASK_INDEX.md`;
- exactly one matching task file exists;
- index status and task-file status agree;
- target task status is `READY`;
- there is currently no other ACTIVE task;
- target task itself is not already ACTIVE/DONE/BLOCKED/REVIEW/BACKLOG.

If any precondition fails:

- print a concise reason;
- exit nonzero;
- write nothing.

On success:

- change only target task status from `READY` to `ACTIVE` in `TASK_INDEX.md`;
- change only the task file's `Status: READY` line to `Status: ACTIVE`;
- preserve all unrelated content;
- report the transition;
- exit 0.

Do not select or start any additional task.

## Command: `task done`

Usage:

```powershell
.\dev.ps1 task done Mxx-yy
```

Preconditions:

- task ID exists exactly once in `TASK_INDEX.md`;
- exactly one matching task file exists;
- target is the single current ACTIVE task;
- index and task-file statuses both equal `ACTIVE`;
- acceptance checklist in the task file is explicitly complete.

### Acceptance checklist contract

For lifecycle automation, task files intended to be closed by `task done` must contain a section:

```markdown
## Acceptance checklist

- [x] ...
- [x] ...
```

`task done` must refuse completion if:

- the section is absent;
- it contains no checkbox items;
- any checkbox in that section is unchecked (`[ ]`);
- task-control state is inconsistent.

Checkbox matching should be case-insensitive for `[x]`.

Do not infer completion from prose or test output.

On success:

- change only target status `ACTIVE` -> `DONE` in `TASK_INDEX.md`;
- change only `Status: ACTIVE` -> `Status: DONE` in the task file;
- do not start the next task;
- report the transition;
- exit 0.

## Atomicity / write safety

Before writing:

1. read and validate both files;
2. compute both updated contents in memory;
3. confirm exactly the intended status fields would change.

If validation fails, write nothing.

For a successful transition, updates to the two task-control files should behave transactionally as far as practical in local PowerShell:

- write temporary files first;
- replace originals only after both temporary outputs are valid;
- if replacement cannot complete, surface an error and avoid intentionally leaving one file updated and the other stale.

Do not introduce a dependency for transactions.

## Encoding and line-ending safety

This task must specifically prevent the kind of mojibake/EOL churn previously observed in task files.

Requirements:

- preserve valid UTF-8 content, including Vietnamese and em dashes;
- do not convert characters such as `—` into mojibake;
- preserve the existing newline style of each file where practical;
- do not add/remove unrelated blank lines;
- do not trim unrelated whitespace;
- do not rewrite unrelated markdown content.

Use explicit .NET text encoding APIs if needed rather than relying on PowerShell defaults that vary by version.

A lifecycle transition diff should contain only the intended status-line changes.
