# M10-01 — Tutor Conversation Shell

Status: ACTIVE
Codex: YES

## Goal

Tighten the existing tutoring conversation shell so it reflects the stabilized backend Tutor Engine contract instead of rendering only raw message text.

The shell must make the learning flow visible without redesigning the application:

- problem input → tutor starts session;
- tutor asks for an attempt;
- student replies;
- tutor response shows current tutoring stage and hint progression;
- loading/error states remain clear;
- backend-guarded tutor messages are rendered as-is.

This task is a focused frontend contract-alignment task, not a UI redesign.

## Context

The current frontend already has a working single-page MVP in:

`frontend/app/page.tsx`

It already supports:

- register/login;
- student creation/selection;
- mastery list;
- problem text input;
- optional image upload;
- `/tutor/start`;
- message thread;
- `/tutor/reply`;
- starting a new problem.

Current frontend typecheck passes:

```text
npm run lint
tsc --noEmit
```

The existing UI currently models only a subset of `TutorTurn` and discards Tutor Engine metadata after API responses.

The backend Tutor Engine contract is stable and exposes:

```text
TutorState:
diagnose
ask_attempt
hint_1
hint_2
explain_step
verify
transfer
complete
```

`TutorTurn` fields include:

```text
message
state
next_action
hint_level
skill_tags
misconception
likely_correct
reveal_final_answer
```

`StartTutorResponse` returns:

```text
session_id
analysis
tutor
```

`TutorReplyResponse` returns:

```text
tutor
```

The frontend must call backend APIs only. It must never call OpenAI directly.

## Product intent

The conversation shell should reinforce tutoring progress, not optimize for answer delivery.

Do not expose internal or low-confidence learning judgments merely because the backend schema contains them.

For M10-01:

- show tutor state;
- show hint level when relevant;
- show skill tags when available;
- do NOT display `misconception`;
- do NOT display `likely_correct`;
- do NOT display `reveal_final_answer` as a learner-facing signal;
- do NOT expose internal expected answers or verification notes.

The tutor message itself remains authoritative display content from the backend response.

## TypeScript contract

Define a frontend tutor state type equivalent to:

```ts
type TutorState =
  | "diagnose"
  | "ask_attempt"
  | "hint_1"
  | "hint_2"
  | "explain_step"
  | "verify"
  | "transfer"
  | "complete";
```

Define a frontend `TutorTurn` type compatible with the backend public response:

```ts
type TutorTurn = {
  message: string;
  state: TutorState;
  next_action: string;
  hint_level: number;
  skill_tags: string[];
  misconception: string | null;
  likely_correct: boolean | null;
  reveal_final_answer: boolean;
};
```

Do not use `any`.

`StartResponse` must use this `TutorTurn`.

Define a reply response type equivalent to:

```ts
type TutorReplyResponse = {
  tutor: TutorTurn;
};
```

The frontend must continue to model only public response data.

## Conversation message model

Extend the local chat message model so tutor messages can preserve the current turn metadata.

A suitable equivalent is:

```ts
type ChatMessage =
  | {
      role: "student";
      content: string;
    }
  | {
      role: "tutor";
      content: string;
      turn: TutorTurn;
    };
```

Equivalent strongly typed designs are acceptable.

Do not copy tutor metadata onto student messages.

On `/tutor/start`, store the returned `TutorTurn` with the first tutor message.

On `/tutor/reply`, store the returned `TutorTurn` with the new tutor message.

## Learner-facing state labels

Render a concise Vietnamese label for the tutor state.

Use deterministic labels equivalent to:

```text
diagnose       -> Đang chẩn đoán
ask_attempt    -> Đang chờ em thử
hint_1         -> Gợi ý 1
hint_2         -> Gợi ý 2
explain_step   -> Giải thích bước
verify         -> Đang kiểm tra
transfer       -> Bài vận dụng
complete       -> Hoàn thành
```

Implement this as a small typed mapping or helper.

Do not let unknown strings silently map through unsafe casts.

The TypeScript union should prevent invalid state values in normal typed code.

## Tutor progress display

For tutor messages, show a compact metadata row near the tutor label/message.

Display:

- human-readable tutor-state label;
- `hint_level` only when greater than `0`;
- skill tags only when non-empty.

Example conceptual display:

```text
Gia sư
Gợi ý 1 · Mức gợi ý 1
algebra.linear_equation
```

Exact visual wording may differ.

Keep the metadata visually secondary to the tutor message.

Do not show:

- `misconception`;
- `likely_correct`;
- `reveal_final_answer`;
- internal answers;
- verification notes.

## Current session indicator

When a tutoring session is active, show the latest tutor state prominently but compactly near the analysis/conversation area.

This should update after every tutor response.

It may be derived from the most recent tutor message rather than stored as duplicated independent state.

Do not add global state libraries.

## Start flow

Keep the existing `/tutor/start` request contract:

```json
{
  "student_id": 123,
  "problem_text": "...",
  "image_data_url": null
}
```

Do not change backend fields.

On success:

- set `sessionId`;
- store public analysis;
- store first `TutorTurn`;
- clear stale reply text if needed;
- show a successful session status.

Do not show or infer the expected answer.

## Reply flow

Keep the existing `/tutor/reply` request contract:

```json
{
  "session_id": 123,
  "student_message": "..."
}
```

On submit:

- trim empty replies;
- append the student message once;
- disable the input/button while request is in flight;
- append returned tutor turn with metadata on success.

Do not call `/tutor/attempt` from M10-01.

The current mastery contract deliberately does not trust a client `correct` claim, so the UI must not fabricate correctness or mastery updates.

## Failure behavior

Preserve the existing visible error status.

Do not erase the conversation if a reply fails.

Do not duplicate the tutor message on retry.

Keep implementation simple; no retry framework is needed.

## Busy state

During start/reply requests:

- relevant action controls remain disabled;
- expose a concise visible busy cue in existing status/UI;
- do not introduce a spinner package.

No new dependency.

## New problem reset

Keep the existing “Bài mới” action.

Reset only session-local tutoring state:

- `sessionId`;
- messages;
- analysis;
- reply;
- selected image if appropriate.

Do not log out.

Do not clear student selection.

Do not clear mastery.
