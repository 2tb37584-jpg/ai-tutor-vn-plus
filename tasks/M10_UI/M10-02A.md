# M10-02A — Explicit Hint Request Contract

Status: ACTIVE
Codex: YES

## Goal

Add an explicit, deterministic backend contract for a student requesting more help during tutoring.

A hint request must advance tutor assistance without pretending that the student submitted an incorrect answer.

The client may express only the intent:

```text
hint_request
```

The client must not decide:

- whether an attempt is correct;
- whether an attempt is incorrect;
- mastery evidence;
- misconception confirmation.

This task is a backend prerequisite for M10-02B Student Attempt + Hint Controls UI.

## Why this task exists

The current Tutor Engine advances:

```text
ask_attempt -> hint_1 -> hint_2 -> explain_step
```

only when `TutorAI` returns:

```text
likely_correct = False
```

A student message such as:

```text
"Em chưa biết, cho em gợi ý."
```

may legitimately produce:

```text
likely_correct = None
```

and therefore leave state at:

```text
ask_attempt
```

That makes a UI “Xin gợi ý” button nondeterministic.

M10-02A introduces a trusted server-side hint-request event so requesting help has deterministic state behavior.

## Product/trust rule

Requesting a hint is not evidence that an attempt was wrong.

Do not implement hint requests by:

- setting `correct=false`;
- calling `/tutor/attempt`;
- creating mastery evidence;
- creating confirmed misconception evidence;
- reusing a client correctness claim.

Hint request intent affects tutoring assistance state only.

## Module / micro-task

Module:

`Tutor Engine / M10 prerequisite`

3. make TutorAI generate at the requested assistance state;

6. add focused tests.

## Reply intent contract

Add a typed enum equivalent to:

```python
class TutorReplyIntent(str, Enum):
    ATTEMPT = "attempt"
    HINT_REQUEST = "hint_request"
```

Extend:

```python
class TutorReplyRequest(BaseModel):
    session_id: int
    student_message: str = Field(min_length=1, max_length=8000)
```

with:

```python
intent: TutorReplyIntent = TutorReplyIntent.ATTEMPT
```

The default is critical for backward compatibility.

Existing clients that omit `intent` must continue behaving exactly as attempt replies do today.

## Transition event

Add a new deterministic event:

```python
TutorTransitionEvent.HINT_REQUESTED
```

Do not reuse:

```python
ATTEMPT_INCORRECT
```

because requesting help is not equivalent to an incorrect attempt.

## Deterministic hint transitions

Add exactly these transitions:

```text
ASK_ATTEMPT + HINT_REQUESTED -> HINT_1
HINT_1      + HINT_REQUESTED -> HINT_2
HINT_2      + HINT_REQUESTED -> EXPLAIN_STEP
```

Do not add a hint transition from:

```text
DIAGNOSE
EXPLAIN_STEP
VERIFY
TRANSFER
COMPLETE
```

A hint request outside the supported assistance states is invalid.

## TutorAI behavior

Extend `TutorAI.continue_turn(...)` with a typed intent argument while preserving the existing call shape through a default:

```python
intent: TutorReplyIntent = TutorReplyIntent.ATTEMPT
```

Equivalent naming is acceptable.

### ATTEMPT intent

Existing behavior must remain unchanged:

- model may return `likely_correct=True` -> deterministic correctness transition;
- model may return `likely_correct=False` -> deterministic incorrect-attempt transition;
- `likely_correct=None` -> retain current state.

### HINT_REQUEST intent

For a hint request:

1. derive the next assistance state with:
   ```text
   current_state + HINT_REQUESTED
   ```
2. generate assistance appropriate to that new state;
3. normalize the returned turn to exactly that new state;
4. set `hint_level` from the resulting state mapping;
5. do not allow model `likely_correct` to advance the state again.

Example:

```text
current state: ask_attempt
intent: hint_request
target generation state: hint_1
returned/persisted state: hint_1
hint_level: 1
```

Even if the model returns:

```text
likely_correct=False
```

the same request must not jump directly to `hint_2`.

Likewise:

```text
hint_1 + hint_request -> hint_2
```

must produce exactly `hint_2`, not `explain_step`.

## Generation policy

For `hint_request`, use the generation policy for the target assistance state.

Examples:

```text
ask_attempt + hint_request
=> generate with HINT_1 policy

hint_1 + hint_request
=> generate with HINT_2 policy

hint_2 + hint_request
=> generate with EXPLAIN_STEP policy
```

Do not ask the LLM to choose whether a hint should advance.

The application chooses the target state deterministically first.

## Demo/no-client behavior

The existing no-client/demo path must also obey deterministic hint-request progression.

For example:

```text
ASK_ATTEMPT + HINT_REQUEST
=> returned state HINT_1
=> hint_level 1
```

No network should be required to test this.

The actual demo text may remain simple and generic.

## API behavior

`POST /tutor/reply` must pass:

```text
payload.intent
```

to `TutorAI.continue_turn(...)`.

The route continues to:

- load the owned session;
- validate persisted TutorState;
- load conversation history;
- persist the student message;
- call TutorAI;
- run the existing answer-leakage guard;
- persist returned tutor state;
- persist returned tutor message;
- commit;
- return `TutorReplyResponse`.

Do not create a separate `/hint` endpoint.

## Invalid hint request state

If `intent=hint_request` is received while the persisted state is outside:

```text
ask_attempt
hint_1
hint_2
```

the API must fail clearly and must not silently reinterpret the request as an attempt.

Preferred behavior:

```text
HTTP 409 Conflict
```

with a stable detail such as:

```text
Hint request is unavailable in the current tutor state
```

Equivalent explicit 4xx behavior is acceptable if documented in tests.

Do not return 500 for a normal client request that is invalid for the current tutor state.

Do not call the LLM when the hint request is invalid.

Do not persist the user message for an invalid hint request.

## State ownership

The server remains authoritative for tutor state.

The client sends:

```text
intent = hint_request
```

not:

```text
state = hint_1
```

The client must never choose the target state directly.

## Mastery separation

M10-02A must not:

- call `record_mastery_evidence`;
- call `/tutor/attempt`;
- create a mastery row;
- increment mastery exposures;
- change streak;
- infer correctness from hint request.

A hint request is assistance intent only.

## Misconception separation

M10-02A must not:

- create confirmed misconception evidence;
- turn free-text misconception fields into trusted evidence;
- infer a misconception merely because help was requested.

## Answer-leakage guard

The existing runtime leakage guard remains unchanged and still applies to tutor messages generated for hint requests.

Do not bypass:

```python
_guard_tutor_turn(...)
```

Do not modify `answer_leakage.py`.

## Required tests

Cover at least:

1. `TutorReplyRequest` defaults intent to `attempt`;
2. explicit `"hint_request"` parses to the typed intent;
3. unknown reply intent is rejected by schema;
4. `ASK_ATTEMPT + HINT_REQUESTED -> HINT_1`;
5. `HINT_1 + HINT_REQUESTED -> HINT_2`;
6. `HINT_2 + HINT_REQUESTED -> EXPLAIN_STEP`;
7. unsupported hint transition fails explicitly;
8. normal attempt transition behavior remains unchanged;
9. no-client TutorAI hint request from `ASK_ATTEMPT` returns `HINT_1`;
10. no-client TutorAI hint request from `HINT_1` returns `HINT_2`;
11. no-client TutorAI hint request from `HINT_2` returns `EXPLAIN_STEP`;
12. hint request sets the correct normalized `hint_level`;
13. model-provided state cannot override deterministic hint target;
14. model `likely_correct=False` during hint request does not double-escalate;
15. model `likely_correct=True` during hint request does not jump to `VERIFY`;
16. API passes `hint_request` intent to TutorAI;
17. API persists state returned for a valid hint request;
18. API default attempt request remains backward compatible;
19. invalid-state hint request returns explicit 4xx;
20. invalid-state hint request does not call TutorAI;
21. invalid-state hint request does not persist the new user message.

Add any additional narrow regression needed for correctness.

## Backward compatibility

These existing call forms must continue working:

```python
TutorReplyRequest(
    session_id=1,
    student_message="x = 4",
)
```

and existing direct TutorAI calls that omit intent:

```python
continue_turn(
    problem,
    skill,
    history,
    student_message,
    current_state=TutorState.ASK_ATTEMPT,
)
```

They must retain attempt semantics.

## Acceptance criteria

M10-02A is complete when:

- typed `attempt | hint_request` reply intent exists;
- reply intent defaults to `attempt`;
- `HINT_REQUESTED` is a separate transition event;
- deterministic hint progression is:
  - `ask_attempt -> hint_1`
  - `hint_1 -> hint_2`
  - `hint_2 -> explain_step`
- hint request does not depend on model correctness judgment;
- one hint request advances at most one assistance level;
- TutorAI generates using the target assistance state's policy;
- server remains authoritative for state;
- API persists valid hint-request state;
- invalid-state hint request is explicit 4xx;
- invalid-state hint request does not call AI or persist the request;
- existing attempt behavior remains compatible;
- answer-leakage guard still applies;
- no mastery mutation is added;
- no misconception evidence is added;
- no frontend changes;
- no new endpoint;
- no DB migration;
- no new dependency;
- focused tests pass;
- full backend regression passes.
