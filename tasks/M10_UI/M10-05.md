# M10-05 — Add minimal pilot PRE → learning → POST UI

Status: DONE
Codex: Yes, small
Module: UI
Phase: Phase 3 pilot readiness

## Goal

Add the smallest learner-facing pilot UI that composes the existing trusted backend enrollment, PRE assessment, exact pilot-learning, POST assessment, and completion flow. The frontend presents server state and submits learner input; the backend remains the authority for pilot phase, assignment identity, current assessment item, correctness, progression, TRANSFER, and eligibility.

## Context

The trusted pilot endpoints already exist. M10-05 connects them in the existing `frontend/app/page.tsx` without moving assignment selection, assessment correctness, or progression into the client. Generic tutoring and recommendation behavior remains intact.

## Backend authority

Use unchanged endpoints:

- `POST /students/{student_id}/pilot` — explicit enrollment, no body.
- `GET /students/{student_id}/pilot` — authoritative phase and progress; 404 means no enrollment.
- `GET /students/{student_id}/pilot/assessment` and `POST /students/{student_id}/pilot/assessment` — server-selected PRE/POST item and assessment submission.
- `POST /tutor/start-pilot-learning/{student_id}` — server-selected exact frozen learning item, no body.
- `POST /tutor/reply` — existing tutor progression.

Never use `/tutor/start-authored` for pilot learning. Do not derive phase, choose questions/assignments, or determine correctness in the frontend.

## Frontend state boundary

Keep pilot-specific state local to `page.tsx`: typed pilot status and current learner-safe assessment item, in-memory candidate text, loading/error presentation, and `pilotSessionStudentId` provenance. The latter identifies which student owns the current pilot tutor session; it is not assignment authority. Guard asynchronous reads so an old selected student's response cannot replace the current student's panel.

## Enrollment flow

Enrollment is an explicit user action only. A 404 status response is rendered as no existing pilot and offers a start button; it never triggers enrollment automatically. On click, POST to the selected student's pilot endpoint with no request body, use the returned status, and load the current PRE item. Do not expose a re-enrollment/reset flow or display `pilot_id`.

## PRE/POST flow

Render phase and all three progress counters from server status. In PRE/POST, fetch and display only problem text, skill code, difficulty, and phase/progress. Keep `question_id` opaque and use only the current server-returned ID in a submission body containing exactly `question_id` and `candidate`. Handle 204 without parsing JSON. After successful submission, show only neutral acknowledgement, clear the candidate, and reload status/current item; do not reveal correctness, solutions, or expected answers. Submission errors preserve the current item and candidate for retry.

## Intervention flow

When server phase is `intervention`, offer an explicit start action. POST to `/tutor/start-pilot-learning/{student_id}` with no body or assignment/question metadata. On success, install the returned session ID, tutor turn, and server-returned question as the new tutor presentation; bind both session identity and pilot provenance to that student, and clear stale analysis, reply, recommendation, and image presentation. Prevent an obvious duplicate start when that selected student already owns an in-progress pilot tutor session.

## Generic-vs-pilot tutor boundary

Pilot turns continue through `/tutor/reply`. For a pilot session, ignore `next_learning_action` as pilot-start authority and never pass it to `/tutor/start-authored`; on COMPLETE, reload pilot status only if the completed pilot session owner is still selected. Generic tutor recommendations retain their existing `/tutor/start-authored` behavior. Clear pilot-session provenance on successful normal free-form start, successful generic authored start, `Bài mới`, and logout.

## Assessment feedback boundary

Assessment submission's 204 response carries no correctness result. The UI must not display correct/incorrect feedback, a solution, or an expected answer. Discover PRE→intervention and POST→complete only from refreshed server status. COMPLETE uses neutral wording and does not imply learner improvement, pilot success, or Phase 3 exit.

## Privacy boundary

Never request or display assignment seeds, expected answers, verifier references/metadata, frozen assignment lists, or assignment IDs. Do not display question IDs. Candidate text exists only in current React state and the submission request; do not store it in browser storage, URLs, analytics, or logs. Use no new analytics or live correctness authority.
