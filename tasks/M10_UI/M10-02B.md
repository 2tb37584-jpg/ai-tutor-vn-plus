# M10-02B — Student Attempt + Hint Controls

Status: ACTIVE
Codex: YES

## Goal

Make the tutor conversation UI distinguish two student intents:

1. submitting an attempt;
2. explicitly requesting more help.

Both intents continue to use:

```text
POST /tutor/reply
```

The UI must use the backend contract introduced by M10-02A:

```text
attempt
hint_request
```

This task is UI-only.

## Product rule

The UI must not treat “Xin gợi ý” as an incorrect answer.

Do not:

- call `/tutor/attempt`;
- send `correct=false`;
- infer mastery from requesting help;
- infer a misconception from requesting help;
- choose the next tutor state in the browser.

The browser sends only the intent.

The backend remains authoritative for:

- tutor state;
- hint progression;
- correctness judgment;
- answer-leakage protection.

## Current baseline

The conversation shell already:

- starts a tutor session;
- stores full public `TutorTurn` metadata;
- displays tutor/student bubbles;
- displays tutor state;
- displays non-zero `hint_level`;
- displays public skill tags;
- disables reply input while busy;
- supports “Bài mới”.

The current reply form sends:

```json
{
  "session_id": "...",
  "student_message": "..."
}
```

Because `intent` defaults to `attempt`, this remains backward-compatible, but M10-02B should make the UI intent explicit.

## Backend contract available

M10-02A added:

```text
TutorReplyIntent.ATTEMPT = "attempt"
TutorReplyIntent.HINT_REQUEST = "hint_request"
```

Deterministic hint progression:

```text
ask_attempt + hint_request -> hint_1
hint_1      + hint_request -> hint_2
hint_2      + hint_request -> explain_step
```

Hint requests are invalid outside:

```text
ask_attempt
hint_1
hint_2
```

The backend returns HTTP 409 for unsupported hint requests.

## Module / micro-task

Module:

`M10 Tutor UI`

Micro-task:

1. type the frontend tutor reply intent;
2. send explicit `attempt` for normal replies;
3. add a dedicated hint-request control;
4. allow hint requests only in eligible tutor states;
5. append the resulting conversation exactly once;
6. preserve existing busy/error/new-problem behavior.

## Frontend reply intent type

Add a frontend type equivalent to:

```ts
type TutorReplyIntent = "attempt" | "hint_request";
```

Do not expose internal transition events such as `HINT_REQUESTED` to the UI.

The UI sends user intent only.

## Shared reply submission

Avoid duplicating fetch/persistence UI logic between:

- normal attempt submit;
- hint button.

Prefer one shared helper equivalent to:

```ts
submitTutorReply(studentText, intent)
```

The helper should:

1. require an active `sessionId`;
2. refuse duplicate submission while `busy`;
3. append exactly one student message locally;
4. set busy state;
5. POST `/tutor/reply`;
6. include:
   - `session_id`;
   - `student_message`;
   - `intent`;
7. append exactly one tutor response;
8. surface request errors through the existing status area;
9. clear busy in `finally`.

Equivalent structure is acceptable.

## Normal attempt behavior

Submitting the existing text input must send:

```json
{
  "session_id": 123,
  "student_message": "<typed text>",
  "intent": "attempt"
}
```

The current form still represents the student's own reasoning, calculation, or next step.

Preserve:

- trimmed input;
- empty-input prevention;
- busy disabling;
- existing placeholder unless a small clarity improvement is useful.

After submission:

- clear the input;
- append one student bubble;
- append one tutor bubble.

Do not call `/tutor/attempt`.

## Hint-request control

Add a dedicated button in the active tutor conversation area.

Suggested visible label:

```text
Xin gợi ý
```

A small state-sensitive label is acceptable, but keep the interaction simple.

When clicked, send:

```json
{
  "session_id": 123,
  "student_message": "Em muốn xin thêm một gợi ý.",
  "intent": "hint_request"
}
```

Equivalent natural Vietnamese wording is acceptable.

The sent text should also appear as the student's conversation bubble so the UI matches the server-side conversation history.

Do not send empty text for a hint request because the backend schema requires a non-empty `student_message`.

## Hint eligibility

Derive hint availability from the latest server-returned tutor turn.

Hint request is eligible only while:

```text
ask_attempt
hint_1
hint_2
```

Use the existing derived `latestTutorTurn`.

Do not create a second duplicated tutor-state store.

Equivalent logic:

```ts
const canRequestHint =
  latestTutorTurn !== null &&
  ["ask_attempt", "hint_1", "hint_2"].includes(latestTutorTurn.state);
```

A typed helper/set is preferable if clear.

When state is:

```text
diagnose
explain_step
verify
transfer
complete
```

the hint button should not be actionable.

Prefer hiding the hint button outside eligible states rather than letting the user trigger a known 409.

If you keep it visible, it must be disabled and clearly non-actionable.

## Busy behavior

While a tutor request is in flight:

- normal input is disabled;
- normal submit button is disabled;
- hint button is disabled;
- no second attempt/hint request can be started;
- existing `role="status"` / `aria-live` behavior remains.

Do not introduce parallel tutor reply requests.

## Error behavior

If a request fails:

- keep using the existing status/error area;
- do not append a fake tutor response;
- do not fabricate state progression;
- do not retry automatically.

If a hint request unexpectedly receives backend 409 because state changed, surface the backend error through the existing API/error mechanism.

Do not work around it in the client by selecting another state.

## Conversation consistency

For each successful attempt:

```text
1 student bubble
1 tutor bubble
```

For each successful hint request:

```text
1 student bubble
1 tutor bubble
```

Do not append the tutor response twice.

Do not create a separate “system” bubble for hint requests.

## State display

Continue using the server-returned:

```text
tutor.state
tutor.hint_level
tutor.skill_tags
```

The existing latest-state indicator must update after a successful hint request.

Expected examples:

```text
ask_attempt
-- Xin gợi ý -->
hint_1 / Mức gợi ý 1

hint_1
-- Xin gợi ý -->
hint_2 / Mức gợi ý 2

hint_2
-- Xin gợi ý -->
explain_step / Mức gợi ý 3
```

Do not calculate `hint_level` in the browser.

## Internal metadata

Continue NOT rendering internal/sensitive fields merely because they exist on `TutorTurn`.

Do not newly expose:

- `misconception`;
- `likely_correct`;
- `reveal_final_answer`;
- expected answers;
- verification notes;
- internal transition events.

## Accessibility / interaction

The hint button must:

- be a real `<button>`;
- use `type="button"` if placed inside/near a form and not intended to submit it;
- be disabled while busy;
- have visible text;
- work via keyboard activation.

Preserve semantic form submission for normal attempts.

## Styling

Keep styling minimal and consistent with the existing conversation shell.

A small control row is sufficient.

For example:

```text
[ reply input................ ] [ Gửi ]
[ Xin gợi ý ]                  [ Bài mới ]
```

Equivalent compact layout is acceptable.

Do not redesign unrelated sections.

Do not reintroduce the prior `.tutor` selector collision. If styling the tutor card, keep selectors scoped.

## Acceptance criteria

M10-02B is complete when:

- frontend has typed `attempt | hint_request`;
- normal text submit explicitly sends `intent: "attempt"`;
- hint control explicitly sends `intent: "hint_request"`;
- hint request sends non-empty natural-language `student_message`;
- hint request uses `/tutor/reply`, not `/tutor/attempt`;
- hint availability is derived from `latestTutorTurn.state`;
- hint is available in:
  - `ask_attempt`
  - `hint_1`
  - `hint_2`;
- hint is non-actionable outside those states;
- browser never chooses the next tutor state;
- browser never computes hint level;
- one successful action appends one student + one tutor bubble;
- busy blocks both attempt and hint actions;
- latest tutor state updates from server response;
- public hint level remains visible when `> 0`;
- no internal metadata is newly exposed;
- “Bài mới” behavior remains intact;
- no backend changes;
- no dependency changes;
- `npm run lint` passes;
- `npm run build` passes;
- manual smoke checks pass.

## Manual smoke checks

Run the app with the M10-02A backend.

### Smoke 1 — normal attempt

Start a tutor session.

Type a student attempt and press `Gửi`.

Verify:

- exactly one student bubble appears;
- exactly one tutor bubble appears;
- no hint-specific UI side effect occurs;
- request succeeds.

### Smoke 2 — first explicit hint

From `ask_attempt`, click `Xin gợi ý`.

Verify:

- one student hint-request bubble appears;
- one tutor bubble appears;
- latest state becomes `hint_1`;
- `Mức gợi ý 1` is visible.

### Smoke 3 — second explicit hint

Click `Xin gợi ý` again from `hint_1`.

Verify:

- latest state becomes `hint_2`;
- `Mức gợi ý 2` is visible;
- conversation appends exactly once.

### Smoke 4 — third explicit hint

Click `Xin gợi ý` from `hint_2`.

Verify:

- latest state becomes `explain_step`;
- `Mức gợi ý 3` is visible;
- hint control becomes non-actionable/hidden after the response.

### Smoke 5 — busy protection

Throttle the network if needed.

Trigger an attempt or hint request.

While busy verify:

- input disabled;
- Gửi disabled;
- Xin gợi ý disabled;
- a second tutor request cannot be initiated;
- existing busy status is visible.

### Smoke 6 — Bài mới

Click `Bài mới`.

Verify:

- conversation/session UI resets as before;
- auth/student context remains;
- hint control is not active without a current tutor turn.
