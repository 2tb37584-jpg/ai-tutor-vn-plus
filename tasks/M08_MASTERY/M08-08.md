# M08-08 — Define Post-Completion Next-Learning-Action Delivery Contract

Status: DONE
Codex: NO
Module: Mastery / Adaptive Learning

## Goal

Define how the internal next-learning-action recommendation produced by M08-07 should be delivered to the product after a tutor session completes.

This is a design/decomposition task only.

Do not modify product code in this task.

## Context

M08-07 is DONE and provides an internal application seam:

```text
TutorState.COMPLETE
→ load current student Mastery rows
→ map to MasterySnapshot
→ recommend_next_question(...)
→ QuestionBankItem | None
```

The current public tutor response remains:

```python
class TutorReplyResponse(BaseModel):
    tutor: TutorTurn
```

The current frontend consumes only:

```text
data.tutor
```

No public next-learning-action payload exists.

The tutor runtime now has a reliable deterministic completion path:

```text
TRANSFER
+ deterministic CORRECT
→ TRANSFER_COMPLETED
→ COMPLETE
```

The current `/tutor/reply` request is therefore the natural point where completion becomes known.

There is still no lifecycle contract for starting a new tutor session from a recommended authored question.

That start lifecycle must not be invented implicitly inside this delivery task.

## Design decision

### Delivery boundary

Expose the next learning recommendation as an optional structured field on `TutorReplyResponse`.

Do not create a separate read endpoint for the first delivery integration.

Rationale:

- the completion transition already occurs during `/tutor/reply`;
- the latest transfer mastery evidence is available in the same transaction;
- M08-07 can read the flushed current mastery state before commit;
- the frontend already consumes the completion reply;
- an inline optional field avoids an extra request and avoids recomputing recommendation after the fact;
- recommendation remains a result of the completion transition, not a general session query.

### Trigger

Recommendation must run only on the transition into `COMPLETE` in the current request:

```python
current_state is not TutorState.COMPLETE
and tutor_turn.state is TutorState.COMPLETE
```

With the current state machine this is expected to be:

```text
TRANSFER -> COMPLETE
```

Do not run recommendation merely because a loaded session is already `COMPLETE`.

Do not run recommendation on:

```text
ASK_ATTEMPT
HINT_1
HINT_2
EXPLAIN_STEP
VERIFY
TRANSFER entry
ordinary mastery update
```

This avoids duplicate/repeated recommendation work if a completed session is queried or a future route reuses the session.

### Internal caller

`backend/app/api/tutor.py` remains orchestration-only.

After authoritative tutor state has been determined and before commit, it may call:

```text
recommend_next_learning_question(...)
```

from M08-07.

The route must not contain recommendation ranking logic or ORM-to-MasterySnapshot mapping.

### Public projection

Do not expose the full internal `QuestionBankItem`.

Define a dedicated public projection containing only learner-safe fields.

Recommended shape:

```python
class NextLearningAction(BaseModel):
    question_id: str
    skill_code: str
    problem_text: str
    difficulty: int
```

Then:

```python
class TutorReplyResponse(BaseModel):
    tutor: TutorTurn
    next_learning_action: NextLearningAction | None = None
```

Do not expose:

```text
expected_answer
verification_reference
verification_family
internal verifier metadata
```

These are internal correctness/answer data and must remain private.

### No-eligible behavior

When M08-07 returns:

```text
None
```

the public response returns:

```text
next_learning_action = None
```

The tutor reply still succeeds.

No HTTP error is produced solely because no next question is eligible.

### Transaction ordering

For the completion request:

```text
record deterministic transfer mastery evidence
→ authoritative state becomes COMPLETE
→ invoke M08-07 next-learning-action seam
→ project QuestionBankItem to learner-safe NextLearningAction
→ persist assistant message/session state
→ commit
→ return TutorReplyResponse
```

M08-07 owns flushing before its mastery read.

Do not add another recommendation-specific commit.

### Persistence

Do not persist the recommendation in this delivery task.

No recommendation-history table or TutorSession field is required.

The recommendation is an ephemeral response derived from current mastery and the deterministic question bank.

If product requirements later require resume/history/audit of recommended actions, that must be a separate persistence decision.

### Frontend consumer

The frontend may consume `next_learning_action` only after the completion reply.

The first UI behavior should be presentation-only:

```text
session completes
→ show "Bài tiếp theo" card with problem text / skill / difficulty
```

Do not automatically replace the current session.

Do not automatically submit the recommended problem to `/tutor/start`.

### Separate authored-start lifecycle

Starting a new tutoring session from the recommended authored question is a separate contract.

The current:

```python
StartTutorRequest(
    student_id,
    problem_text,
    image_data_url,
)
```

does not preserve the selected authored question identity.

Sending only `problem_text` back through `/tutor/start` would re-run model analysis and could lose:

```text
exact question_id
authored skill identity
authored expected answer
authored verifier family
authored difficulty
```

Therefore the frontend must not treat `problem_text` alone as an exact authored-start contract.

A later task must define a safe authored-question start path, likely using `question_id` as trusted server-side lookup input.

That later task must preserve the answer/verifier trust boundary and must not accept client-supplied expected answers.

## API/schema impact

A public schema change is required for delivery:

```text
TutorReplyResponse.next_learning_action
```

with a learner-safe projection model.

This is now justified because there is a real frontend consumer point after COMPLETE.

No change is required to:

```text
TutorTurn
StartTutorResponse
TutorSession ORM model
database schema
```

for delivery alone.

## Implementation decomposition

Do not combine backend delivery and authored-session start in one task.

### Task A — M08-09 Backend Next-Learning-Action Delivery

Goal:

Wire the M08-07 seam into the completion reply and expose a learner-safe optional response field.

Likely files:

```text

backend/tests/test_tutor_api_state.py
```

Optionally one dedicated API-schema test file if necessary.

Expected scope: 3–4 files.

### Task B — M10-03 Render Post-Completion Next Learning Action

Goal:

Render `next_learning_action` after COMPLETE.

Likely files:

```text
frontend/app/page.tsx
frontend tests if present
```

Presentation only.

Do not start a new session automatically.

### Task C — future authored-question start contract

Goal:

Define and then implement starting a fresh tutor session from a trusted authored `question_id`.

This must be a separate design/implementation sequence because it affects:

```text
session initialization
analysis trust boundary
expected-answer source
verification-family source
question identity
frontend action
```

Do not fold it into M08-09 or M10-03.

## Required tests for M08-09

The follow-on backend implementation must cover:

```text
TRANSFER -> COMPLETE
→ M08-07 seam called exactly once

```

Use fixed time in tests by monkeypatching/injecting the existing route clock seam.

Do not require live model calls.

## Risks

### Answer leakage

`QuestionBankItem` contains internal correctness metadata.

Never serialize the internal dataclass directly into the public response.

Use an explicit learner-safe projection.

### Duplicate recommendation

Triggering on:

```text
session.current_state == COMPLETE
```

alone would recompute recommendations on repeated completed-session interactions.

Trigger on the transition into COMPLETE in the current request instead.

### Authored identity loss

Passing the recommended `problem_text` back into the existing generic `/tutor/start` route would lose the deterministic authored identity and verifier trust boundary.

Do not use that as the exact start contract.

### Scope expansion

Do not combine:

```text
backend delivery
frontend display
new-session authored start
recommendation persistence/history
```

into one implementation ticket.

## Review evidence

Repository inspection supporting this design decision:

- `TutorReplyResponse` currently contains only `tutor: TutorTurn`.
- `/tutor/reply` is the runtime point where deterministic `TRANSFER -> COMPLETE` occurs.
- The frontend currently consumes only `data.tutor` from `/tutor/reply`.
- No existing public next-learning-action payload exists.
- No existing runtime consumer starts a new tutor session from a recommended `QuestionBankItem`.
- Existing `/tutor/start` accepts free-form `problem_text` / image input rather than a trusted authored `question_id`.
- Reusing only `problem_text` for a recommended authored item would lose the exact authored question identity and its trusted expected-answer/verifier context.

Design conclusion:

```text
M08-09
→ expose optional learner-safe next_learning_action on completion reply

M10-03
→ render it after COMPLETE

future authored-start contract
→ start a fresh session from trusted server-side question_id lookup
```

No product code was changed for M08-08.

## Stop conditions

Stop and reassess if:

- exposing the safe recommendation requires persistence;
- the existing completion request cannot call M08-07 before commit;
- learner-safe projection cannot avoid internal answer/verifier data;
- frontend consumption would require starting the new session in the same task;
- backend implementation exceeds 4 files.
