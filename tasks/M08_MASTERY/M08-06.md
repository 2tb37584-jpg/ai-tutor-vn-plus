## Integration decision

### Caller

The global next-best-question recommender belongs at the application/service boundary after a tutor session has actually reached `TutorState.COMPLETE`.

It must not be called from `TutorAI`, ORM models, or from inside `question_recommender.py`.

### Input adapter

Load existing `Mastery` rows for the session student and map each row directly to:

```python
MasterySnapshot(
    skill_code=mastery.skill_code,
    probability=mastery.probability,
    exposures=mastery.exposures,
    last_seen_at=mastery.last_seen_at,
)
```

No new persistence model is required.

### Clock ownership

The application caller owns the clock and creates one `now` value for the recommendation operation.

The caller injects that value into `recommend_next_question(...)`.

The recommender remains free of runtime clock calls.

### Trigger

Recommendation runs only after the current tutor session has actually completed.

It must not run merely because:

- mastery was updated;
- an attempt was correct;
- the tutor entered `VERIFY`;
- the tutor entered `TRANSFER`.

`TRANSFER` means applying the current learned idea to a related case. The global recommender may intentionally select a different due, unseen, or lower-mastery skill, so it is not a transfer-question generator.

### Output consumer

A next-learning-action application seam consumes the selected `QuestionBankItem` after session completion.

The selected question is the candidate for the learner's next learning activity, not a replacement for the current session's transfer exercise.

Do not put recommendation responsibility into `TutorAI`.

Do not mutate the current `TutorSession` into the recommended question without a separate lifecycle decision.

### Failure behavior

`question_recommender.py` keeps its existing pure contract and may raise `ValueError` when no eligible question-bank skill exists.

The application integration boundary must translate that condition into a non-fatal "no next question available" result rather than failing the tutor request.

### API/schema impact

No public tutor API/schema change is required for the first internal integration seam.

Do not add `QuestionBankItem` to `TutorTurn` or `TutorReplyResponse` speculatively.

If the frontend later needs a structured next-question payload, define that in a separate API/schema task with tests.

### Persistence impact

None.

Existing `Mastery` rows already provide:

- `skill_code`
- `probability`
- `exposures`
- `last_seen_at`

No table, model, migration, or recommendation-history persistence is required.

### Discovered lifecycle gap

The deterministic state model defines:

```text
VERIFY -> TRANSFER -> COMPLETE
```

but the current application runtime does not emit `TRANSFER_COMPLETED`.

Repository search found `TRANSFER_COMPLETED` only in schema/state-machine/tests, not in the tutor application flow.

Therefore `TutorState.COMPLETE` is not yet a reliable runtime integration seam.

### Follow-on decomposition

Do not implement recommendation integration as one combined ticket.

Split it into two micro-tasks.

#### Task A — make transfer completion explicit

Goal:

Provide an explicit, testable runtime path from `TRANSFER` to `COMPLETE`.

Likely scope:

```text
backend/app/api/tutor.py
backend/app/services/tutor_ai.py and/or tutor-state orchestration seam
relevant targeted tests
```

Keep this task focused on tutor lifecycle semantics. Do not add next-best-question recommendation to it.

#### Task B — integrate next learning recommendation after COMPLETE

Goal:

After a session reaches `COMPLETE`, load current mastery snapshots and call `recommend_next_question(...)` through a small application/service integration seam.

Likely scope:

```text
one small recommendation integration service
backend/app/api/tutor.py or the eventual completion caller
targeted integration tests
```

Prefer 2–4 files.

Do not modify `question_recommender.py` unless a separately reviewed contract defect is discovered.

### Tests required

Task A:

- valid transfer completion reaches `COMPLETE`;
- incomplete/invalid transfer does not complete early;
- existing tutor-state tests remain green.

Task B:

- ORM mastery maps exactly to `MasterySnapshot`;
- latest flushed mastery is visible to recommendation in the same transaction;
- recommendation is called only after `COMPLETE`;
- recommendation is not called on ordinary mastery update, `VERIFY`, or entry to `TRANSFER`;
- no eligible question is handled without crashing the tutor flow;
- no DB dependency is introduced into `question_recommender.py`;
- fixed time is injected in deterministic tests.

### Risks

- Treating the global recommender as a transfer-question generator would conflate two different pedagogical policies.
- Replacing the current session problem with a recommended question would invalidate existing `primary_skill`, expected-answer, and verifier-family lifecycle assumptions.
- Putting DB access in `TutorAI` would mix generation with learning-state orchestration.
- Adding public API fields before a real consumer exists would expand scope unnecessarily.
