# M08-06 — Define Next-Best-Question Integration Contract

Status: ACTIVE
Codex: NO
Module: Mastery / Adaptive Learning

## Goal

Define the smallest integration contract that connects the deterministic next-best-question recommender to the existing learning flow.

This is a design/decomposition task only.

Do not modify product code in this task.

## Context

M08-05 is DONE and provides:

- `MasterySnapshot`
- `recommend_next_question(...)`
- deterministic prerequisite gating
- spaced-review priority
- authored-difficulty selection

The recommender is currently a pure service with:

- no DB access
- no API
- no persistence
- no runtime clock
- no LLM
- no randomization

The next step is to determine where it belongs in the existing learning loop before implementing integration.

Target learning flow:

```text
student evidence
→ mastery update
→ persisted/current mastery state
→ recommendation input adapter
→ recommend_next_question(...)
→ next learning action
```

## Design questions

Determine and document:

1. Which existing module should call `recommend_next_question(...)`.
2. How existing mastery state should be converted into `MasterySnapshot`.
3. Where caller-injected `now` should originate.
4. When recommendation should run in the tutor/session lifecycle.
5. Which component consumes the selected `QuestionBankItem`.
6. What should happen when no question-bank skill is eligible.
7. Whether the integration can remain internal or requires an API/schema change.
8. Which deterministic tests are required for the integration seam.
9. The smallest follow-on implementation scope, ideally 2–6 files.

## Inspection scope

Inspect only the minimum files required to answer the design questions.

Prefer existing seams around:

```text
backend/app/services/question_recommender.py
backend/app/services/mastery.py
Tutor orchestration/service code
existing mastery persistence/model contract
relevant tutor/session schemas only if required
```

Do not ask Codex to explore the whole repository.

## Forbidden scope

Do not:

- modify product code
- modify database schema
- add migrations
- add dependencies
- add API fields speculatively
- add persistence
- add a new ranking/scoring framework
- add BKT/IRT
- add LLM recommendation
- add randomization
- refactor unrelated tutor/mastery code
- create the implementation task until the integration boundary is understood

## Architecture constraints

Keep the modular monolith.

Prefer composition of existing services over a new subsystem.

Generation and deterministic policy must remain separate.

Do not move recommendation logic into ORM models or API routes.

Do not introduce an abstraction layer unless the integration actually requires it.

## Stop conditions

Stop and split the work if:

- integration requires more than 6 implementation files;
- a public API/schema change becomes necessary;
