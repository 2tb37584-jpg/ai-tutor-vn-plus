# M08-02 — Implement v1 Mastery Update

Status: DONE
Codex: YES

## Goal

Implement the v1 mastery evidence gate defined by M08-01.

Mastery may change only from server-side evidence that is explicitly eligible under the mastery event contract.

The current `/tutor/attempt` endpoint must stop treating the client-provided `correct` boolean as authoritative mastery evidence.

## Context

M08-01 established these trust rules:

- a client correctness claim alone must not mutate mastery;
- a single unverified LLM judgment alone must not mutate mastery;
- only controlled mastery-bearing skills may mutate mastery;
- unknown/reserved skills must never create mastery rows;
- verification must be explicit;
- `outcome=unknown` is not mastery-bearing;
- unverified/unsupported/disputed evidence is not mastery-bearing;
- exposures and correct streak change only when an eligible event is actually applied.

Current runtime behavior violates that contract:

```python
@router.post("/attempt")
def save_attempt(...):
    ...
    attempt = Attempt(**payload.model_dump())
    db.add(attempt)
    update = record_attempt(
        db,
        student_id=payload.student_id,
        skill_code=payload.skill_code,
        correct=payload.correct,
        hint_count=payload.hint_count,
    )
```

`AttemptRequest.correct` is client-controlled.

M08-02 must close this trust-boundary gap.

## Module / micro-task

Module:

`M08 Mastery`

Micro-task:

1. add a typed server-side mastery evidence contract in the mastery service;
2. add deterministic eligibility gating;
3. apply probability/exposure/streak changes only for eligible verified evidence;
4. keep the current `/tutor/attempt` route as attempt logging, but do not let its client claim mutate mastery;
5. make the API response explicitly report that mastery was not updated from the client claim.

Do not wire TutorAI or verifier routing into mastery in this task.

## Mastery evidence types

Implement typed values equivalent to:

```python
class MasteryOutcome(str, Enum):
    CORRECT = "correct"
    INCORRECT = "incorrect"
    UNKNOWN = "unknown"


class MasteryEvidenceType(str, Enum):
    DETERMINISTIC_VERIFICATION = "deterministic_verification"
    VERIFIED_TRANSFER = "verified_transfer"
    CONFIRMED_MISCONCEPTION = "confirmed_misconception"
    LLM_JUDGMENT = "llm_judgment"
    CLIENT_CLAIM = "client_claim"


class VerificationStatus(str, Enum):
    VERIFIED = "verified"
    UNVERIFIED = "unverified"
    UNSUPPORTED = "unsupported"
    DISPUTED = "disputed"
```

Names may differ slightly, but semantics must remain explicit.

## MasteryEvidenceEvent

Add a frozen typed structure equivalent to:

```python
@dataclass(frozen=True)
class MasteryEvidenceEvent:
    student_id: int
    session_id: int | None
    skill_code: str
    outcome: MasteryOutcome
    evidence_type: MasteryEvidenceType
    verification_status: VerificationStatus
    verification_method: str | None = None
    confidence: float = 1.0
    hint_count: int = 0
    misconception_code: str | None = None
    is_transfer: bool = False
```

This is an internal server-side business object.

Do not accept it directly from client input in M08-02.

## Input validation

The mastery service must reject/invalidate events where:

- `confidence < 0` or `confidence > 1`;
- `hint_count < 0`;
- `student_id` is invalid for the service contract;
- skill cannot resolve to a controlled mastery-bearing skill.

Validation may return an ineligible decision rather than raising for normal trust failures.

Programmer/type errors may still raise where appropriate.

## Canonical skill handling

Use the controlled skill registry.

Before an event is eligible:

1. resolve `event.skill_code` with `resolve_skill_code(...)`;
2. require a canonical result other than `UNKNOWN_SKILL_CODE`;
3. require `is_mastery_bearing_skill(canonical_code)`.

Unknown or reserved labels must:

- be ineligible;
- not create a `Mastery` row;
- not increment exposures;
- not modify correct streak.

Reviewed aliases may resolve to their canonical skill before persistence.

## v1 eligibility rule

An event is mastery-eligible only when all of these are true:

1. canonical skill is mastery-bearing;
2. `verification_status == VERIFIED`;
3. outcome is `CORRECT` or `INCORRECT`;
4. evidence type is one of:
   - `DETERMINISTIC_VERIFICATION`
   - `VERIFIED_TRANSFER`
5. the event is not otherwise invalid.

The following are never eligible by themselves:

- `CLIENT_CLAIM`;
- `LLM_JUDGMENT`;
- `CONFIRMED_MISCONCEPTION`;
- `UNVERIFIED`;
- `UNSUPPORTED`;
- `DISPUTED`;
- `UNKNOWN` outcome.

Confidence alone must never make an otherwise ineligible event eligible.

## Confidence rule

For v1:

- validate confidence is in `[0.0, 1.0]`;
- do not use confidence as a shortcut around verification/source eligibility;
- do not add arbitrary probability weighting based on confidence in M08-02.

A deterministic verified event with a valid confidence remains eligible because of its source and verification status, not because confidence is high.

Future confidence weighting may be introduced only with explicit evaluation evidence.

## Hint rule

Keep the existing transparent probability heuristic:

```python
update_probability(old, correct, hint_count)
```

For eligible evidence:

- correct evidence may receive less positive credit when more hints were used;
- incorrect evidence remains incorrect;
- hints alone never create an event or decrement mastery;
- ineligible events do not reach `update_probability`.

Keep `hint_count` validation non-negative.

## Transfer rule

`VERIFIED_TRANSFER` is eligible only when:

- verification status is `VERIFIED`;
- outcome is `CORRECT` or `INCORRECT`.

Do not add a transfer-specific numeric multiplier in M08-02.

Use the same v1 probability heuristic for now.

## Mastery update result

Replace/extend the existing result object so callers can distinguish applied vs ignored evidence.

Use an explicit structure equivalent to:

```python
@dataclass(frozen=True)
class MasteryUpdate:
    applied: bool
    reason: str
    skill_code: str | None
    old: float | None
    new: float | None
```

For an ineligible event:

- `applied=False`;
- no mastery row is created;
- no persistence mutation occurs;
- `old/new` may be `None`.

For an eligible event:

- `applied=True`;
- use the canonical skill code;
- update/create the matching mastery record;
- report old/new probability.

Reason values should be deterministic and suitable for tests/audit.

## Persistence behavior for eligible evidence

For eligible evidence only:

1. find mastery by `(student_id, canonical_skill_code)`;
2. if absent, create with:
   - probability `0.35`;
   - exposures `0`;
   - correct streak `0`;
3. compute new probability with existing `update_probability(...)`;
4. increment exposures exactly once;
5. increment correct streak for eligible correct evidence;
6. reset correct streak to zero for eligible incorrect evidence;
7. update `last_seen_at`;
8. flush.

Do not commit inside the service.

Transaction ownership remains with the API/caller.

## `/tutor/attempt` trust-boundary fix

The current endpoint may continue to persist the `Attempt` record for logging.

However:

`AttemptRequest.correct`

must be treated as a client claim only.

The endpoint must NOT call the mastery mutation function using that client claim.

The endpoint must NOT:

- create a mastery row;
- increment exposures;
- change correct streak;
- change mastery probability;

solely because the client sent `correct=true` or `correct=false`.

## Attempt API response

Because runtime behavior changes, define an explicit response schema.

Recommended shape:

```python
class AttemptResponse(BaseModel):
    ok: bool = True
    mastery_updated: bool
    mastery_reason: str
    mastery_before: float | None = None
    mastery_after: float | None = None
```

For the current client-claim-only `/tutor/attempt` path:

```text
mastery_updated = false
mastery_reason = "client_claim_not_mastery_eligible"
mastery_before = null
mastery_after = null
```

Equivalent deterministic naming is acceptable.

Do not falsely return a mastery update that was not applied.

## Important API behavior

The endpoint still:

- validates student ownership;
- validates session ownership when `session_id` is supplied;
- stores the attempt claim;
- commits the attempt logging transaction.

Only automatic mastery mutation is removed from this client-controlled path.

## Do not delete `AttemptRequest.correct`

Do not remove or rename the existing request field in M08-02.

The heuristic remains intentionally transparent for v1.
