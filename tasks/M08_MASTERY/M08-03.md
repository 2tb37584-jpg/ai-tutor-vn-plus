# M08-03 — Misconception Evidence Model

Status: ACTIVE
Codex: YES

## Goal

Implement a controlled, deterministic misconception evidence model for Grade 8 algebra skills.

Misconception evidence must use the existing controlled skill taxonomy rather than arbitrary free-text labels.

The model must distinguish a suspected misconception from a confirmed misconception and must preserve the M08-01/M08-02 trust boundary:

- one LLM guess alone is not confirmed evidence;
- a client-provided misconception string alone is not confirmed evidence;
- misconception evidence alone does not mutate mastery;
- correctness and misconception are separate concepts.

## Context

The controlled Grade 8 algebra taxonomy already contains `common_misconceptions` for every controlled skill.

The runtime skill registry already exposes controlled skill definitions containing `SkillDefinition.common_misconceptions`.

The current runtime also contains free-text misconception fields:

- `TutorTurn.misconception`
- `AttemptRequest.misconception`
- `Attempt.misconception`

Those fields are not yet a trustworthy controlled misconception evidence path.

M08-02 already introduced:

- `MasteryEvidenceType.CONFIRMED_MISCONCEPTION`
- `MasteryEvidenceEvent.misconception_code`

but confirmed misconception evidence is intentionally not mastery-bearing by itself.

M08-03 defines the controlled runtime model for misconception evidence.

## Module / micro-task

Module:

`M08 Mastery / Learning Evidence`

Micro-task:

1. expose controlled misconception codes by canonical skill;
2. validate misconception evidence against the taxonomy;
3. distinguish suspected from confirmed evidence;
4. enforce source/confirmation trust rules;
5. add unit tests.

Do not wire the model into TutorAI, Tutor API, Attempt persistence, or mastery mutation in this task.

## Identity rule

A misconception is identified by the pair:

`(canonical_skill_code, misconception_code)`

The same misconception code may theoretically appear under more than one skill in future taxonomy versions.

Do not require global uniqueness across all skills.

Within one skill, duplicate misconception codes must not be treated as separate concepts.

## Canonical skill rule

Resolve the supplied skill label with the existing controlled skill registry.

Required behavior:

- canonical skill code → accepted when controlled;
- reviewed alias → resolve to canonical skill;
- unknown skill → invalid;
- reserved/non-mastery skill → invalid.

Do not create new skills or new misconception labels at runtime.

## Controlled misconception lookup

Add a small public runtime API equivalent to:

```python
def get_misconceptions_for_skill(skill_label: str) -> tuple[str, ...]:
    ...
```

Required behavior:

- resolve aliases to canonical skill;
- return the controlled `common_misconceptions` tuple for that skill;
- return an empty tuple for unknown/reserved skills;
- never mutate the taxonomy/registry.

Also add a predicate equivalent to:

```python
def is_controlled_misconception(
    skill_label: str,
    misconception_code: str,
) -> bool:
    ...
```

Matching should use controlled misconception codes, not fuzzy matching.

For v1:

- exact code identity is preferred;
- surrounding whitespace may be rejected or normalized deterministically;
- do not strip Vietnamese diacritics;
- do not perform fuzzy/semantic matching;
- do not invent aliases for misconception codes.

## Evidence status

Introduce an explicit status equivalent to:

```python
class MisconceptionEvidenceStatus(str, Enum):
    SUSPECTED = "suspected"
    CONFIRMED = "confirmed"
```

### suspected

A plausible misconception signal that is not independently established.

Examples:

- TutorAI proposes a misconception;
- client submits a misconception label;
- heuristic observation without accepted confirmation.

Suspected evidence may be useful for tutoring and diagnostics.

It must not be presented as confirmed evidence.

### confirmed

The misconception has been established by an accepted confirmation source.

M08-03 does not implement the detector itself.

It only enforces which source/status combinations are valid.

## Evidence source

Introduce an explicit source equivalent to:

```python
class MisconceptionEvidenceSource(str, Enum):
    DETERMINISTIC_RULE = "deterministic_rule"
    LLM_JUDGMENT = "llm_judgment"
    CLIENT_CLAIM = "client_claim"
```

Do not add teacher-review/UI workflows in this task.

## Source/status trust rule

For v1:

### deterministic_rule

May produce:

- `SUSPECTED`
- `CONFIRMED`

provided the skill and misconception code are controlled.

### llm_judgment

May produce only:

- `SUSPECTED`

An LLM judgment with confidence `1.0` is still not allowed to become `CONFIRMED` by itself.

### client_claim

May produce only:

- `SUSPECTED`

A client-provided misconception label is never authoritative confirmation.

## Confidence rule

Confidence must be in:

`0.0 <= confidence <= 1.0`

Confidence does not override source/status trust rules.

Do not introduce a confidence threshold that converts suspected evidence into confirmed evidence.

## Misconception evidence structure

Add an immutable typed structure equivalent to:

```python
@dataclass(frozen=True)
class MisconceptionEvidence:
    student_id: int
    session_id: int | None
    skill_code: str
    misconception_code: str
    status: MisconceptionEvidenceStatus
    source: MisconceptionEvidenceSource
    confidence: float
```

This is an internal evidence object.

Do not expose it as a client-controlled API schema in M08-03.

## Validation result

Use an explicit deterministic validation result equivalent to:

```python
@dataclass(frozen=True)
class MisconceptionEvidenceDecision:
    accepted: bool
    reason: str
    skill_code: str | None
    misconception_code: str | None
```

Provide a public validation function equivalent to:

```python
def validate_misconception_evidence(
    evidence: MisconceptionEvidence,
) -> MisconceptionEvidenceDecision:
    ...
```

The validation function must not mutate persistence.

## Validation rules

Evidence is accepted only when:

1. `student_id > 0`;
2. confidence is in `[0,1]`;
3. skill resolves to a controlled mastery-bearing canonical skill;
4. misconception code belongs to that skill's `common_misconceptions`;
5. source/status combination is permitted by the v1 trust rule.

Otherwise return an explicit rejected decision.

Normal evidence rejection should not raise exceptions.

## Deterministic reason strings

Use stable reason strings suitable for tests/audit.

Equivalent examples:

- `accepted`
- `invalid_student_id`
- `invalid_confidence`
- `skill_not_controlled`
- `misconception_not_controlled_for_skill`
- `llm_cannot_confirm_misconception`
- `client_cannot_confirm_misconception`

Exact naming may differ, but each failure class must be distinguishable.

## Relationship to correctness

Misconception evidence and correctness are separate.

A misconception may accompany:

- a correct attempt;
- an incorrect attempt;
- an unknown correctness outcome.

Do not infer `misconception present => incorrect`.

Do not infer `correct answer => no misconception`.

M08-03 does not add correctness fields to the misconception evidence object.

## Relationship to mastery

Do not mutate mastery from misconception evidence in M08-03.

Do not call `record_mastery_evidence(...)` from this service.

`CONFIRMED_MISCONCEPTION` remains non-mastery-bearing by itself under the M08-02 eligibility gate.

Future policy may use confirmed misconception evidence together with separately verified correctness evidence, but that is outside this task.

## Relationship to existing free-text fields

Do not remove or rename:

- `TutorTurn.misconception`
- `AttemptRequest.misconception`
- `Attempt.misconception`

Those are legacy/free-text surfaces until a later wiring task.

M08-03 must not silently reinterpret arbitrary free text from those fields as controlled confirmed evidence.

## Acceptance criteria

M08-03 is complete when:

- controlled misconception codes are discoverable by skill;
- reviewed skill aliases resolve to canonical skills;
- unknown/reserved skills return no controlled misconceptions;
- misconception validation uses `(canonical_skill_code, misconception_code)`;
- controlled misconception code for the correct skill is accepted;
- misconception code belonging to another skill is rejected;
- arbitrary misconception strings are rejected;
- suspected deterministic evidence is accepted;
- confirmed deterministic evidence is accepted;
- suspected LLM evidence is accepted;
- confirmed LLM evidence is rejected;
- suspected client evidence is accepted;
- confirmed client evidence is rejected;
- confidence outside `[0,1]` is rejected;
- invalid student id is rejected;
- confidence alone cannot promote evidence to confirmed;
- no persistence mutation occurs;
- no mastery mutation occurs;
- no existing API/schema field is reinterpreted as trusted evidence;
- no dependency is added;
- full backend regression passes.
