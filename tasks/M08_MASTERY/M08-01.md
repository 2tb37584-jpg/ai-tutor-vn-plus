# M08-01 — Mastery Event Contract

Status: ACTIVE
Codex: MOSTLY NO

## Goal

Define the evidence contract that controls whether a student interaction is allowed to update mastery.

Mastery must represent supported learning evidence, not a raw client claim or a single unverified LLM judgment.

This task defines the contract only.

Implementation of the v1 mastery updater belongs to M08-02.

## Current context

The current backend already has:

- `Mastery`
  - `skill_code`
  - `probability`
  - `exposures`
  - `correct_streak`
  - `last_seen_at`
- `Attempt`
  - `skill_code`
  - `correct`
  - `hint_count`
  - `misconception`
- `record_attempt(...)`
- a controlled skill registry
- deterministic verifier support for one-variable linear equations
- TutorState including `VERIFY` and `TRANSFER`

The current `/tutor/attempt` flow accepts a client-provided `correct: bool` and immediately calls `record_attempt()`.

That existing behavior is not a sufficient trust boundary for mastery.

M08-01 defines the contract that M08-02 must enforce.

## Product rule

Do not update mastery from one unverified LLM judgment alone.

Do not treat a client-provided `correct=true` flag as authoritative correctness evidence.

Do not update mastery for unknown or non-mastery-bearing skills.

## Module / micro-task

Module:

`M08 Mastery`

Micro-task:

Define a deterministic, auditable mastery-evidence event contract and explicit eligibility rules.

No mastery probability formula is implemented in this task.

## Core separation

The system must distinguish three separate concepts:

1. **Attempt claim**
   - what the student/client submitted;
   - may include a proposed answer;
   - is not authoritative by itself.

2. **Verification result**
   - what a deterministic verifier or other accepted verification mechanism concluded;
   - may be correct, incorrect, unknown, unsupported, or disputed.

3. **Mastery evidence decision**
   - whether the verified interaction is allowed to affect mastery;
   - this decision must be derived server-side;
   - it must never be directly supplied by the client.

## Proposed v1 contract

M08-02 should implement an equivalent typed structure to:

```python
MasteryEvidenceEvent(
    student_id: int,
    session_id: int | None,
    skill_code: str,
    outcome: MasteryOutcome,
    evidence_type: MasteryEvidenceType,
    verification_status: VerificationStatus,
    verification_method: str | None,
    confidence: float,
    hint_count: int,
    misconception_code: str | None,
    is_transfer: bool,
)
```

This is a conceptual contract.

Exact Python class location and persistence shape belong to M08-02.

## MasteryOutcome

Supported semantic outcomes:

- `correct`
- `incorrect`
- `unknown`

`unknown` means there is not enough trustworthy evidence to label the attempt correct or incorrect.

`unknown` must not be converted into incorrect merely to simplify scoring.

## MasteryEvidenceType

The v1 contract distinguishes at least:

- `deterministic_verification`
- `verified_transfer`
- `confirmed_misconception`
- `llm_judgment`
- `client_claim`

### deterministic_verification

Evidence produced by a supported deterministic verifier.

Examples:

- verified one-variable linear equation solution;
- future expression-equivalence verifier;
- future numeric/unit verifier.

This may be mastery-bearing when all other eligibility checks pass.

### verified_transfer

A transfer task result that has been independently verified.

This is mastery-bearing evidence and is semantically stronger than repeating the identical worked problem because it demonstrates transfer.

M08-01 does not define a numeric weight.

### confirmed_misconception

Evidence that a specific misconception was observed with sufficient support.

A misconception signal may be recorded as learning evidence, but misconception evidence alone must not automatically be treated as a verified incorrect answer unless the correctness outcome is independently established.

Numeric mastery effects belong to M08-02/M08-03.

### llm_judgment

A model-generated judgment such as `likely_correct=True/False`.

A single LLM judgment alone is never sufficient to mutate mastery.

It may be retained as auxiliary evidence for tutoring behavior or later corroboration.

### client_claim

A correctness value originating from client input, including the current `AttemptRequest.correct`.

A client claim is never authoritative mastery evidence.

The server must independently establish eligibility before mastery changes.

## VerificationStatus

The v1 contract distinguishes at least:

- `verified`
- `unverified`
- `unsupported`
- `disputed`

### verified

A trusted mechanism has established the outcome inside its supported domain.

### unverified

No accepted verifier has established correctness.

### unsupported

The problem/attempt is outside the active verifier's supported domain.

### disputed

Two evidence sources materially disagree.

A disputed event must not directly mutate mastery until resolved by a stronger verification path.

## Skill eligibility

A mastery event may affect mastery only when:

1. `skill_code` resolves to a canonical controlled skill;
2. `is_mastery_bearing_skill(skill_code)` is true;
3. the code is not `unknown`;
4. the code is not a reserved non-mastery label such as `general.problem_solving`.

Unknown labels must never create new mastery rows.

Client-provided arbitrary skill strings must never create mastery-bearing skills.

## Mastery eligibility rule

An event is eligible to mutate mastery only when all of the following are true:

1. skill is controlled and mastery-bearing;
2. verification status is `verified`;
3. outcome is `correct` or `incorrect`;
4. evidence source is an accepted mastery-bearing source;
5. confidence satisfies the source-specific trust rule;
6. event is not disputed.

For v1, accepted mastery-bearing sources are:

- deterministic verification;
- verified transfer.

Other sources require corroboration before becoming mastery-bearing.

## Explicit non-eligible cases

The following must NOT mutate mastery:

- `client_claim` alone;
- `llm_judgment` alone;
- `verification_status=unverified`;
- `verification_status=unsupported`;
- `verification_status=disputed`;
- `outcome=unknown`;
- unknown skill;
- reserved non-mastery skill;
- malformed attempt;
- missing verifier result;
- ambiguous problem where correctness cannot be established.

These events may still be useful for tutoring, logging, diagnostics, or future review.

## Confidence contract

`confidence` is a value in `[0.0, 1.0]`.

Confidence does not override verification status.

Examples:

- an LLM judgment with confidence `0.99` is still not mastery-bearing by itself;
- deterministic verified evidence may use confidence `1.0` or another explicitly defined deterministic confidence convention;
- unsupported evidence remains ineligible regardless of confidence.

M08-02 must not implement a rule equivalent to:

```text
high confidence => update mastery
```

without also satisfying source and verification eligibility.

## Hint contract

`hint_count` is contextual evidence, not a correctness source.

Rules:

- `hint_count >= 0`;
- hints may reduce the strength of positive evidence;
- hints do not turn an incorrect answer into correct;
- hints do not make an unverified answer mastery-bearing;
- receiving hints alone must not decrement mastery.

The exact numeric adjustment belongs to M08-02.

## Transfer contract

Transfer performance must be represented explicitly.

A transfer event is mastery-bearing only when its result is independently verified.

`is_transfer=True` without verification does not qualify.

Successful verified transfer may later receive stronger positive weighting than a repeated same-problem success, but M08-01 does not define the numeric multiplier.

## Misconception contract

Misconception evidence must be separable from correctness.

A misconception code should eventually be controlled rather than arbitrary free text.

For M08-01:

- misconception evidence may accompany correct, incorrect, or unknown outcomes;
- misconception evidence alone does not establish correctness;
- one low-confidence LLM misconception guess must not mutate mastery;
- M08-03 owns the detailed misconception evidence model.

## Exposure contract

`Mastery.exposures` should mean:

> number of mastery-eligible evidence events applied to this skill

It must not mean:

> every message, every client attempt, or every unverified judgment

Therefore an ineligible event must not increment `exposures`.

## Correct streak contract

`correct_streak` changes only from mastery-eligible verified correctness evidence.

Rules:

- eligible verified correct evidence may increment the streak;
- eligible verified incorrect evidence may reset the streak;
- unknown/unverified/unsupported/disputed evidence must leave the streak unchanged.

Exact streak behavior belongs to M08-02.

## Auditability

A mastery mutation must be explainable from its evidence.

For every applied update, the implementation should be able to answer:

- which student;
- which canonical skill;
- which session/attempt;
- what verified outcome;
- which verification method;
- how many hints;
- whether it was transfer;
- what confidence;
- why the evidence was eligible.

M08-01 does not require a new database event table.

Persistence design can be introduced later if required.

## Trust boundary

Values that may originate from a client must be treated as claims, including:

- `correct`;
- `skill_code`;
- hint metadata if client-controlled;
- misconception text if client-controlled.

The server must derive mastery eligibility.

The client must never be able to directly submit:

```text
eligible_for_mastery=true
```

or an equivalent authoritative flag.

## Relationship to current API

The current `/tutor/attempt` endpoint is legacy behavior relative to this contract because it trusts:

```python
AttemptRequest.correct
```

and immediately updates mastery.

M08-01 does not modify that endpoint.

M08-02 must bring runtime behavior into compliance with this contract before the mastery system is considered trustworthy.

## Relationship to verifier

Deterministic verifier output is preferred where a verifier family exists.

The skill registry's `verifier_family` should guide future verification routing.

M08-01 does not implement routing.

If a skill has no supported deterministic verifier yet, the system must not silently substitute one unverified LLM judgment as equivalent deterministic evidence.

## Relationship to TutorState

TutorState may generate evidence signals:

- attempt states;
- VERIFY;
- TRANSFER.

State transitions alone are not mastery evidence.

For example:

```text
state == VERIFY
```

does not itself prove the student's answer was correct.

Mastery requires an eligible verified evidence event.

## Decision examples

### Example A — verified correct linear equation

Skill:

`algebra.linear_equation`

Deterministic verifier confirms candidate solution.

Outcome:

`correct`

Verification:

`verified`

Evidence type:

`deterministic_verification`

Result:

Eligible for mastery update.

### Example B — deterministic incorrect result

Controlled skill and deterministic verifier proves candidate is incorrect.

Outcome:

`incorrect`

Verification:

`verified`

Evidence type:

`deterministic_verification`

Result:

Eligible for mastery update.

### Example C — LLM says likely correct

Tutor model emits:

`likely_correct=True`

No deterministic or independent verification exists.

Outcome:

may be an auxiliary model judgment

Verification:

`unverified`

Evidence type:

`llm_judgment`

Result:

Not eligible for mastery update.

### Example D — client sends correct=true

Client POST contains:

`correct=true`

No trusted verification result.

Evidence type:

`client_claim`

Result:

Not eligible for mastery update.

### Example E — unknown skill

Skill resolves to:

`unknown`

Result:

Not eligible.

Must not create a mastery row.

### Example F — reserved skill

Skill:

`general.problem_solving`

Result:

Not eligible.

Must not create a mastery row.

### Example G — verified transfer

Student succeeds on a related transfer problem and the result is independently verified.

Outcome:

`correct`

Verification:

`verified`

Evidence type:

`verified_transfer`

Result:

Eligible.

### Example H — unsupported verifier domain

Student submits work for a problem outside the active deterministic verifier domain.

Verification:

`unsupported`

Even if an LLM reports high confidence.

Result:

Not eligible without another accepted verification path.

### Example I — misconception guess only

LLM predicts a misconception with confidence 0.7.

Correctness is not independently established.

Result:

May be retained as auxiliary diagnostic evidence.

Must not mutate mastery by itself.
