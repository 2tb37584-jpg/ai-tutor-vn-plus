# M05-14 — Define Trusted Authored-Question Tutor Start Contract

Status: DONE
Codex: NO
Module: Tutor Engine
Type: Design / contract only

## Goal

Define the trusted backend contract for starting a new tutor session from a recommended authored question identified by `question_id`.

This task does not implement production code.

The contract must preserve authored question identity and verification authority without treating learner/client-provided problem text or metadata as trusted.

## Context

The adaptive-learning flow now reaches:

```text
deterministic mastery
→ next-best-question recommendation
→ completion response.next_learning_action
→ frontend renders “Bài tiếp theo”
```

M10-03 intentionally does not start the recommended question.

The existing free-form endpoint is:

```text
POST /tutor/start
```

with client input:

```text
student_id
problem_text
image_data_url
```

Its current path is:

```text
client problem/image
→ ai.analyze_problem(...)
→ model-derived primary skill / expected answer
→ TutorSession
```

That path is appropriate for free-form learner problems.

It is not authoritative enough for a question selected from the trusted server-side question bank.

The question-bank service already provides:

```text
get_question(question_id)
```

and authored-item verification is already supported through the question-bank verification adapter:

```text
verification_request_for_candidate(item, candidate)
```

Transfer verification already demonstrates the trust boundary:

```text
persisted question identity
→ server-side get_question(...)
→ authored item
→ deterministic verification request
```

## Core decision

Do not extend the existing free-form `/tutor/start` request with optional authored metadata.

Introduce a separate authored-question start path.

Proposed endpoint:

```text
POST /tutor/start-authored
```

The client supplies only:

```json
{
  "student_id": 123,
  "question_id": "trusted-question-id"
}
```

The client must not supply authoritative:

```text
problem_text
skill_code
difficulty
expected_answer
verification_reference
verification_family
```

for this path.

The server resolves all authored content from:

```text
get_question(question_id)
```

## Why a separate endpoint

A separate endpoint keeps two trust models explicit:

### Free-form learner problem

```text
POST /tutor/start
client problem/image
→ model analysis
→ inferred tutoring metadata
```

### Authored question

```text
POST /tutor/start-authored
client question_id
→ trusted server-side question lookup
→ authored tutoring metadata
```

Do not create a request where `problem_text`, `question_id`, and verification metadata can conflict.

There must be exactly one authority for authored-question content: the server-side question bank.

## Request contract

Add a future schema equivalent to:

```python
class StartAuthoredTutorRequest(BaseModel):
    student_id: int
    question_id: str = Field(min_length=1, max_length=120)
```

No other authored question fields are accepted from the client.

Authentication and student ownership checks must be identical in strength to the existing `/tutor/start` path.

## Lookup contract

The endpoint must:

1. verify the authenticated user owns `student_id`;
2. resolve `question_id` with `get_question(question_id)`;
3. reject an unknown question ID without creating a session;
4. use only the returned `QuestionBankItem` as authored content authority.

Unknown question behavior:

```text
HTTP 404
```

with a stable learner-safe/API-safe error such as:

```text
Question not found
```

Do not fall back to free-form analysis if the ID is unknown.

## Session provenance

An authored-started session must retain its authored source identity separately from transfer-question identity.

Introduce a future nullable `TutorSession` field:

```text
authored_question_id
```

Semantics:

```text
authored_question_id = question used to START this tutor session
transfer_question_id = transfer item selected LATER inside this session
```

Do not overload:

```text
transfer_question_id
```

for authored session provenance.

For ordinary free-form sessions:

```text
authored_question_id = null
```

For authored starts:

```text
authored_question_id = item.id
```

The exact database migration belongs to a later implementation task.

## Trusted session construction

For an authored start, the persisted session must be derived from the resolved item, not from client copies and not from `ai.analyze_problem(...)`.

At minimum:

```text
normalized_problem      ← authored item problem text
primary_skill           ← authored item skill code
internal_expected_answer← authored item learner-hidden expected answer
verification_family     ← authored item verification family
authored_question_id    ← authored item ID
```

If the current `QuestionBankItem` distinguishes an expected answer from another verification reference, preserve the existing distinction.

Do not reconstruct verifier authority from display text.

Do not derive authored verification metadata from an LLM.

## Difficulty authority

The client may display difficulty from the recommendation payload, but it is not authoritative input to start.

Difficulty is recovered from the resolved authored item.

For MVP, do not add a duplicate `difficulty` column to `TutorSession` merely to copy question-bank metadata.

The persisted `authored_question_id` is the provenance key; trusted difficulty can be resolved server-side from the authored item when needed.

If future historical/versioning requirements make immutable difficulty snapshots necessary, that must be a separate persistence decision.

## Verification contract

This is the critical runtime rule.

Authored sessions must not lose the authored verifier/reference semantics by reducing verification to the current generic session fields alone.

When:

```text
session.authored_question_id is not null
```

attempt verification should resolve:

```text
item = get_question(session.authored_question_id)
```

and build the deterministic request using the existing authored-item adapter:

```text
verification_request_for_candidate(item, candidate)
```

This preserves authored question support across all deterministic families supported by the question bank.

Do not assume the existing normal-session helper:

```text
_verification_request_for_session(...)
```

is sufficient for authored sessions.

That helper currently constructs only the runtime families it explicitly knows about and therefore must not silently downgrade an authored question.

If the persisted authored ID cannot be resolved during a later attempt:

```text
do not trust model likely_correct as replacement authority
do not record verified mastery from that attempt
do not silently convert to free-form verification
```

The exact learner-facing failure behavior can be defined in the implementation task, but deterministic authority must fail closed.

## First tutor turn

The authored-start path must not call:

```text
ai.analyze_problem(...)
```

to rediscover skill, expected answer, difficulty, or verification family.

It may still use the existing tutor-generation layer to produce the first Socratic tutor turn.

If `ai.first_turn(...)` requires a `ProblemAnalysis`, construct an internal deterministic analysis object from the trusted authored item.

Required authoritative parts are:

```text
normalized_problem = item.problem_text
skills = [item.skill_code]
expected_answer = authored expected answer
confidence = 1.0
```

Other presentation-only analysis fields must be populated deterministically from existing controlled metadata/defaults.

They must not become verification authority.

The initial generated tutor message remains subject to the existing answer-leakage guard using the authored expected answer.

## Public response

Do not expose authored answer/verifier internals.

The authored-start response must include:

```text
session_id
tutor
```

and may include the same learner-safe authored question projection already used by next-learning-action delivery:

```text
question_id
skill_code
problem_text
difficulty
```

Preferred future response:

```python
class StartAuthoredTutorResponse(BaseModel):
    session_id: int
    question: NextLearningAction
    tutor: TutorTurn
```

Reusing `NextLearningAction` here is acceptable because it is already a learner-safe projection of the authored question.

Do not expose:

```text
expected_answer
verification_reference
verification_family
internal verifier metadata
```

The existing free-form `StartTutorResponse` does not need to change for this contract.

## State contract

An authored-started session is a normal new learning session, not a transfer continuation.

Starting an authored question must not initialize the session in:

```text
TRANSFER
COMPLETE
```

merely because the question came from `next_learning_action`.

Its initial tutor state follows the normal tutor first-turn/state-machine contract.

`authored_question_id` identifies session provenance only.

`transfer_question_id` remains null until/unless this new session later enters TRANSFER and a transfer item is selected.

## Mastery contract

Starting an authored question does not itself create mastery evidence.

Mastery evidence is recorded only through the existing authoritative attempt/verification rules.

For authored sessions, deterministic correctness must come from the authored question-bank verification adapter.

`likely_correct` remains non-authoritative where deterministic verification is available.

## Recommendation contract

The recommendation that produced the `question_id` is not persisted as a separate recommendation-history object in this milestone.

Starting the question establishes only:

```text
TutorSession.authored_question_id
```

No recommendation-history table or analytics event is added here.

## Security and trust-boundary rules

The authored-start endpoint must reject client attempts to override authored metadata by design because those fields are absent from the request schema.

Never accept or trust client copies of:

```text
problem_text
skill_code
difficulty
expected_answer
verification_reference
verification_family
```

for authored start.

The only client-selected authored value is:

```text
question_id
```

and it is always resolved against the server-side question bank.

## Non-goals

M05-14 does not:

- implement the endpoint;
- add database columns;
- add migrations;
- change verification code;
- change frontend code;
- add the “Bắt đầu bài này” button;
- add recommendation history;
- redesign the question bank;
- add dependencies;
- change free-form `/tutor/start`;
- broaden subject coverage.

## Design review evidence

Reviewed against the current backend seams captured before task creation.

Confirmed decisions:

- free-form `POST /tutor/start` remains the model-analysis path;
- authored start is a separate trust path;
- client authority is limited to `student_id` and `question_id`;
- `get_question(question_id)` is the sole authored-content source;
- unknown authored IDs fail closed and do not fall back to free-form analysis;
- authored session provenance is represented separately from transfer provenance;
- `authored_question_id` and `transfer_question_id` have distinct semantics;
- authored problem text, skill, expected-answer authority, verifier family, and difficulty come from the server-side question-bank item;
- authored attempts must reconstruct the trusted item and use `verification_request_for_candidate(...)`;
- model `likely_correct` cannot replace deterministic authored verification;
- authored start must not call `ai.analyze_problem(...)`;
- the existing answer-leakage guard remains applicable to the first generated tutor turn;
- the public response exposes only learner-safe authored fields;
- starting an authored question does not itself create mastery evidence;
- authored start begins a normal tutor lifecycle and is not implicitly a TRANSFER state;
- the implementation is decomposed into M05-15, M05-16, M05-17, then M10-04.

No production code, schema, migration, frontend, dependency, or question-bank content change is part of M05-14.

No runtime tests are required for this design-only task. Follow-up implementation tasks carry the persistence, verification, API, and UI tests defined in this contract.


## Tests required by follow-up implementation

### Persistence

- free-form session persists `authored_question_id = null`;
- authored session can persist exact authored question ID;
- transfer question identity remains independent.

### Authored lookup/start

- owned student + valid question ID creates session;
- unknown question ID returns 404 and creates no session;
- another user's student remains rejected;
- client cannot submit answer/verifier overrides because schema has no such fields;
- `ai.analyze_problem(...)` is not called;
- persisted problem/skill/expected answer/family come from resolved item;
- initial tutor output remains leakage-guarded.

### Verification

- authored attempt reconstructs item from persisted authored ID;
- candidate is verified through `verification_request_for_candidate(...)`;
- supported authored family produces deterministic correctness;
- missing/invalid authored ID does not record deterministic mastery;
- model `likely_correct` cannot override deterministic authored verification;
- transfer behavior for the same session remains independent.

### Public response

- learner sees only safe authored question fields;
- expected answer absent;
- verification reference absent;
- verification family absent.

## Stop conditions for implementation

Stop and split/return for review if implementation requires:

- changing more than 6 files in one task;
- combining DB migration, endpoint, verification runtime, and frontend in one task;
- adding a dependency;
- changing question-bank content;
- weakening deterministic verification;
- using client `problem_text` as authored authority;
- overloading `transfer_question_id`;
- introducing recommendation-history persistence.

## Design result

The trusted authored-question lifecycle is:

```text
next_learning_action.question_id
→ learner explicitly chooses it
→ POST /tutor/start-authored
→ owned student check
→ get_question(question_id)
→ persist authored_question_id
→ build session from authored item
→ guarded first Socratic tutor turn
→ authored attempts resolve same item
→ verification_request_for_candidate(item, candidate)
→ deterministic mastery evidence
```

The trust boundary is:

```text
client chooses ID
server owns content and verification truth
```
