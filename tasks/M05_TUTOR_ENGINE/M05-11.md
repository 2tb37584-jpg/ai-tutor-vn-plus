# M05-11 — Select and Persist Deterministic Transfer Item

Status: ACTIVE
Codex: YES
Module: Tutor Engine

## Goal

When a tutor session enters `TRANSFER`, deterministically select one authored same-skill transfer item and persist its exact question-bank ID in:

```text
TutorSession.transfer_question_id
```

The selected ID must be reused on later turns.

This task is selection/persistence only.

It must not verify the learner's transfer answer, emit `TRANSFER_COMPLETED`, update mastery, or invoke the post-completion recommender.

## Context

M05-08 established the deterministic transfer-completion contract:

- transfer practice uses an authored deterministic `QuestionBankItem`;
- the transfer item must match the session's skill;
- model-only correctness is not sufficient.

M05-09 added persisted:

```text
TutorSession.transfer_question_id
```

M05-10 added the deterministic adapter:

```text
transfer_question_id
→ exact authored QuestionBankItem
→ family-specific VerificationRequest
```

M07-06 guarantees authored transfer coverage for every currently deterministic-transfer-eligible mastery-bearing skill.

The remaining prerequisite before M05-07 runtime completion wiring is to select and persist the authored transfer item when the runtime actually enters `TRANSFER`.

## Micro-task

Implement one deterministic selection path:

```text
session transitions into TRANSFER
→ select one authored item for session.primary_skill
→ persist item.id in session.transfer_question_id
→ keep that same ID on later TRANSFER turns
```

Do not select a new item on every request.

Do not overwrite an already-persisted valid transfer ID during the same transfer interaction.

## Determinism contract

Selection must be deterministic.

No:

```text
random
shuffle
LLM choice
time-based choice
database-order ambiguity
```

Prefer a stable question-bank helper that returns the first authored item in declaration order for the exact canonical skill.

If an existing helper already provides deterministic declaration-order results, reuse it rather than introducing a new selection subsystem.

Do not use the next-best-question recommender for this task.

That recommender is a separate post-completion learning-action concern, not the transfer-item generator.

## Eligibility boundary

A transfer item may be selected only when:

- `session.primary_skill` is present;
- the skill has an authored deterministic-transfer item in the question bank;
- the selected item's `skill_code` exactly matches `session.primary_skill`.

If no deterministic authored item exists:

```text
do not invent one
do not fall back to another skill
do not ask the model to generate one
```

Return/retain the existing explicit no-selection behavior and report via tests.

Do not broaden `manual_or_future` into deterministic transfer.

## Question-bank selection helper

Prefer adding/reusing a small deterministic helper conceptually like:

```python
def get_transfer_question_for_skill(skill_code: str) -> QuestionBankItem | None:
    ...
```

Exact naming may follow current module style.

Required behavior:

- exact canonical skill match only;
- authored bank only;
- deterministic declaration-order choice;
- returns `None` when no authored item exists for the skill;
- no randomization;
- no verifier-family coercion;
- no fallback to prerequisite/neighbor skills.

If `get_questions_for_skill(skill_code)` already returns a stable declaration-order tuple, the new helper may simply reuse that contract.

Do not duplicate question-bank filtering logic in `tutor.py` if it belongs in the question-bank service.

## Tutor runtime integration contract

Integrate selection at the narrow point where a persisted tutor session first enters `TutorState.TRANSFER`.

Conceptually:

```text
previous state != TRANSFER
next state == TRANSFER
```

or the equivalent existing runtime boundary.

At that boundary:

1. if `session.transfer_question_id` is already set, preserve it;
2. otherwise, use `session.primary_skill`;
3. deterministically select the authored transfer item;
4. persist only its `item.id`.

Do not persist:

```text
problem_text
verification_reference
expected_answer
verification_family
```

Those remain owned by the authored question bank and are reconstructed later by ID.

## Reuse contract

While the session remains in `TRANSFER`:

```text
existing transfer_question_id
```

must remain unchanged.

Repeated learner turns must not select a new item.

A later task may define lifecycle reset behavior for a new transfer episode if needed.

Do not invent reset semantics in M05-11.

## No-selection semantics

Expected no-selection conditions include:

```text
no primary_skill
no authored item for exact skill
ineligible/manual_or_future skill
```

In those cases:

- leave `transfer_question_id` as `None`;
- do not fall back to another skill;
- do not raise for expected absence unless current tutor API conventions require an explicit controlled error.

Do not silently select a semantically unrelated item.
