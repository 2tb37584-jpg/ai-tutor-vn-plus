# M05-04A — Hide Internal Solution Data From Student API

Status: DONE
Codex: YES — SMALL

## Goal

Prevent internal answer-bearing and verification-only fields from crossing the student-facing `/tutor/start` API boundary.

## Problem

Internal `ProblemAnalysis` contains:

- `expected_answer`
- `verification_notes`

`StartTutorResponse` currently exposes `ProblemAnalysis` directly.

Therefore server-internal solution data can be serialized to the student client even when the TutorTurn itself follows Socratic behavior.

## Product rule

Internal verification data must remain available server-side but must not be exposed to the student-facing client unless explicitly designed for that purpose.

## Allowed implementation files

- backend/app/schemas/tutor.py
- backend/app/api/tutor.py
- backend/tests/test_tutor_api_leakage.py
- frontend/app/page.tsx

## Forbidden scope

Do NOT modify:

- backend/app/services/tutor_ai.py
- backend/app/services/tutor_state.py
- backend/app/services/verifier.py
- database models
- migrations
- authentication
- mastery
- dependencies
- Docker files
- runtime tutor-message leakage detection
- eval infrastructure

Do not add a dependency.

## Required behavior

### Internal analysis

Keep `ProblemAnalysis` unchanged.

It must continue to contain:

- expected_answer
- verification_notes

TutorAI must continue returning internal `ProblemAnalysis`.

### Student-facing analysis

Introduce a separate typed response schema for safe public analysis.

It may expose:

- normalized_problem
- subject
- grade_band
- skills
- prerequisites
- confidence

It must NOT expose:

- expected_answer
- verification_notes

`StartTutorResponse.analysis` must use the safe public schema instead of internal `ProblemAnalysis`.

### API conversion

`/tutor/start` must explicitly convert the internal `ProblemAnalysis` into the public/student-facing analysis schema.

Do not mutate the internal analysis object.

Do not depend on accidental field dropping as the security boundary.

### Frontend

Update the `StartResponse.analysis` TypeScript type so it matches the student-facing API contract.

Remove `verification_notes`.

Do not otherwise change frontend behavior or rendering.

## Acceptance criteria

- Internal `ProblemAnalysis.expected_answer` still exists.
- Internal `ProblemAnalysis.verification_notes` still exists.
- TutorAI behavior is unchanged.
- `/tutor/start` response JSON contains no `expected_answer`.
- `/tutor/start` response JSON contains no `verification_notes`.
- Safe analysis fields remain available.
- Tutor message behavior is unchanged.
- Existing request shape is unchanged.
- Frontend no longer declares the removed internal field.
- No runtime-message leakage detector is added in this task.
- Only the four allowed files change.

## Tests

Create:

`backend/tests/test_tutor_api_leakage.py`

Tests must prove at minimum:

1. Fake/internal `ProblemAnalysis` contains a known secret expected answer.
2. Internal `ProblemAnalysis` still retains that answer before and after public conversion.
3. Student-facing `/tutor/start` serialized output contains no `expected_answer`.
4. Serialized output contains no `verification_notes`.
5. Safe fields such as `normalized_problem`, `skills`, and `confidence` remain present.
6. Existing tutor payload shape does not change.

Prefer testing the actual FastAPI response serialization or an equivalent typed response boundary, not only checking model field declarations.
