# M05-03 — State-aware Hint Generation Policy

Status: DONE
Codex: YES — SMALL

## Goal

Make TutorAI generation respect the explicit tutor state so that hint escalation is behaviorally distinct and bounded.

The deterministic state transitions already exist. This task does not reimplement them.

## Existing transition contract

Incorrect attempts already progress deterministically:

ASK_ATTEMPT -> HINT_1 -> HINT_2 -> EXPLAIN_STEP

Correct attempts from ASK_ATTEMPT / HINT_1 / HINT_2 progress to VERIFY.

These transition rules remain owned by tutor_state.py.

## Required behavior

Tutor generation must receive explicit guidance derived from the persisted/current TutorState.

### ASK_ATTEMPT

For an incorrect attempt, the next response should behave as HINT_1:

- give one small conceptual cue or focused question;
- do not perform the algebraic/procedural step for the student;
- keep hint_level consistent with HINT_1.

### HINT_1

For another incorrect attempt, the next response should behave as HINT_2:

- give a more concrete scaffold than HINT_1;
- identify the relevant operation, relation, formula, or sub-step;
- still leave meaningful work for the student;
- keep hint_level consistent with HINT_2.

### HINT_2

For another incorrect attempt, the next response should behave as EXPLAIN_STEP:

- explain exactly one useful intermediate step;
- stop after that step and ask the student to continue;
- do not provide a complete worked solution;
- keep hint_level consistent with EXPLAIN_STEP.

### Correct attempt

A correct attempt continues to VERIFY using the existing deterministic transition logic.

## State ownership

TutorAI may use current_state to choose generation instructions.

TutorAI must NOT duplicate the transition table.

The application-controlled state returned by transition_tutor_state remains authoritative.

Model-provided state must not become authoritative.

## Hint-level consistency

TutorTurn.hint_level must be application-controlled for the tutor progression states.

At minimum:

- ASK_ATTEMPT = 0
- HINT_1 = 1
- HINT_2 = 2
- EXPLAIN_STEP = 3

Do not trust a conflicting model-provided hint_level.

## Answer leakage boundary

This task defines the intended degree of assistance only.

Do not implement the full M05-04 answer-leakage guard here.

Do not add expected-answer comparison, regex leakage detection, verifier logic, or eval infrastructure in this task.

## Acceptance criteria

- Generation instructions are explicitly state-aware.
- HINT_1, HINT_2, and EXPLAIN_STEP have distinct bounded policies.
- Existing deterministic transition logic is reused, not duplicated.
- hint_level is consistent with the application-controlled resulting state.
- A model-provided conflicting state or hint_level cannot override application state/policy metadata.
- Existing TutorAI call shape remains compatible.
- Existing tutor-state tests remain green.
- Only the two allowed implementation files change.

## Tests

Create:

backend/tests/test_tutor_hint_policy.py

Tests must cover at minimum:

1. Policy for ASK_ATTEMPT describes first-level guidance.
2. Policy for HINT_1 is more concrete than ASK_ATTEMPT guidance and targets HINT_2 behavior.
3. Policy for HINT_2 allows one explained intermediate step but not a complete solution.
4. Result state HINT_1 forces hint_level = 1.
5. Result state HINT_2 forces hint_level = 2.
6. Result state EXPLAIN_STEP forces hint_level = 3.
7. Conflicting model-provided hint_level is overwritten.
8. Existing model-provided state remains overwritten by application state.
