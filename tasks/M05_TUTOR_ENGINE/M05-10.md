# M05-10 — Add Deterministic Transfer Verification Adapter

Status: ACTIVE
Codex: YES
Module: Tutor Engine

## Goal

Add a deterministic adapter that reconstructs the exact authored transfer question from a persisted `TutorSession.transfer_question_id` and builds the correct family-specific `VerificationRequest`.

This task prepares trusted transfer-answer verification for M05-07.

It must not change tutor state, emit `TRANSFER_COMPLETED`, update mastery, or select/recommend a transfer item.

## Context

M05-09 now persists:

```text
TutorSession.transfer_question_id
```

as the opaque authored question-bank ID selected for the session.

M07-06 guarantees authored deterministic transfer coverage for every currently eligible mastery-bearing skill.

Supported deterministic transfer verifier families are:

```text
numeric
expression_equivalence
linear_equation
factorization
domain_condition
```

The question bank already owns authored:

```text
verification_reference
expected_answer
verification_family
skill_code
```

and already self-validates those values deterministically.

The remaining prerequisite before runtime completion orchestration is a trusted adapter:

```text
persisted transfer_question_id
→ exact authored QuestionBankItem
→ family-specific VerificationRequest
```

No learner correctness may be inferred from `likely_correct`.

## Micro-task

Add a pure deterministic transfer-verification adapter.

Given a persisted tutor session:

1. read `session.transfer_question_id`;
2. resolve exactly one authored question-bank item by that ID;
3. reject missing/unknown/mismatched transfer context explicitly;
4. build the deterministic `VerificationRequest` from the authored item;
5. substitute the learner's current transfer answer only at the candidate/answer side when the adapter API requires it.

Do not call `verify()` from tutor runtime orchestration yet unless a pure helper test needs to call `verify()` directly.

Do not change tutor state in this task.

## Design boundary

The authored question bank is the trusted source for:

```text
skill_code
verification_family
verification_reference
```

The learner message is only the candidate answer.

Never reconstruct transfer verification from:

```text
normalized_problem
internal_expected_answer
likely_correct
model output
skill-only lookup
```

Skill-only lookup is ambiguous and must not be used to recover a transfer item.

## Question-bank adapter contract

Prefer reusing the existing deterministic question-bank verification-request construction logic.

Do not duplicate the full family-switch in `tutor.py` if `question_bank.py` already owns it.

If the existing builder is private, add the smallest stable application-layer wrapper needed for tutor use rather than creating a second independent implementation.

The adapter must support exactly the deterministic transfer families already accepted by the authored bank:

```text
numeric
expression_equivalence
linear_equation
factorization
domain_condition
```

`manual_or_future` must not become supported.

## Session adapter contract

Add a small pure helper in `backend/app/api/tutor.py` conceptually similar to:

```python
def _transfer_verification_request_for_session(
    session: TutorSession,
    candidate: str,
) -> VerificationRequest | None:
    ...
```

Exact naming may follow current module style.

Required behavior:

### No persisted transfer ID

If:

```text
session.transfer_question_id is None
```

return no deterministic transfer request.

Do not guess from `primary_skill`.

### Unknown authored ID

If the persisted ID does not resolve to an authored question-bank item:

```text
return no deterministic transfer request
```

Do not fall back to another item for the same skill.

### Skill mismatch

If the resolved authored item does not match the session's trusted primary skill when a primary skill is present:

```text
return no deterministic transfer request
```

This prevents a stale/corrupted transfer ID from verifying against a different skill.

Do not mutate the session.

### Supported authored item

For a valid matching authored item:

- preserve the authored verification family;
- preserve the authored verification reference/equation/expected trusted side;
- use the learner transfer answer as the candidate side;
- return the appropriate deterministic `VerificationRequest`.

## Family semantics

The adapter must preserve existing verifier request semantics.

Conceptually:

### numeric

Trusted authored answer/reference stays trusted; learner text becomes numeric candidate.

### expression_equivalence

Trusted authored expression/reference stays trusted; learner text becomes the compared candidate expression.

### linear_equation

Trusted authored equation stays trusted; learner text becomes candidate solution.

### factorization

Trusted authored polynomial/reference stays trusted; learner text becomes candidate factorization.

### domain_condition

Trusted authored excluded-value reference stays trusted; learner text becomes candidate domain-condition expression.

Do not derive trusted values from the learner message.

## Error semantics

This task is an adapter, not runtime orchestration.

Expected missing/invalid transfer context should produce:

```text
None
```

or the existing equivalent no-request sentinel used by tutor verification helpers.

Do not raise for normal:

```text
missing ID
unknown ID
skill mismatch
unsupported authored family
```

Unexpected programming/runtime errors should not be silently converted into learner correctness.

Follow the existing tutor verification-helper convention.
