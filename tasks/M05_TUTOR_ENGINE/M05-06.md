# M05-06 — Deterministic Tutor Session Summary

Status: DONE
Codex: YES

## Goal

Add a deterministic, read-only summary for one owned tutor session.

The summary must be computed from persisted `TutorSession` + `TutorMessage` data at read time.

Do not call an LLM and do not persist a denormalized summary row.

## Why compute on read

The repository currently has:

- `TutorSession` with primary skill and current tutor state;
- `TutorMessage` with role/content/timestamps;
- M05-05 telemetry on user replies:
  - `reply_intent`
  - `response_latency_ms`

There is no existing session-summary endpoint or summary persistence model.

For Phase 1, the summary is small enough to derive deterministically from existing rows. Persisting another summary record would introduce stale-data synchronization and a migration without demonstrated need.

## Module / micro-task

Module:

`M05 Tutor Engine`

Micro-task:

1. define a public session-summary response contract;
2. add a pure deterministic summary function;
3. expose one owned-session GET endpoint;
4. add focused unit/API tests.

## Endpoint

Add:

```text
GET /tutor/sessions/{session_id}/summary
```

The endpoint must:

- require the existing authenticated user dependency;
- use existing `owned_session(...)` authorization;
- return 404 for a missing/not-owned session using current ownership behavior;
- query that session's `TutorMessage` rows;
- compute the summary deterministically;
- not mutate DB state;
- not call TutorAI.

## Response contract

Add a Pydantic model such as:

```python
class TutorSessionSummaryResponse(BaseModel):
    session_id: int
    primary_skill: str
    current_state: TutorState
    student_reply_count: int
    attempt_reply_count: int
    hint_request_count: int
    unclassified_reply_count: int
    timed_reply_count: int
    average_response_latency_ms: float | None
```

Equivalent naming is acceptable only if semantics remain exactly clear.

### Field semantics

`session_id`
- current tutor session ID.

`primary_skill`
- persisted `TutorSession.primary_skill`.

`current_state`
- parsed persisted `TutorSession.current_state`.

`student_reply_count`
- count of all `TutorMessage` rows for the session where `role == "user"`.

`attempt_reply_count`
- count of user messages where `reply_intent == "attempt"`.

`hint_request_count`
- count of user messages where `reply_intent == "hint_request"`.

`unclassified_reply_count`
- count of user messages whose `reply_intent` is NULL or is not one of the two controlled intent values.
- This keeps legacy pre-M05-05 messages visible instead of silently treating them as attempts.

`timed_reply_count`
- count of user messages whose `response_latency_ms` is not NULL.

`average_response_latency_ms`
- arithmetic mean of all non-NULL user `response_latency_ms` values.
- return `None` when there are no timed replies.
- do not include assistant messages.
- do not synthesize latency for legacy rows.

The count invariant must hold:

```text
student_reply_count
==
attempt_reply_count
+ hint_request_count
+ unclassified_reply_count
```

## Deliberately excluded from v1

Do not return:

- raw student/tutor message content;
- `internal_expected_answer`;
- model prompts/responses;
- IP/device/browser/geolocation;
- mastery conclusions;
- correctness claims from `/tutor/attempt`;
- misconception conclusions;
- an LLM-generated prose summary;
- a score/rating for the student;
- a "good/bad" judgment about response speed.

This task reports deterministic telemetry only.

## Service design

Create:

```text
backend/app/services/session_summary.py
```

Keep the summary computation pure and deterministic.

A suitable public function shape is:

```python
def summarize_tutor_session(
    session: TutorSession,
    messages: Sequence[TutorMessage],
) -> TutorSessionSummaryResponse:
    ...
```

Equivalent naming is acceptable.

The service must not query the database itself.

The API owns authorization/querying; the service owns aggregation.

## Intent handling

Controlled persisted intent values are:

```text
attempt
hint_request
```

Use the existing `TutorReplyIntent` values or their `.value` strings rather than duplicating behavior inconsistently.

Legacy/unknown intent values must be counted as `unclassified_reply_count`.

Do not fail an otherwise valid summary because an old row has `reply_intent=None`.

## Latency handling

Only user messages with:

```text
response_latency_ms is not None
```

participate in:

- `timed_reply_count`
- `average_response_latency_ms`

Current M05-05 prevents new negative latency values, but summary logic should be read-only and should not mutate legacy values.

Do not calculate latency from timestamps in this task. Summarize the already persisted telemetry.

## Current state handling

Parse `TutorSession.current_state` through `TutorState`.

If persisted state is invalid, preserve the existing tutor API convention and return:

```text
HTTP 500
Tutor session is unavailable
```

Do not invent a fallback state.

## API query

Use a single message query for the session, ordered consistently if desired.

The summary does not depend on message order, so do not introduce multiple aggregation queries unless necessary.

Do not load another student's messages.

## Tests

Create:

```text
backend/tests/test_tutor_session_summary.py
```

Cover both pure aggregation and endpoint behavior as appropriate.

At minimum include:

### 1. Mixed attempt + hint summary

Given user messages containing:

- two `attempt` replies;
- one `hint_request`;
- deterministic latency values, for example:
  - 1000
  - 2000
  - 3000

Assert:

```text
student_reply_count == 3
attempt_reply_count == 2
hint_request_count == 1
unclassified_reply_count == 0
timed_reply_count == 3
average_response_latency_ms == 2000.0
```

### 2. Legacy/unclassified user replies

Include at least one user message with:

```text
reply_intent is None
```

and preferably one unknown non-NULL value.

Assert they contribute to:

```text
student_reply_count
unclassified_reply_count
```

but not attempt/hint counts.

### 3. Missing latency

Include user messages with `response_latency_ms=None`.

Assert:

- they still count as student replies/intents;
- they do not count in `timed_reply_count`;
- they do not affect average.

### 4. No timed replies

Assert:

```text
timed_reply_count == 0
average_response_latency_ms is None
```

### 5. Assistant messages ignored for reply metrics

Assistant messages may contain NULL or even synthetic telemetry in a test fixture.

They must not affect student reply/intent/latency counts.

### 6. Endpoint ownership / missing session

Use existing API-test conventions.

Assert the endpoint uses `owned_session` semantics and returns the existing 404 behavior for inaccessible/missing sessions.

### 7. Invalid persisted tutor state

An owned session with an invalid `current_state` must result in:

```text
HTTP 500
"Tutor session is unavailable"
```

### 8. Read-only / no AI

Assert summary endpoint:

- does not commit/mutate DB;
- does not call TutorAI.

If the fake test harness can expose commit count / AI calls, assert both.
