# M05-01 — Deterministic Tutor State Model

Status: ACTIVE
Codex: YES — SMALL

## Goal
Introduce an explicit, deterministic tutor state model without yet rewriting the entire tutor flow.

## Why now
The product must control tutoring progression in code rather than letting the LLM freely decide whether to hint, reveal or finish.

## Read only / primary context
- `AGENTS.md`
- `backend/AGENTS.md`
- `backend/app/services/AGENTS.md`
- `backend/app/services/tutor_ai.py`
- `backend/app/schemas/tutor.py`

## Allowed changes
- `backend/app/schemas/tutor.py`
- `backend/app/services/tutor_state.py` (new)
- `backend/tests/test_tutor_state.py` (new)

## Forbidden scope
- API routes
- database entities/migrations
- frontend
- OpenAI prompt rewrite
- dependency changes
- unrelated refactors

## Required v1 states
- DIAGNOSE
- ASK_ATTEMPT
- HINT_1
- HINT_2
- EXPLAIN_STEP
- VERIFY
- TRANSFER
- COMPLETE

## Requirements
1. Represent states with a typed enum.
2. Define a typed transition input/event model.
3. Define a pure deterministic transition function.
4. Reject impossible/unknown transitions explicitly.
5. No model/API/database calls inside the state module.

## Acceptance criteria
- [ ] state enum exists
- [ ] transition function is deterministic and pure
- [ ] happy-path state progression is tested
- [ ] wrong-attempt hint escalation is tested
- [ ] invalid transition behavior is tested
- [ ] only allowed files changed

## Targeted tests
```bash
cd backend && pytest -q tests/test_tutor_state.py
```

## Stop and report if
- existing schema makes the task impossible without changing API/database
- a new dependency appears necessary
- integrating this state model requires touching tutor routes in this ticket
