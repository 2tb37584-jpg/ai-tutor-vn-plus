# M05-13 — Record Deterministic Transfer Mastery Evidence

Status: READY
Codex: YES
Module: Tutor Engine / Mastery

## Goal

Record mastery evidence from deterministic transfer verification without changing transfer state-machine behavior.

When a tutor session is already in `TutorState.TRANSFER` and the authored transfer answer is deterministically verified:

```text
CORRECT   -> record verified transfer CORRECT evidence
INCORRECT -> record verified transfer INCORRECT evidence
```

The evidence must be explicitly marked:

```text
is_transfer=True
```

Unsupported, indeterminate, and missing-request outcomes must not create mastery evidence.

This task must not change recommendation behavior or transfer completion semantics.

## Context

Completed prerequisites:

- M05-09 persists `TutorSession.transfer_question_id`.
- M05-10 reconstructs the exact authored transfer item and builds its deterministic `VerificationRequest`.
- M05-11 deterministically selects and persists the authored same-skill transfer item.
- M05-12 makes deterministic transfer verification authoritative:
  - `CORRECT -> TRANSFER_COMPLETED -> COMPLETE`
  - all non-CORRECT outcomes remain `TRANSFER`
  - model `likely_correct` has no authority over transfer correctness.

The existing mastery service already accepts:

```text
MasteryEvidenceEvent(..., is_transfer=True)
```

M05-13 wires that existing capability to deterministic transfer outcomes only.

## Micro-task

Extend the existing M05-12 `current_state == TRANSFER` runtime branch.

Conceptually:

```text
transfer_request = _transfer_verification_request_for_session(...)
if transfer_request exists:
    result = verify(transfer_request)

    if result.status == CORRECT:
        record deterministic verified transfer CORRECT evidence
        emit TRANSFER_COMPLETED

    elif result.status == INCORRECT:
        record deterministic verified transfer INCORRECT evidence
        remain TRANSFER

    else:
        no mastery evidence
        remain TRANSFER
```

Do not record evidence when there is no deterministic transfer request.

Do not use model `likely_correct`.

## Evidence contract

For deterministic transfer `CORRECT`, create:

```text
outcome = CORRECT
evidence_type = DETERMINISTIC_VERIFICATION
verification_status = VERIFIED
confidence = 1.0
hint_count = 0
is_transfer = True
```

For deterministic transfer `INCORRECT`, create:

```text
outcome = INCORRECT
evidence_type = DETERMINISTIC_VERIFICATION
verification_status = VERIFIED
confidence = 1.0
hint_count = 0
is_transfer = True
```

Transfer hints are not supported in the current runtime, so:

```text
hint_count = 0
```

for transfer evidence in this task.

## Verification method contract

The mastery event's:

```text
verification_method
```

must come from the deterministic transfer request actually used for verification:

```text
transfer_request.family.value
```

Do not use the original session's:

```text
session.verification_family
```

because that field describes the original problem context and may differ from the authored transfer item.

## Skill contract

The mastery event must use:

```text
session.primary_skill
```

which has already been checked against the persisted authored transfer item's `skill_code` by the transfer verification adapter.

Do not infer another skill from model output.

## Outcome eligibility

Create transfer mastery evidence only for deterministic statuses:

```text
CORRECT
INCORRECT
```

Do not create evidence for:

```text
UNSUPPORTED
INDETERMINATE
missing transfer request
```

These outcomes are not reliable mastery signals.

## Runtime ordering

Preserve M05-12 completion semantics.

For `CORRECT`:

1. deterministic verify;
2. construct/record transfer mastery evidence;
3. transition through `TRANSFER_COMPLETED`;
4. persist/return `COMPLETE`.

The implementation may record evidence immediately before or immediately after calculating the authoritative next state, provided the existing transaction behavior remains coherent and no direct `COMPLETE` assignment is introduced.

For `INCORRECT`:

1. deterministic verify;
2. record transfer incorrect evidence;
3. remain `TRANSFER`.

Do not change the state machine.

## Model-output boundary

`likely_correct` must have zero influence on transfer mastery evidence.

Required regressions:

```text
deterministic INCORRECT + likely_correct=True
-> transfer INCORRECT evidence

deterministic CORRECT + likely_correct=False
-> transfer CORRECT evidence
```

The deterministic verifier status is authoritative.

## No duplication contract

Exactly one transfer mastery evidence event should be recorded per deterministically `CORRECT` or `INCORRECT` transfer answer processed by this runtime branch.

Do not record both:

```text
is_transfer=False
and
is_transfer=True
```

for the same transfer answer.

The existing non-transfer mastery path must remain unchanged.
