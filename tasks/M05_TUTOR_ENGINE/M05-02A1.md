# M05-02A1 — Add Persisted Tutor Session State

Status: DONE
Codex: YES — SMALL

## Goal

Add durable storage for the current tutor state on `TutorSession` and provide a safe Alembic migration.

This task adds persistence capability only. It does NOT wire `/start` or `/reply` to read/write the state yet.

## Context

M05-01 defined deterministic tutor states.

M05-02 integrated those states into `TutorAI`, but state currently exists only during a single service call.

Alembic is now the schema migration mechanism.

The development database is already at Alembic head.

Existing tutor sessions must remain valid when the new column is introduced.

## Allowed files

- backend/app/models/entities.py
- backend/alembic/versions/0002_tutor_session_state.py

## Forbidden scope

Do NOT modify:

- backend/app/api/**
- backend/app/services/**
- backend/app/schemas/**
- frontend/**
- docker-compose.yml
- Alembic baseline revision 0001
- dependencies
- task/status files during Codex implementation
- unrelated models or schema

Do not add a dependency.

## Requirements

1. Add `current_state` to `TutorSession`.

2. Persist it as a string column, not a PostgreSQL enum.

3. The final column must be:
   - non-nullable;
   - large enough for existing TutorState string values.

4. Preserve compatibility with the current `/tutor/start` code, which does not yet explicitly provide `current_state`.

5. Until M05-02A2 wires state explicitly, newly created sessions must safely default to:

   `ask_attempt`

6. Create Alembic revision:

   `0002_tutor_session_state`

   with:

   `down_revision = "0001_initial_schema"`

7. Existing TutorSession rows must be backfilled to:

   `ask_attempt`

   during migration.

8. Prefer a migration pattern that:
   - adds the column with a temporary server default;
   - safely backfills existing rows;
   - leaves the final schema without an unnecessary migration-only server default if the model uses an application-side default.

9. Downgrade must remove only the new column.

10. Do not introduce tutor-state transition logic in the model or migration.

## Acceptance criteria

- `TutorSession` exposes a non-null `current_state` string.
- Current route code remains compatible without changes.
- Existing session rows migrate successfully and receive `ask_attempt`.
- Migration has exactly one head after 0001.
- Upgrade from 0001 → 0002 succeeds on a disposable PostgreSQL database.
- Existing rows survive the migration.
- Downgrade 0002 → 0001 succeeds.
- `alembic check` reports no schema drift after upgrade.
- Existing backend tests pass.
- Only the two allowed implementation files change.

## Testing

Migration testing must use a disposable PostgreSQL database first.

The test must include at least one TutorSession row created while the database is still at revision 0001, then prove that after upgrading to 0002:

- the row still exists;
- `current_state = 'ask_attempt'`.

After disposable migration verification, run the backend regression suite.

Do not test migration by deleting the existing development database or Docker volume.

## Stop conditions

Stop and report instead of expanding scope if:

- API route changes are required;
- TutorAI changes are required;
- tutor schemas must change;
- another dependency is required;
- migration cannot preserve existing TutorSession rows;
- any file outside the two allowed implementation files is required.
