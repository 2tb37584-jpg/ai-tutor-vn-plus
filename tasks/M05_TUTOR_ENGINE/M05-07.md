# M05-07 — Add Explicit Transfer Completion Runtime Path

Status: BLOCKED
Codex: YES
Module: Tutor Engine

## Goal

Add an explicit, deterministic, testable runtime path from `TutorState.TRANSFER` to `TutorState.COMPLETE`.

This task only closes the existing tutor-state lifecycle gap.

Do not integrate next-best-question recommendation in this task.

## Context

M08-06 design review established that the global next-best-question recommender must run only after the current tutor session has actually completed.

The deterministic tutor state machine already defines:

```text
VERIFY -> TRANSFER -> COMPLETE
```

with:

```text
TutorState.TRANSFER
+ TutorTransitionEvent.TRANSFER_COMPLETED
-> TutorState.COMPLETE
```

However, repository inspection found that `TRANSFER_COMPLETED` currently appears only in:

- schema/state definitions;
- deterministic state-machine rules;
- tests.

The runtime tutor application path does not currently emit `TRANSFER_COMPLETED`.

Therefore `TutorState.COMPLETE` is not yet a reliable application seam for the later recommendation integration.

Existing runtime behavior already includes:

- deterministic verification;
- authoritative correction of tutor state;
- verified mastery evidence updates;
- answer-leakage guard;
- persisted `TutorSession.current_state`.

This task must add the smallest runtime behavior needed to make transfer completion explicit and testable without changing recommendation logic.

## Micro-task

When the current tutor state is `TRANSFER`, define and implement one explicit runtime event path that can advance the session to `COMPLETE`.

The behavior must reuse the existing deterministic state machine rather than assigning `COMPLETE` ad hoc.

Do not add global recommendation behavior.

## Design constraints

The implementation must preserve these boundaries:

- `tutor_state.py` remains the source of truth for deterministic state transitions.
- `TutorAI` remains generation-oriented and must not gain DB/recommendation responsibility.
- API/application orchestration may invoke deterministic transition logic.
- verification/mastery behavior must not be broadened.
- the current session must not be replaced with a different question.
- `TRANSFER_COMPLETED` must be explicit and testable.

## Required behavior

The runtime path must satisfy:

1. A tutor reply handled while the session is in `TutorState.TRANSFER` can produce an explicit `TRANSFER_COMPLETED` event when the transfer activity is considered complete under the existing tutor-turn contract.

2. The final state must be produced by:

```python
transition_tutor_state(
    TutorTransitionInput(
        state=TutorState.TRANSFER,
        event=TutorTransitionEvent.TRANSFER_COMPLETED,
    )
)
```

or an equivalent existing deterministic orchestration helper.

3. The resulting `TutorTurn.state` and persisted `TutorSession.current_state` must both become `TutorState.COMPLETE`.

4. The normal response remains a `TutorReplyResponse` containing the resulting `TutorTurn`.

5. The answer-leakage guard must continue to allow the existing COMPLETE-state behavior and must not be weakened for earlier states.

6. No mastery update should be created merely because transfer completed unless the current verified-mastery contract already requires it.

7. No next-best-question recommendation may run in this task.

## Completion semantics

Prefer the smallest behavior consistent with the existing tutor-turn contract.

Do not invent a new public request field or schema solely to signal transfer completion.

If the existing `TutorTurn` / `likely_correct` semantics are insufficient to determine transfer completion safely and deterministically, STOP and report rather than adding a speculative API or schema change.

## Blocker discovered

Repository inspection confirmed that the existing tutor-turn contract is not sufficient to determine transfer completion safely and deterministically.

Evidence:

- `TutorAI._with_continued_turn_state(...)` only interprets `likely_correct` while `current_state` is in `_ATTEMPT_STATES`.
- For non-attempt states, including `TutorState.TRANSFER`, `likely_correct=True` and `likely_correct=False` are intentionally ignored and the state is retained.
- `backend/tests/test_tutor_ai_state.py` explicitly locks this behavior in `test_non_attempt_states_retain_state_despite_correctness_signal`.
- Therefore reusing `likely_correct` as `TRANSFER_COMPLETED` evidence would change an existing semantic contract rather than merely wiring a missing runtime event.
- `likely_correct` is model-provided generation output, not deterministic verification evidence.
- The current transfer generation policy can ask a related case, but the inspected contract does not provide a deterministic expected answer / verifier contract for that generated transfer case.

Result:

M05-07 hits its declared stop condition:

> existing `TutorTurn` semantics cannot safely represent transfer completion.

Do not implement or hand this task to Codex while this blocker remains.

A separate design decision is required to define deterministic transfer-completion evidence before this task can return to `READY`.
