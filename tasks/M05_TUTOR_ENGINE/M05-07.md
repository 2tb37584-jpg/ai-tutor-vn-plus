# M05-07 — Add Explicit Transfer Completion Runtime Path

Status: DONE
Codex: NO
Module: Tutor Engine

## Goal

Add an explicit, deterministic, testable runtime path from `TutorState.TRANSFER` to `TutorState.COMPLETE`.

This task closes the tutor-state lifecycle gap without integrating next-best-question recommendation.

## Context

The deterministic tutor state machine already defines:

```text
VERIFY -> TRANSFER -> COMPLETE
```

with:

```text
TutorState.TRANSFER
+ TutorTransitionEvent.TRANSFER_COMPLETED
-> TutorState.COMPLETE
```

M05-07 was originally blocked because the runtime had no deterministic transfer-completion evidence. Reusing model-provided `likely_correct` was explicitly rejected because it is not trustworthy deterministic evidence for transfer completion.

That blocker has now been resolved by the completed prerequisite chain:

```text
M05-09 — Persist authored transfer item identity
M05-10 — Add deterministic transfer verification adapter
M05-11 — Select and persist deterministic transfer item
M05-12 — Wire deterministic TRANSFER verification and completion
M05-13 — Record deterministic transfer mastery evidence
```

Together these tasks provide the explicit runtime completion path required by M05-07.

## Implemented runtime contract

The implemented flow is:

```text
enter TRANSFER
→ select deterministic authored same-skill transfer item
→ persist exact transfer_question_id
→ later TRANSFER turn reconstructs exact authored item
→ build deterministic transfer VerificationRequest
→ verify learner answer
→ CORRECT
→ emit TRANSFER_COMPLETED
→ existing tutor state machine
→ COMPLETE
```

All other deterministic outcomes:

```text
INCORRECT
UNSUPPORTED
INDETERMINATE
missing transfer request
```

remain in:

```text
TRANSFER
```

Model `likely_correct` has no authority over transfer correctness or completion.

## Deterministic evidence boundary

Transfer correctness is based only on the persisted authored transfer item and its deterministic verifier contract.

The runtime does not use:

```text
likely_correct
model prose
skill-only transfer lookup
original-session verification context
```

as completion evidence.

The authored transfer item's verifier family is also used for transfer-specific mastery evidence.

## Transfer mastery evidence

For reliable deterministic transfer outcomes:

```text
CORRECT
INCORRECT
```

the runtime records exactly one verified mastery evidence event with:

```text
is_transfer=True
evidence_type=DETERMINISTIC_VERIFICATION
verification_status=VERIFIED
confidence=1.0
hint_count=0
```

The event's:

```text
verification_method
```

comes from the actual transfer request family, not the original session's `verification_family`.

No transfer mastery evidence is created for:

```text
UNSUPPORTED
INDETERMINATE
missing transfer request
```

## Recommendation boundary

Next-best-question recommendation is not part of M05-07.

The completed transfer runtime does not invoke the recommender.

Recommendation remains a separate post-completion concern.

## Transfer hint boundary

Transfer hints remain intentionally unchanged.

The current state machine does not add a new:

```text
TRANSFER + HINT_REQUESTED
```

path as part of this task.

That UX is separate from M05-07 completion semantics.

## Resolved blocker

The original blocker was:

> existing `TutorTurn` semantics cannot safely represent transfer completion.

That conclusion remains correct for model-only `TutorTurn.likely_correct`.

The blocker was resolved without changing that semantic contract.

Instead, the runtime now uses deterministic authored transfer evidence:

```text
persisted transfer_question_id
→ exact authored transfer item
→ deterministic verifier request
→ deterministic verifier result
→ TRANSFER_COMPLETED only on CORRECT
```

Therefore M05-07 no longer depends on model correctness signals and is ready for closure.
