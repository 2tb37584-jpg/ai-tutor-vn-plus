# M05-02A2 — Wire Persisted State Through Tutor API

Status: ACTIVE
Codex: YES — SMALL

## Goal

Wire the persisted TutorSession.current_state through `/tutor/start` and `/tutor/reply`.

This task connects the deterministic TutorAI state from M05-02 with the durable TutorSession state added in M05-02A1.

## Prerequisites

- M05-01 DONE — deterministic tutor state model.
- M05-02 DONE — TutorAI state integration.
- M05-02A1 DONE — TutorSession.current_state persistence.

## Current state

TutorSession has:

`current_state: str`

with default:

`ask_attempt`

TutorAI.first_turn() returns TutorTurn with an application-controlled state.

TutorAI.continue_turn() accepts:

`current_state: TutorState`

as a keyword-only argument and returns a TutorTurn containing the next application-controlled state.

The API route currently does not thread persisted state through these calls.

## Requirements

### /tutor/start

After `TutorAI.first_turn()` returns:

1. Store the returned tutor state in `TutorSession.current_state`.
2. Persist the string enum value, e.g. `"ask_attempt"`.
3. Do not derive the state from free-form model text.
4. Existing API request/response compatibility must be preserved.

### /tutor/reply

1. Read `session.current_state`.
2. Convert it explicitly to `TutorState`.
3. Pass it to:

   `TutorAI.continue_turn(..., current_state=current_state)`

4. After TutorAI returns, persist:

   `session.current_state = tutor_turn.state.value`

5. Persist the state in the same transaction as the assistant message.

6. Do not independently calculate next state in the API layer.

7. Do not infer state from message text, hint_level, next_action or other free-form fields.

### Invalid persisted state

If `session.current_state` cannot be parsed as TutorState:

- fail explicitly;
- do not silently reset it to ASK_ATTEMPT;
- do not call TutorAI with an invented state.

Use an internal/server error response without leaking unnecessary implementation details.

## Acceptance criteria

- `/tutor/start` persists the state returned by `TutorAI.first_turn()`.
- A new session begins persisted as `ask_attempt`.
- `/tutor/reply` reads persisted state and supplies it to `TutorAI.continue_turn()`.
- `/tutor/reply` persists the returned next state.
- State survives across multiple reply requests.
- API layer never computes state transitions itself.
- Invalid persisted state fails explicitly rather than silently resetting.
- Existing tutor API request shapes remain compatible.
- Existing response contracts remain compatible.
- Existing TutorAI/state tests continue to pass.
- Only the two allowed files change.

## Tests

Create:

`backend/tests/test_tutor_api_state.py`

Use FastAPI TestClient and dependency overrides or an equivalent isolated route test approach.

Tests must prove at minimum:

1. Starting a tutor session stores `ask_attempt`.

2. A reply reads the session's persisted current_state and passes the corresponding TutorState to TutorAI.

3. The state returned by TutorAI is written back to TutorSession.current_state.

4. State persists across two sequential reply requests, for example:

   ASK_ATTEMPT -> HINT_1 -> HINT_2

   The test may use a fake TutorAI so it verifies API persistence/wiring rather than duplicating TutorAI transition logic.

5. An invalid persisted current_state fails explicitly and is not silently reset.

6. Existing API request shape does not require a client-supplied tutor state.
