# M05-05 — Record Student Reply Latency

Status: ACTIVE
Codex: YES

## Goal

Record server-derived student reply latency for accepted `/tutor/reply` turns.

The system must distinguish whether the recorded reply was:

- a normal student attempt; or
- an explicit hint request.

This task is telemetry only. It must not change tutor behavior, state transitions, mastery, misconception logic, or API response semantics.

## Context

The current tutor conversation persists every accepted turn in `tutor_messages`.

Current relevant model:

```text
TutorMessage
- id
- session_id
- role
- content
- created_at
```

Current `/tutor/reply` flow:

1. load owned session;
2. parse current TutorState;
3. validate explicit hint requests;
4. load previous TutorMessage history;
5. add user TutorMessage;
6. call TutorAI;
7. guard answer leakage;
8. update session state;
9. add assistant TutorMessage;
10. commit.

Rejected hint requests return HTTP 409 before any user TutorMessage is persisted.

`Attempt` is a separate client-claim endpoint and is not the source of truth for conversation reply timing.

## Module / micro-task

Module:

`M05 Tutor Engine`

Micro-task:

Persist latency metadata on accepted user-side `TutorMessage` records created by `/tutor/reply`.

## Data contract

Add nullable columns to `tutor_messages`:

```text
reply_intent          VARCHAR(32) NULL
response_latency_ms   INTEGER NULL
```

Meaning:

### `reply_intent`

For user messages created by `/tutor/reply`, persist the request intent value:

```text
attempt
hint_request
```

Assistant messages keep:

```text
NULL
```

Legacy messages remain valid with `NULL`.

### `response_latency_ms`

For accepted user messages created by `/tutor/reply`, compute elapsed time between:

```text
the most recent previous assistant TutorMessage.created_at
```

and:

```text
the server-side receipt time for the current accepted reply
```

Persist whole milliseconds.

Rules:

- source must be server-derived;
- do not accept latency from the client;
- do not trust a client timestamp;
- never persist a negative latency;
- if no previous assistant message exists, persist `NULL` rather than failing the request;
- rejected/invalid turns must not create latency telemetry.

## Privacy / minimization

Do not add or persist:

- IP address;
- device identifier;
- browser fingerprint;
- raw client clock timestamp;
- geolocation;
- any new student profile field.

Persist only the intent category and elapsed milliseconds required by this roadmap item.

## API behavior

Update only `/tutor/reply`.

At request processing time, capture a server-side receipt timestamp.

The exact implementation may use a small private helper, but keep it local and deterministic.

After loading previous session messages:

1. find the most recent previous message whose:
   ```text
   role == "assistant"
   ```
2. if found, compute:
   ```text
   received_at - previous_assistant.created_at
   ```
3. convert to non-negative whole milliseconds;
4. create the user `TutorMessage` with:
   ```text
   reply_intent=payload.intent.value
   response_latency_ms=<computed value>
   ```

The timestamp used for the current reply must be captured before the AI call so model/network generation time is never included in student response latency.

Use server time only.

### Time compatibility

Existing DB timestamps are naive UTC-style `DateTime`.

Do not perform a project-wide datetime migration.

Use a server-side timestamp compatible with the existing naive timestamp values. Avoid introducing timezone-aware/naive subtraction errors.

## Hint behavior

For accepted explicit hint requests:

```text
reply_intent == "hint_request"
```

and latency is computed normally.

For unsupported hint requests that return HTTP 409:

- no user message is persisted;
- no latency row/event is persisted;
- AI is not called;
- existing behavior remains unchanged.

## Attempt behavior

For normal `/tutor/reply` requests:

```text
reply_intent == "attempt"
```

including requests where the client omitted `intent` and the schema default resolves it to `attempt`.

Do not change `/tutor/attempt`.

## Failure behavior

If a legacy or unusual session has no prior assistant message:

- allow the accepted reply to proceed;
- persist the user message with:
  ```text
  response_latency_ms = NULL
  ```
- still persist the resolved `reply_intent`.

Do not synthesize latency from session creation time.

## Tests

Add focused API persistence tests.

Tests must not use real sleep delays.

Control time deterministically using persisted message timestamps and/or a patchable clock boundary.

At minimum test:

### 1. Attempt latency

Given a session with a previous assistant message at a controlled timestamp, an accepted attempt reply persists exactly one new user TutorMessage with:

```text
reply_intent == "attempt"
response_latency_ms == expected deterministic value
```

The assistant message created afterward must keep both telemetry fields `NULL`.

### 2. Hint-request latency

Given a hint-eligible state and previous assistant timestamp, an accepted explicit hint request persists the user message with:

```text
reply_intent == "hint_request"
response_latency_ms == expected deterministic value
```

### 3. Rejected hint request

Given a tutor state where explicit hint request is invalid:

- endpoint returns HTTP 409;
- no user TutorMessage is persisted;
- no latency telemetry is persisted;
- preserve the existing no-AI-call behavior if the existing test harness exposes it.

### 4. No prior assistant message

Given an owned session with no assistant message, an accepted reply persists:

```text
reply_intent == "attempt"
response_latency_ms is None
```

and the request does not fail because timing context is absent.

### 5. Non-negative clamp

If controlled test timestamps would produce a negative duration because of clock skew or inconsistent legacy data:

```text
response_latency_ms == 0
```

Do not persist negative milliseconds.
