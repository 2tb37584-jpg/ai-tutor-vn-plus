# M05-08 — Define Deterministic Transfer Completion Contract

Status: DONE
Codex: NO
Module: Tutor Engine

## Goal

Define the deterministic contract required to complete a tutor transfer activity safely and testably.

This is a design/decomposition task only.

Do not modify product code in this task.

The output must be sufficient to decide whether `M05-07 — Add Explicit Transfer Completion Runtime Path` can be unblocked and, if so, what the smallest implementation scope should be.

## Context

`M05-07` is currently BLOCKED.

Repository inspection established:

- the tutor state machine already defines `TRANSFER + TRANSFER_COMPLETED -> COMPLETE`;
- the runtime tutor flow does not currently emit `TRANSFER_COMPLETED`;
- `TutorAI._with_continued_turn_state(...)` only interprets `likely_correct` in attempt states;
- `TutorState.TRANSFER` intentionally ignores `likely_correct=True/False`;
- existing tests explicitly lock that non-attempt-state behavior;
- `likely_correct` is model-provided generation output, not deterministic verification evidence;
- the current transfer generation policy can ask a related case, but the inspected contract does not expose a deterministic expected-answer/verifier contract for that generated transfer case.

Therefore the missing problem is not merely wiring an event.

The project needs an explicit transfer-completion contract before runtime implementation.

## Design questions

Determine and document:

1. Who owns creation of the transfer activity.
2. Whether the transfer activity is:
   - generated dynamically by the model;
   - selected deterministically from an authored source;
   - derived deterministically from the current problem;
   - or another explicitly justified approach.
3. How the transfer activity obtains:
   - problem text;
   - target skill;
   - expected answer or verification reference;
   - verification family;
   - any metadata required for deterministic verification.
4. Whether the existing verifier can validate the transfer answer without new verifier behavior.
5. What exact evidence constitutes `TRANSFER_COMPLETED`.
6. What evidence keeps the tutor in `TRANSFER`.
7. Whether incorrect transfer evidence should:
   - remain in `TRANSFER`;
   - return to `EXPLAIN_STEP`;
   - use another existing transition;
   - or require a state-machine change.
8. Whether transfer completion should update mastery.
9. Whether transfer activity data must be persisted in `TutorSession` or elsewhere.
10. Whether the current API/schema can represent the required transfer contract without modification.
11. Whether the answer-leakage guard needs any new policy for transfer.
12. The smallest implementation scope required to unblock `M05-07`.

## Product constraints

The design must preserve:

- Socratic tutoring before direct-answer solving;
- deterministic verification whenever feasible;
- generation and verification separation;
- explicit/testable tutor progression;
- no early answer leakage;
- modular monolith architecture;
- student-data minimization;
- no new dependency without demonstrated need.

A model-generated assertion that an answer is correct is not sufficient evidence for transfer completion.

## Preferred design direction

Prefer a transfer activity whose verification contract is deterministic before the student answers.

Strong preference order:

```text
1. authored/deterministic transfer item with known verification reference
2. deterministic transformation with known verification reference
3. model-generated transfer item only if independently verifiable before presentation
4. model-only correctness judgment — unacceptable
```

This preference is not itself an implementation decision. Repository inspection must confirm which option fits the existing architecture with the smallest safe scope.

`TRANSFER_COMPLETED` may only be emitted from evidence that is independently checkable by deterministic application logic.

## Transfer completion decision

### Transfer activity source

Use an authored deterministic transfer item as the target contract.

The existing Grade 8 algebra question bank is the preferred source because each `QuestionBankItem` already carries a verification contract before the student sees the problem:

```text
id
skill_code
problem_text
verification_reference
expected_answer
verification_family
difficulty
```

The bank also validates each authored verification pair through the existing deterministic verifier at load time.

Do not use model-only transfer generation as the completion source.

Do not treat `TutorTurn.likely_correct` as transfer evidence.

Current blocker: the bank is not yet a universal transfer source. Repository inspection shows:

```text
mastery-bearing skills: 10
skills represented in question bank: 7
missing:
- algebra.factorization
- algebra.rational_expression.domain
- algebra.rational_expression.simplify
```

In addition, the session fallback skill `general.problem_solving` is not proven to have an authored deterministic transfer contract.

Therefore transfer coverage must be made explicit before the runtime completion task can be unblocked.

### Transfer contract

For a transfer-eligible session, the selected authored item owns:

```text
problem text            = QuestionBankItem.problem_text
target skill            = QuestionBankItem.skill_code
verification reference  = QuestionBankItem.verification_reference
expected answer          = QuestionBankItem.expected_answer
verification family      = QuestionBankItem.verification_family
```

The transfer item should target the current session's learned skill, not a global next-best skill.

Selection must be deterministic.

A follow-on implementation should use a stable authored-item selector for the current skill and must not use randomization.

If multiple items exist for a skill, the selector must choose one reproducibly. A stable session identifier may be used as part of that selector.

The selector should avoid presenting the exact current problem again when that can be determined safely, but correctness of reconstruction is more important than heuristic variation.

### Lifecycle owner

Transfer activity ownership belongs to an application/service seam, not `TutorAI`, ORM models, or the global question recommender.

The application/service seam is responsible for:

```text
select authored transfer item
-> persist/reconstruct its identity
-> present item.problem_text
-> verify the later student response
-> map verified correctness to tutor-state behavior
```

`TutorAI` may continue to generate pedagogical language around the flow, but it must not own the verification reference or decide that transfer is complete.

When deterministic verification moves the tutor from `VERIFY` to `TRANSFER`, the runtime response must present the selected authored transfer activity rather than relying on a free-form model-generated transfer problem whose verification contract is unknown.

The existing `TutorTurn.message` is sufficient as the public presentation surface for the authored transfer problem.

### Persistence

The current `TutorSession` persists only one problem verification contract:

```text
normalized_problem
primary_skill
internal_expected_answer
verification_family
```

Those fields belong to the original tutoring problem.

They must not be overwritten with transfer data because doing so would destroy the original session contract and make session behavior harder to reason about.

The transfer activity spans requests:

```text
request N:
verified current problem
-> enter TRANSFER
-> present transfer item

request N+1:
student answers transfer item
-> verify that exact item
```

Therefore runtime code must be able to reconstruct the exact authored item on request N+1.

Current `skill_code` alone is insufficient because several skills have multiple authored questions:

```text
algebra.equation.equivalent_transform -> 2 items
algebra.linear_equation -> 2 items
arithmetic.signed_number_operations -> 4 items
```

Minimum persistence decision:

```text
TutorSession.transfer_question_id: nullable string
```

The value references an authored `QuestionBankItem.id`.

Persist the ID when the transfer activity is selected.

Retain it through completion so the transfer contract remains reproducible.

Do not persist duplicated problem text, expected answer, or verifier data when those can be reconstructed from the immutable authored item.

This requirement needs a separate model + migration implementation task before M05-07 can be unblocked.

No public API field is required for this persistence.

### Verification

Reuse the existing deterministic verifier unchanged.

Do not add a second verifier framework.

Build the transfer verification request from the persisted `QuestionBankItem` and the student's candidate answer:

```text
numeric:
    expected = item.verification_reference
    candidate = student response

expression_equivalence:
    left = item.verification_reference
    right = student response

linear_equation:
    equation = item.verification_reference
    candidate = student response
```

This differs from `_verification_request_for_session(...)`, which currently reads the original-problem contract from `TutorSession`.

Therefore the existing session helper cannot be reused unchanged for transfer.

A small transfer-specific adapter/service should construct the verifier request from `QuestionBankItem`.

The transfer completion path must use deterministic verifier output directly.

Model-provided `likely_correct` must not override transfer verification.

### Completion mapping

Only independently verified correct transfer evidence may emit:

```text
TutorState.TRANSFER
+ TutorTransitionEvent.TRANSFER_COMPLETED
-> TutorState.COMPLETE
```

The final state must still be produced by `transition_tutor_state(...)`.

Do not assign `TutorState.COMPLETE` directly.

The returned `TutorTurn.state` and persisted `TutorSession.current_state` must both become `COMPLETE`.

### Non-completion mapping

Use the smallest behavior compatible with the existing state machine.

#### Verified incorrect

Remain in:

```text
TutorState.TRANSFER
```

Do not emit `TRANSFER_COMPLETED`.

Do not introduce a new incorrect-transfer transition in the first implementation.

#### Unsupported / indeterminate / otherwise unknown deterministic verification

Remain in:

```text
TutorState.TRANSFER
```

Do not complete.

Do not collapse unknown verification into correct.

Do not let model confidence convert unknown verification into completion.

#### Hint/help request during TRANSFER

Current deterministic state rules do not define:

```text
TRANSFER + HINT_REQUESTED
```

The API validates hint transitions before calling `TutorAI`, so a hint request while in `TRANSFER` currently returns HTTP `409` and does not mutate tutor state.

Preserve that behavior in the minimal transfer-completion implementation.

Improving transfer-specific hint UX requires a separate state/product decision and is outside M05-07.

### Mastery

A verified transfer answer represents a distinct student exposure and is pedagogically meaningful evidence.

Target design:

- record mastery only when transfer verification is deterministically classified as correct or incorrect;
- attribute the evidence to the transfer item's `skill_code`;
- mark the evidence as transfer evidence using the existing `is_transfer=True` contract;
- do not count the previously solved original problem again;
- do not create mastery evidence for UNKNOWN/unverifiable results or a rejected hint request.

If the existing mastery service cannot accept this event unchanged, split that implementation rather than broadening M05-07.

### API/schema

No public request or response field is required for the target design.

Existing surfaces are sufficient:

```text
TutorReplyRequest.student_message
TutorReplyRequest.intent
TutorReplyResponse.tutor
TutorTurn.message
TutorTurn.state
```

The authored transfer problem can be presented in `TutorTurn.message`.

Internal persistence does require a new nullable session field for the selected transfer item ID.

That model/migration change must be implemented separately.

### Answer leakage

The current reply guard uses:

```text
session.internal_expected_answer
```

which belongs to the original problem.

While the session is in `TRANSFER`, guarding only against the original answer is insufficient.

The transfer path must guard generated/presented tutoring language against:

```text
selected_transfer_item.expected_answer
```

when transfer is active.

Do not weaken the existing answer-leakage rules for earlier states.

The authored transfer prompt itself may contain the problem statement but must not expose its authored final answer.

### Existing verifier reuse

Decision: reuse the current deterministic verifier unchanged.

Supported authored question-bank families already match the verifier families:

```text
numeric
expression_equivalence
linear_equation
```

The missing work is not a verifier capability.

The missing work is:

1. universal/explicit transfer-item coverage;
2. transfer-item identity persistence;
3. transfer-specific verification adaptation;
4. runtime completion orchestration.


The service should own deterministic item reconstruction and verifier-request construction.

The API/application orchestration should own lifecycle timing and state persistence.

Do not put transfer verification policy into `TutorAI`.

### Tests

Prerequisite coverage tests:

```text
every transfer-eligible skill has at least one authored transfer item
every authored transfer item has a supported verification family
every authored verification pair self-validates
selection is deterministic
```

Persistence tests:

```text
selected transfer_question_id survives commit/reload
nullable field does not affect pre-transfer sessions
invalid migration state is not introduced
```

M05-07 runtime tests:

```text
VERIFY + verified original answer selects/persists a transfer item
returned TRANSFER turn presents that authored item
later TRANSFER reply reconstructs the same item by ID
verified correct transfer answer -> TRANSFER_COMPLETED -> COMPLETE
persisted TutorSession.current_state == "complete"
returned TutorTurn.state == COMPLETE

verified incorrect transfer answer -> remains TRANSFER
UNKNOWN/unsupported/indeterminate transfer answer -> remains TRANSFER
hint request during TRANSFER -> existing 409, state unchanged

model-provided likely_correct cannot override deterministic transfer verification
transfer answer is checked against item.verification_reference, not original-session answer
answer-leakage guard uses transfer expected_answer while transfer is active
original ASK_ATTEMPT/HINT/VERIFY behavior remains unchanged
no next-best-question recommendation runs during transfer completion
```

If transfer mastery is enabled:

```text
verified transfer result creates exactly one transfer mastery event
event skill == transfer item skill
is_transfer == True
prior solved problem is not counted again
UNKNOWN/hint request creates no mastery event
```

### M05-07 unblock decision

Decision: **keep M05-07 BLOCKED**.

It must not return to READY yet.

Before unblocking, all of the following must be true:

1. every transfer-eligible skill has an authored deterministic transfer contract;
2. fallback/non-mastery skill behavior is explicitly resolved;
3. the exact selected transfer item can be reconstructed on the student's next request;
4. `transfer_question_id` persistence exists and is tested;
5. deterministic verifier input can be built from the selected authored item;
6. verified correct maps unambiguously to `TRANSFER_COMPLETED`;
7. incorrect/unknown behavior remains explicitly non-completing;
8. transfer hint behavior remains explicit;
9. no model-only correctness signal is required;
10. M05-07 allowed files are updated to the reviewed runtime seam.

### Risks

- Using the global next-best-question recommender for transfer would conflate remediation/scheduling with same-skill transfer.
- Using model-generated `likely_correct` would violate deterministic completion requirements.
- Overwriting the original session verification fields with transfer data would corrupt the original tutoring contract.
- Reconstructing a transfer item from `skill_code` alone is ambiguous for skills with multiple items.
- Treating the current 7/10 question-bank coverage as universal would leave some sessions unable to complete.
- Ignoring fallback/non-mastery skills could leave the tutor stuck in TRANSFER.
- Reusing the original answer-leakage reference during transfer could guard the wrong final answer.
- Expanding state-machine semantics for transfer hints or incorrect answers inside M05-07 would create scope creep and should be a separate product decision if desired.
