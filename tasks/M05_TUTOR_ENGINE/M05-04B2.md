# M05-04B2 — Persist Expected Answer From Tutor Start

Status: ACTIVE
Codex: YES — SMALL

## Goal

Persist the internal expected answer produced by problem analysis into the newly created TutorSession during `/tutor/start`.

This task wires existing internal data to existing internal storage only.

It does NOT implement runtime answer-leakage detection.

## Context

`ProblemAnalysis.expected_answer` already exists as server-internal analysis data.

`TutorSession.internal_expected_answer` was added in M05-04B1 and is now available in the database.

`/tutor/start` creates the TutorSession after problem analysis.

The student-facing start response must continue to exclude internal answer-bearing fields.

## Allowed implementation files

- backend/app/api/tutor.py
- backend/tests/test_tutor_api_leakage.py

## Forbidden scope

Do NOT modify:

- backend/app/schemas/**
- backend/app/services/**
- backend/app/models/**
- backend/alembic/**
- frontend/**
- verifier logic
- tutor state transitions
- runtime answer-leakage detection
- dependencies
- Docker files
- task/status files during Codex implementation

Do not add a dependency.

## Required behavior

During `/tutor/start`, when creating the new TutorSession:

- set `session.internal_expected_answer` from `analysis.expected_answer`;
- preserve the existing normalized problem, primary skill, state, title, status, and message behavior;
- continue passing the original internal `ProblemAnalysis` object to `TutorAI.first_turn`;
- do not mutate `ProblemAnalysis`;
- do not expose `internal_expected_answer` or `expected_answer` through the student API response.

The persisted value must come from the internal analysis object, not from request data or model-generated TutorTurn data.

## Security boundary

The expected answer remains server-internal.

Do not add `internal_expected_answer` to:

- StudentProblemAnalysis
- StartTutorResponse
- TutorReplyResponse
- frontend response types

The existing safe public-analysis allow-list must remain unchanged.

## Acceptance criteria

- `/tutor/start` persists `analysis.expected_answer` into `TutorSession.internal_expected_answer`.
- TutorAI `first_turn` still receives the original internal `ProblemAnalysis`.
- Student-facing serialized response still excludes `expected_answer`.
- Student-facing serialized response still excludes `verification_notes`.
- Student-facing serialized response does not contain the secret expected-answer value.
- Public analysis field allow-list remains unchanged.
- Existing tutor state behavior remains unchanged.
- Existing request shape remains unchanged.
- No schema or migration changes.
- Only the two allowed implementation files change.
- Existing API state tests remain green.
- Full backend test suite remains green.

## Tests

Extend `backend/tests/test_tutor_api_leakage.py`.

At minimum prove:

1. Internal `ProblemAnalysis.expected_answer` contains a distinctive secret value.
2. `/tutor/start` creates a TutorSession whose `internal_expected_answer` equals that secret value.
3. The exact internal `ProblemAnalysis` object is still passed to `TutorAI.first_turn`.
4. Serialized `StartTutorResponse.analysis` contains exactly:

   - normalized_problem
   - subject
   - grade_band
   - skills
   - prerequisites
   - confidence

5. Serialized response contains neither:
   - `expected_answer`
   - `verification_notes`
   - `internal_expected_answer`
   - the secret expected-answer value
   - the secret verification-note value

Run targeted:

`docker compose exec backend pytest -q tests/test_tutor_api_state.py tests/test_tutor_api_leakage.py`

Then full backend:

`docker compose exec backend pytest -q`
